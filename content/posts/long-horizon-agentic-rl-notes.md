给模型一个 Simulink 任务：调整控制器，使超调量不超过 5%，调节时间不超过 2 秒。

模型需要读取工程、理解参数、修改控制器、运行仿真，再根据结果继续调整。一次仿真失败后，它还要判断：是参数不合适，还是修改错了位置？此前有效的调整应该保留，还是全部推倒重来？

这类任务让我逐渐理解了 Long-Horizon Agentic RL 的难点：模型要在一串相互依赖的决策中学习，训练系统还必须知道如何执行、验证和评价这串决策。

沿着这个问题，我梳理了 GiGPO、AgentGym-RL、BEACON、SkyRL-Agent、RAGEN、WebRL、Agent Lightning 和 SWE-Gym。它们分别处理信用分配、训练预算、采样效率、稳定性、业务接入和验证问题。

本文基于已经阅读的论文、仓库说明和部分代码。旅行、CAD、Simulink 示例用于解释业务迁移思路；文中不报告尚未完成的 GPU 训练结果，也不把接口适配当成实验复现。

## 1. Long Horizon 难在哪里

以 CAD 支架建模为例：

```text
读取需求 → 建立草图 → 约束尺寸 → 拉伸实体
→ 定位孔 → 打孔 → 倒角 → 导出 → 几何验证
```

这些操作有真实依赖。草图尺寸错了，后面的加工即使执行成功，最终模型也可能不合格；倒角失败，也不代表前面的底板和孔全部做错。

因此，任务是否具有长程难度，不能只看模型是否输出了很长的推理，或把工具调用上限设成 50 步。更关键的是：前面的决策是否影响后面的可行性，模型是否必须根据环境反馈调整行为，以及失败后是否需要恢复。

训练时还有三类困难。

第一，奖励往往很稀疏。几十次操作后才知道任务是否成功，初始模型可能尝试很多次都失败。

第二，最终成败难以解释每一步的贡献。模型可以在前半段操作正确、后半段失败，也可能绕了很多弯路后偶然成功。

第三，执行环境需要成本。网页等待、单元测试和仿真都可能很慢，还可能产生与模型能力无关的故障。

这八个项目，需要放在这些具体问题里理解。

## 2. 先分清：算法、环境和训练框架

| 项目 | 主要解决的问题 | 主要定位 |
|---|---|---|
| verl-agent / GiGPO | 如何给多轮行为提供更细的优势信号 | 多轮训练框架与信用分配算法 |
| AgentGym-RL | 如何逐阶段增加可用交互预算 | 多环境训练框架与课程策略 |
| BEACON | 如何利用里程碑和部分成功 | 奖励塑造与分段优势 |
| SkyRL-Agent | 如何组织工具执行和高效采样 | Agent 执行与训练集成 |
| RAGEN / RAGEN-2 | 如何发现并缓解多轮训练退化 | 训练框架、诊断与稳定性干预 |
| WebRL | 如何生成新任务、评价结果并复用经验 | 网页 Agent 训练流程 |
| Agent Lightning | 已有 Agent 如何连接采样和训练 | 训练接入与调度框架 |
| SWE-Gym | 如何提供可执行、可验证的代码任务 | 环境、数据及 Agent/Verifier 训练方案 |

一个环境可以支持 GRPO，但不代表环境本身就是 GRPO 算法。一个框架使用 Actor 和 Critic，也不能据此判断它采用标准 PPO。

## 3. GiGPO：在相同状态附近比较行为

普通结果奖励 GRPO 的典型做法是：对同一个任务采样多条轨迹，再根据组内奖励差异计算优势。

```text
同一任务采样四次 → 最终奖励 [0, 1, 0, 1]
```

它能比较整条尝试的结果，但如果把同一个轨迹优势用于全部生成动作，局部决策的好坏就容易被最终成败掩盖。

GiGPO 在轨迹级比较之外，增加状态分组：把轨迹中相同或满足匹配条件的状态组织起来，比较从这些状态出发的后续表现，构造更局部的优势信号。

例如，两次旅行规划都已经找到合适交通，接下来需要选择酒店。一次选择导致超预算，另一次满足约束。局部比较希望更集中地评价这个位置的决策，而不只给整条行程一个统一评价。

它的价值在于改变优势来源，增加信用分配的分辨率。不过，局部回报仍然受后续动作影响，状态匹配也需要足够的重复访问或可靠的相似性定义。连续变化、部分可观测的业务环境里，这些条件并不天然成立。

对应来源：[GiGPO 论文](https://arxiv.org/abs/2505.10978)、[verl-agent 仓库](https://github.com/langfengQ/verl-agent)。

## 4. AgentGym-RL：交互预算也是训练变量

模型最初不会做复杂任务时，一开始就给很长的轨迹，可能得到大量昂贵的失败样本；一直只允许很少的交互，又可能限制模型完成复杂任务。

AgentGym-RL 的 ScalingInter-RL 把允许的交互轮数纳入训练调度。仓库提供的阶段式配置示例是：

```text
训练早期：最多10轮
训练中期：最多20轮
训练后期：最多30轮
```

它改变的是探索和执行预算。底层仍需要策略优化算法更新参数。

这里容易有两个误解。第一，增加步数上限不等于模型已经学会更深的依赖。第二，按训练阶段增加轮数的调度，不等于根据每个任务的难度自动决策。

公平实验应比较固定短预算、固定长预算和阶段式预算，并报告环境交互量、生成 Token、训练时间。允许模型多执行几步和模型真的变强，需要分开测。

对应来源：[AgentGym-RL 仓库与调度配置](https://github.com/WooooDyy/AgentGym-RL)。

## 5. BEACON：最终失败，也能利用已完成的阶段

假设 CAD 任务完成了底板、打孔，却在倒角时失败。只看最终成功奖励，这条轨迹可能得到零分。但已完成部分仍包含可学习的行为。

BEACON 用里程碑划分轨迹：

```text
第1～4步：底板完成 ✓
第5～8步：打孔完成 ✓
第9～12步：倒角失败 ✗
```

在已完成阶段内，距离里程碑越近，分配的塑造奖励越大：

\[
r_t=R_{\mathrm{ms}}\gamma^{t_k-t}
\]

假设一个阶段有四步，里程碑奖励为 1，γ 为 0.9，四步分别获得 0.729、0.81、0.9、1。这是逐步计算的奖励，不是把固定的一分拆开分完。失败且未完成的阶段没有这份里程碑奖励。

随后组合两种优势：

\[
A_{i,t}=A_i^{\mathrm{traj}}+\lambda A_{i,t}^{\mathrm{seg}}
\]

轨迹级优势保留整体目标；分段优势在相应任务组和阶段内比较塑造奖励。组合后的优势进入 PPO 风格的裁剪策略目标，再通过反向传播更新模型。

正奖励不等于正优势。动作即使有里程碑奖励，低于比较组基线时仍可能得到负的分段优势。BEACON 也无法保证每个早期正确动作都免受惩罚，它提供的是更细的近似信用分配。

项目需要环境相关的里程碑信号或预先构建的匹配定义。迁移到 CAD 时，尺寸、孔径和拓扑检查可以成为候选判据；但判据必须可靠，否则模型会被错误奖励引导。

对应来源：[BEACON 仓库](https://github.com/ZJU-REAL/BEACON)。

## 6. RAGEN：训练为什么会学成重复套路

多轮训练的困难还包括：模型可能在训练过程中变得越来越固定，成功率先升后降。

RAGEN 初版的 StarPO-S 从训练数据和更新约束两方面干预。它按同一任务多次尝试的奖励波动筛选任务组，并研究移除 KL 项、采用非对称裁剪等调整。

```text
任务A：[0,0,0,0] → 全失败
任务B：[1,1,1,1] → 全成功
任务C：[0,1,0,1] → 有成有败
```

C 组往往有更直接的对比信号。筛选保留的是任务组，而不是仅保留成功轨迹。这与拒绝采样 SFT 不同。

RAGEN-2 则进一步研究了模板坍塌：输出仍然多样，却不再针对不同输入。

```text
需求A：旅行预算不足 → 推荐原来的路线，换个说法
需求B：老人不能久走 → 仍推荐原来的路线
需求C：交通时间有限 → 继续推荐原来的路线
```

仅看输出熵，可能发现不了这个问题。RAGEN-2 用模型对不同“输入—推理”组合的打分，检查一段推理是否更匹配它原来的输入，形成互信息代理指标。

它还通过梯度分析解释：奖励差异小的时候，任务信号变弱，采样噪声与正则项相对占优，可能推动模型失去输入依赖。对应干预是用奖励方差作为信号质量代理，筛选参与更新的任务组。

初版已有奖励波动筛选，因此 RAGEN-2 的贡献需要连同新诊断、机制解释和实验验证一起看。奖励方差也不等于真实信噪比：如果差异来自环境随机性，筛选可能误判；如果任务全失败，它更不能凭空制造成功信号。

对应来源：[RAGEN 论文](https://arxiv.org/abs/2504.20073)、[RAGEN-2 论文](https://arxiv.org/abs/2604.06268)、[项目仓库](https://github.com/mll-lab-nu/RAGEN)。

## 7. WebRL：把失败任务变成下一轮训练材料

网页业务里，不只有参数更新问题，还要考虑任务从哪里来、谁评价结果，以及学习新任务时如何保留旧能力。

WebRL 把这些事情串成阶段式训练流程：

```text
SFT建立基本能力
→ 当前模型执行网页任务
→ ORM评价执行结果
→ 更新Actor与Critic
→ 利用失败任务生成下一阶段任务
→ 筛选并回放历史成功经验
```

网页操作由 Harness 解析模型动作，再由 Playwright 驱动 Chromium 执行。模型学习根据页面反馈生成下一步操作，浏览器执行器本身不接受梯度更新。

这里有个重要更正：本地 WebRL 原版 Actor 损失不是标准 PPO clipped surrogate。它构造优势，并围绕当前策略与参考策略的对数概率差使用回归式损失及样本掩码。理解它时，应以实际实现为准，不能因为存在 Actor/Critic 就称为 PPO。

这种失败任务驱动的课程，对旅行系统也有启发：从预算冲突、交通不可行等失败案例生成相关训练需求。但生成出来的新需求仍要检查可行性，失败轨迹也要区分模型错误与服务故障。

对应来源：[WebRL 论文](https://arxiv.org/abs/2411.02337)、[WebRL 仓库](https://github.com/THUDM/WebRL)。

## 8. SkyRL-Agent 与 Agent Lightning：解决执行和训练的连接

假设一条 Simulink 轨迹正在等待仿真，GPU 不必只等它回来。系统可以推进其他轨迹的模型生成，等仿真结束后再恢复这条任务。

这里首先是并发执行。SkyRL-Agent 的工程价值在于把任务状态、工具、异步调度、模型后端和训练接口组织成可复用的执行系统。

但要区分两件事：在一个固定策略版本下并发采样，与采样和参数更新同时推进。后者还涉及策略陈旧度、权重同步和数据版本管理。不能把所有异步执行都等同于异步 RL。

Agent Lightning v1.0 则提供 Trainer、API Gateway 和 Rollout Controller，让已有 Agent 可以通过网关调用模型、采集交互，并提交任务奖励。

```text
已有旅行Agent
→ 通过Gateway请求模型
→ 原有工具查询交通、酒店
→ 验证器检查预算和时间约束
→ 上报奖励事件
→ 训练器组织轨迹，按算法更新
```

网关能采集经过它的模型请求；工具结果需要进入后续输入，才成为模型可见上下文。额外的工具日志仍需关联到本次执行。业务验证器也需要自己实现。

提交奖励不等于立即更新。合理的初始实现是固定模型版本、收集一批完整轨迹、检查奖励和环境异常，再进行有限次数更新，最后同步新权重。

对应来源：[SkyRL-Agent](https://github.com/NovaSky-AI/SkyRL/tree/main/skyrl-agent)、[Agent Lightning](https://github.com/microsoft/agent-lightning)。不同版本接口和支持能力应分别核对。

## 9. SWE-Gym：先建立可信的修复与验证闭环

SWE-Gym 提供真实 Python 仓库任务、可执行环境与测试验证，研究如何训练修复 Agent 和 Verifier。项目包含约 2,400 个任务，来自 11 个仓库。

它的原始训练路线不能直接概括成 GRPO。

| 路线 | 数据与训练方式 |
|---|---|
| OpenHands轨迹蒸馏 | 强模型采样，筛选成功轨迹，对开源模型做SFT |
| MoatlessTools自我改进 | 当前模型采样，测试保留成功尝试，再做SFT |
| Verifier训练 | 用带测试成败标签的轨迹做监督学习 |

前两条使用不同 Harness，不能默认直接混合数据。拒绝采样自我改进也不等于组相对策略优化。

Verifier 的 OpenHands 路线把任务和轨迹作为输入，将实际测试结果转换成目标回答：

```text
<judgement>YES</judgement>
或
<judgement>NO</judgement>
```

通过回答部分的交叉熵训练模型，推理时利用成功标签的概率信息给多个候选排序。本地主训练脚本使用 Qwen2.5-Coder-32B 与 LoRA；仓库也有其他训练配置。

这不是 DPO：存在成功和失败两类数据，不代表存在 chosen/rejected 偏好训练对。失败轨迹对应的正确回答是 NO，仍然可以用 SFT 学习。

Verifier 分数首先是预测和排序依据。模型偏向 YES，不代表方案已经通过测试；高置信度也不天然是校准后的成功概率。

这对 CAD、Simulink 的启发很直接：先用几何检查或仿真得到可信标签，再研究轨迹学习和候选选择。学习到的验证器不能替代最终工程验收。

对应来源：[SWE-Gym 论文](https://arxiv.org/abs/2412.21139)、[项目仓库](https://github.com/SWE-Gym/SWE-Gym)。

## 10. 我会怎样把这些方法落到业务实验

如果围绕 Simulink 做一个项目，我会先选择需求边界明确、可以自动验证的调参任务，而不是直接要求模型完成整个复杂系统设计。

首先固定初始模型、测试输入、求解器配置和参数范围。每次尝试从同一份工程副本开始，避免前一条轨迹污染后一条。

然后建立独立验证器：检查仿真是否完成、系统是否稳定、超调和调节时间是否满足要求。基础实验可以先用全部满足为 1，否则为 0。基础设施故障单独记录，不能混成普通任务失败。

如果模型缺少基本工具能力，先收集环境验证过的示范轨迹做 SFT，再比较 RL 方法。强模型生成的轨迹也必须验证，不能因为是教师输出就默认正确。

接下来逐项增加实验变量：

| 阶段 | 核心对照 | 想回答的问题 |
|---|---|---|
| 多轮RL基线 | SFT与GRPO | 环境交互训练是否提高完成率 |
| 信用分配 | GRPO与可适配的GiGPO | 更局部的比较是否有效 |
| 交互预算 | 固定预算与阶段调度 | 课程是否提高训练效率 |
| 部分成功 | 结果奖励与里程碑方法 | 中间信号是否减少浪费 |
| 稳定性 | 不筛选与奖励方差筛选 | 是否减少退化或低信号更新 |
| 系统效率 | 串行与并发采样 | 等待时间和GPU空闲是否减少 |

这些是候选实验，不意味着可以把各仓库模块直接拼接。每项都需要检查接口、分组条件和算法假设；尤其是 GiGPO 状态匹配、BEACON 里程碑，并不对所有业务天然适用。

评测还需要同时控制执行预算。模型在 50 步预算下比旧模型在 10 步预算下做得好，无法独立证明训练方法有效；同样步数也可能消耗不同 Token 和仿真时间。

我会报告任务成功率、逐题改善与退步、全零奖励组比例、错误恢复率、模型Token、工具调用数、仿真耗时和GPU时间。验证集用于选择配置，最终保留测试集用于效果报告，避免在同一批题上反复挑选最好的模型。

这些项目共同提供了一套可以逐层检验的研究路径：先保证任务能执行、结果能验证，再研究学习信号，最后优化采样与训练效率。第一份有说服力的成果，应当是一组可重放任务、一个可信验证器，以及在相同预算下测出的前后差异。
