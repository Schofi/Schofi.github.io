假设一个 Simulink Agent 在某次仿真中发现：降低积分增益 $K_i$ 后，执行器饱和时的超调减小。

它把这句话存进长期记忆。下一次遇到超调，又检索到同一条经验，于是继续降低 $K_i$。

检索可能完全正确，但这条经验适用于哪些模型、控制结构和工况，还需要检查。一次观察经过总结，很容易从“这个条件下发生了什么”，变成“以后遇到这个问题都应该怎么做”。

所以，在“何时写、写什么、写到哪里、如何召回”之前，我会先放一个问题：**谁有权把一次观察变成长期事实？**

召回差，Agent 可能漏掉一条经验。写入和冲突处理出了问题，它可能在之后的每次任务里重复同一个错误，即使检索每次都命中。

## 1. 一次观察怎样成为可以复用的记忆

先把几种信息放在一起看：

| 信息 | 可以支持什么 | 写入时需要保留什么 |
|---|---|---|
| 用户明确纠正的要求 | 当前用户或项目的约束 | 谁提出、适用项目、是否替代旧要求 |
| 工具返回与执行日志 | 当时执行中观察到的状态和结果 | 工具、时间、环境版本与原始记录 |
| 模型对失败原因的解释 | 一项待检查的原因假设 | 推理依据、尚未确认的条件 |
| 多个工况下的验证结果 | 一条具有已检查适用范围的经验 | 工况集合、验收指标、反例和证据 |

这些信息都值得保存，但保存之后承担的作用不同。用户明确更改了项目要求，可以更新对应约束。模型根据一次失败猜测原因，可以写成候选假设。仿真结果支持的是对应模型与工况下的表现。

我会让写入记录同时回答两个问题：这句话从哪里来，以及下一次行动可以在什么条件下依赖它。

因此，记忆系统需要给写入者分配权限，也需要定义更新规则。例如，任务 Agent 可以记录观察和提出候选经验，离线整理流程可以归并记录、提出冲突处理建议，验证器可以提供复跑结果。哪些状态允许自动提升、哪些变更需要人工确认，再由具体业务决定。

## 2. 写入、权威记录和检索，应该分别设计

讨论记忆选型时，可以先看三种常见组合：

| 组合 | 内容怎样保存 | 常见使用方式 |
|---|---|---|
| 独立记忆服务 | 由服务提供持久化、更新和查询接口 | 多个应用通过 API 或工具读写 |
| 文件式记忆 | Markdown 等文件保存内容，Git 记录版本 | 加载索引、按主题读取、搜索文件 |
| 内容与检索索引分离 | 文件或文档保存权威内容，辅助索引负责定位 | 关键词、向量或图检索返回相关记录 |

这张表适合当选型地图。要解释具体系统，还需要拆开三个维度。

**谁负责写入？** 可能是用户、应用代码、任务 Agent，也可能是任务结束后的整理流程。自动写入可以搭配 Markdown，应用显式调用也可以搭配独立记忆服务。

**哪里保存权威记录？** 系统需要明确，内容发生冲突或索引需要重建时，应回到哪份记录核对。选择 Markdown + Git 时，要让被接受的内容、来源和修改历史可以被检查。选择服务时，也需要理解它如何保存来源、版本与更新状态。

**运行时怎么找回来？** 可以常驻上下文、按主题读文件、做关键词检索，也可以使用向量索引或多种方法组合。Markdown 同样可以配向量索引。检索返回的内容还需要携带适用范围与当前状态，供执行阶段判断。

这三个维度可以自由组合。只按“向量库”和“Markdown”划线，很容易漏掉真正决定行为的写入与更新流程。

## 3. 四个项目，展示了不同的组合方式

下面按官方文档核对各项目的接口和记忆机制。

| 项目 | 写入与使用方式 | 内容组织与运行时读取 |
|---|---|---|
| **Mem0** | 提供独立的 `add` 和 `search`。直接 API 接入时由应用编排调用，也可以将接口交给 Agent 作为工具，让它判断保存和查询时机 | 查询结果由应用或 Agent 用于后续上下文。[官方 Quickstart](https://docs.mem0.ai/platform/quickstart) |
| **OpenViking** | `session.commit()` 先归档，再异步生成摘要与抽取记忆。后续处理受策略和 schema 约束 | 用 VikingFS 虚拟文件系统组织内容，完整内容与向量索引分层保存。索引包含检索所需的向量、URI、元数据及部分文本。[Session](https://docs.openviking.ai/en/concepts/08-session)、[架构](https://docs.openviking.ai/en/concepts/01-architecture) |
| **Letta** | V1 SDK 的核心 memory blocks 可以常驻上下文。当前文档还提供 Git 支撑的 MemFS，以及可配置的后台 Dreaming 整理流程 | 常驻块和文件式记忆对应不同接口与运行方式，应按所用 SDK 与运行时核对。MemFS 允许 Agent 更新记忆文件，Dreaming 用于整理经验。[V1 memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks)、[MemFS](https://docs.letta.com/concepts/memfs)、[Memory 与 Dreaming](https://docs.letta.com/configuration/memory) |
| **Claude Code** | `CLAUDE.md` 保存持久项目指令，Auto Memory 允许 Claude 积累自己的记忆 | Auto Memory 以 `MEMORY.md` 作为索引，另设主题文件。索引按启动加载规则进入上下文，主题文件按需读取。[官方 Memory 文档](https://code.claude.com/docs/en/memory) |

例如，OpenViking 同时具有自动提炼与内容、索引分层。Claude Code 展示了文件式记忆也可以由 Agent 写入。Mem0 的 API 则允许应用选择接入时机。

看到项目名之后，我会继续沿调用链看：谁发起保存，什么情况下改写已有内容，怎样处理冲突，查询结果以什么形式进入上下文。这些细节决定它与具体业务怎样配合。

## 4. 冲突处理要保留条件，也要允许撤回

假设已有经验写着“降低 $K_i$ 后超调减小”，新任务里却出现了响应变慢、稳态误差恢复变差的结果。

整理流程首先需要对照两次任务的模型版本、控制器结构、执行器限制、负载和验收指标。条件不同的记录可以分别成立，也可能揭示原来的经验描述过于宽泛。处理冲突时，应该保留这个判断过程和证据。

我会为可复用经验至少保留以下字段：

| 字段 | 在工程案例中的用途 |
|---|---|
| 结论与操作 | 观察到了什么，建议尝试什么 |
| 适用范围 | 模型版本、工况和前置条件 |
| 证据引用 | 对应的日志、仿真配置和结果 |
| 状态 | 候选、已验证、待复核或已撤回 |
| 更新关系 | 替代了哪条记录，变更依据是什么 |
| 复核条件 | 版本或环境怎样变化时需要重查 |

这里的“已验证”也带范围。它表示某组条件与指标已经被检查，后续任务仍然要判断这些条件是否匹配。

运行时检索应读取记录状态。旧内容被撤回之后，缓存和索引也要同步反映变化，让下一次查询能看到更新后的结论及其历史。

## 5. 个人 Coding Agent 可以从 Markdown + Git 起步

对于个人编码与项目协作，我会先采用容易检查的文件组织方式：用索引列主题，把用户约束、项目事实和候选经验分别写清，保留来源与版本记录。

后续增加能力时，按实际故障选择。

| 遇到的故障 | 优先检查的环节 |
|---|---|
| 反复忘记用户明确纠正过的事情 | 写入触发、旧记录更新、冲突优先级，以及运行时是否读到新状态 |
| 经验已经保存，换一种说法就找不到 | 用真实任务比较关键词与语义检索，检查相关记录能否进入上下文 |
| 多个客户端需要共用权限、撤回和过期状态 | 统一身份、权限与状态管理，评估独立服务 |
| 检索拖慢任务执行 | 检查查询是否进入主链路、调用次数、缓存方式和端到端 P95 |

文档字数和固定的“一两秒延迟”很难单独作为选型线。更有判断价值的是实际召回率、关键记录是否进入决策上下文，以及完整任务的成功率和执行成本。

比较检索方案时，可以准备一组真实问题，标出每题应命中的记录，再检查注入后是否帮助完成任务。查询阶段找到相关文档，与 Agent 最终正确使用它，是两个都需要观测的环节。

## 6. 用 Simulink 把双周期记忆落到具体决策上

回到文章开头的假设。一次仿真中，降低 $K_i$ 后，执行器饱和时的超调减小。

我会把在线积累、离线整理和后续使用连接起来。

**在线阶段先保存候选经验。** 记录调整前后的参数、模型版本、工况、验收指标和仿真结果，同时保留原始执行证据。Agent 可以快速积累信息，候选记录里的结论要与证据范围对应。

**离线阶段检查适用范围。** 整理流程汇总相似记录，在其他负载、输入和初始条件下复跑，检查超调、稳定时间、稳态误差等当前任务关心的指标。根据这些结果细化条件、标注反例、更新状态。复跑是这套设计中的验证步骤，需要由接入的仿真与验收流程执行。

**下次执行时使用经验提出尝试。** 遇到相似失败，Agent 检索到这条记录，核对当前模型和工况后，可以优先尝试对应办法。操作完成后，仍按本次任务的验收指标检查结果，并把新证据交回整理流程。

这套双周期设计，让在线阶段积累执行经历，让离线阶段有时间整理、复核与更新。经验随后能否继续被采用，取决于当前条件和新增证据。

对我而言，记忆架构最终需要回答的是一个具体问题：**下一次 Agent 依据这条经验行动时，能否找到它的来源、适用范围和最近一次被检查的依据？**
