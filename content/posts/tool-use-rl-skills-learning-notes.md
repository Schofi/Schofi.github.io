给旅行 Agent 一句话：

> 我想带母亲去杭州玩三天，预算3000元，轻松一点，帮我安排一下。

它需要先问清日期、人数、预算范围和体力限制，再查询天气、地点、路线等信息，最后输出能够执行的行程。模型会生成工具调用的 JSON，只是这条链的起点。

今天的学习一直围绕几个问题展开：工具到底是谁执行的？哪些 token 参与训练？奖励函数里的分数从哪里来？SUM 和 MACRO 究竟差在哪里？写出一份 skill，和通过 RL 训练模型，又是什么关系？

最容易产生误解的地方，是把一个完整系统中的不同环节统称为“Agent 学会了”。这篇笔记沿着一条旅行业务链，把执行、奖励、优化、评测和经验复用分别展开，再把它们接起来。

文中的杭州、苏州等场景和示例价格用于教学，不是实际出行建议、实时工具结果或论文实验数据。论文机制以文末原始来源为依据；源码细节来自本地保存的仓库快照，其中 `J:\ToolRL` 主资料包记录的下载日期为2026年10月24日。本文不报告新训练结果。

## 1. 先画清楚：一次任务和一次训练迭代

假设补充沟通后，任务明确为：

```text
日期：11月6日至8日
人数：两人
起点：第一天上午到杭州东站
预算：当地总费用3000元，含住宿、餐饮、交通、门票
限制：每天步行不超过3公里，不安排爬山
偏好：园林和文化场馆，避免赶场
```

一次任务的执行循环是：

```text
读取当前上下文
  → 模型生成回复或工具调用
  → 程序执行工具，或取得用户回复
  → 把结果放回上下文
  → 模型决定下一步
  → 最终提交行程
```

训练外层还有另一个循环：

```text
取一批任务
  → 当前模型为每个任务生成多条轨迹
  → 环境和评分器计算奖励
  → 训练器计算优势、损失
  → 反向传播，更新模型参数
  → 用更新后的模型继续采样
```

收到工具结果是在增加决策信息。执行优化器更新，才是在改变模型权重。正常的任务执行过程中，不会因为查到一次天气，就自动进行一次参数训练。

### 1.1 模型生成请求，程序执行请求

例如模型生成：

```json
{
  "name": "route_planning",
  "arguments": {
    "origin": "地点A",
    "destination": "地点B"
  }
}
```

这只是说明流程的接口示例，具体参数应以工具 Schema 为准。真正执行时，程序还需要解析字段、验证参数、调用函数、处理错误，再把观察返回给模型。

因此，一次 API 成功也只说明该操作执行成功。把订单改到错误日期，API同样可能返回成功；旅行规划仍然失败。

### 1.2 模型动作和环境内容怎样区分

| 内容 | 来源 | 通常作为策略动作计算损失吗 |
|---|---|---|
| 系统规则、工具 Schema | 程序 | 否 |
| 用户需求和补充回答 | 用户或用户模拟器 | 否 |
| 工具名、参数、模型回复 | 被训练的模型 | 是 |
| 天气、POI、路线结果 | 工具或环境 | 否 |
| 外加的纠错提示 | 环境或其他组件 | 通常否 |

典型的损失掩码可以示意为：

```text
用户输入       模型调用       工具返回       模型回复
00000000       11111111       00000000       11111111
```

`0`表示这部分内容不作为模型生成动作的目标计算策略损失，仍然可以被后续动作读取。它不是“从注意力中删除”，也不是保证相关内部表示完全没有梯度。

还要根据真实来源划分，不能只看聊天角色。在我的旅行训练入口里，一些工具观察被包装成 `user` 消息；它们仍然不是游客的自然语言回复。

## 2. 奖励、优势、损失分别是什么

这是理解后面所有项目的基础。

| 名称 | 回答的问题 | 例子 |
|---|---|---|
| 奖励 Reward | 任务或动作按规则得几分 | 行程全部通过，得1分 |
| 优势 Advantage | 相对基线，这次行为好多少 | 同题其他候选更差，这次获得正优势 |
| 损失 Loss | 怎样用这个信号计算参数更新 | 提高正优势动作的生成倾向 |

同一道题采样四次，奖励为：

```text
[1, 1, 0, 0]
```

GRPO风格的方法会在同题候选组内比较。常见的优势形式是：

$$
A_i=\frac{R_i-\mu_R}{\sigma_R+\epsilon}
$$

然后通过模型动作的概率构造训练目标。省略概率比、裁剪等细节，策略梯度的方向可以用下式理解：

$$
L_{\mathrm{PG}}=-\sum_k m_k A_k\log\pi_\theta(y_k\mid h_k)
$$

`m`是动作掩码，`h`是生成时已有的上下文。正优势推动模型更倾向生成相应动作，负优势推动其减少这些动作。完整PPO/GRPO实现还有新旧概率比、裁剪以及按配置启用的正则项。

需要记住三个区别：

- 原始奖励为0，组内优势仍可能为负或为正。
- 原始奖励为正，不保证组内优势也为正。
- 多个奖励项合成一个分数，不等于每个步骤都获得不同的信用。

策略梯度训练损失可以为负。某个批次的损失数值恰好为0，也不等于梯度一定为0。不能用普通“误差距离必须非负”的直觉解释所有RL目标。

## 3. ToolRL：先学会怎样评价一次工具调用

ToolRL研究有参考工具调用时，怎样提供比“全部正确或全部错误”更细的奖励。它比较格式、工具名、参数名和参数值。

假设教学工具的参考调用是：

```json
{
  "name": "weather_search",
  "parameters": {
    "city": "Hangzhou",
    "date": "2026-11-07"
  }
}
```

这里沿用ToolRL的 `parameters` 字段，不能直接当成我的旅行工具实际Schema。

### 3.1 格式分和内容分

默认基础设计：

$$
R=R_{\mathrm{format}}+R_{\mathrm{correct}}
$$

格式奖励检查相应的 `<think>`、`<tool_call>`、`<response>` 等标签结构，通常为0或1。正确性奖励比较调用内容，默认映射到 `[-3,3]`。

对一个工具、两个参数的例子，最高匹配分为：

```text
工具名匹配：1
参数名匹配：1
city值正确：1
date值正确：1
总计：4
```

如果只把城市写错：

```text
工具名：正确
参数名：完整
city：错误
date：正确
匹配分：3/4
```

则：

$$
R_{\mathrm{correct}}=6\times\frac{3}{4}-3=1.5
$$

格式合法时，总分为 `1+1.5=2.5`。

### 3.2 今天用本地函数核对的结果

关闭长度奖励和可选奖励变体，调用本地 `compute_score()`，得到：

| 输出变化 | 格式分 | 正确性分 | 总分 |
|---|---:|---:|---:|
| 全部正确 | 1 | 3 | 4 |
| 工具名改成 `poi_search` | 1 | -3 | -2 |
| 城市改成 `Suzhou` | 1 | 1.5 | 2.5 |
| 缺少 `date` | 1 | 0.75 | 1.75 |
| 多一个无用参数 | 1 | 2.5 | 3.5 |

参数名匹配使用类似交并比的计算；默认参数值比较使用Python的 `==`。多工具调用时，本地实现按同名、未使用的候选进行匹配，不能把论文的匹配表述直接扩写成代码已实现任意情况下的全局最优匹配算法。

这组例子也说明了边界：城市错了仍可能拿到部分正奖励。分数表达参考调用的匹配程度，不等于满足了真实旅行需求。

ToolRL训练数据中的多步经历会拆成带历史上下文的单步样本。参数级评分更细，也不等于参数token分别得到独立的优势。

源码入口：`verl/utils/reward_score/rlla.py`。来源：[ToolRL论文](https://arxiv.org/abs/2504.13958)、[官方仓库](https://github.com/qiancheng0/ToolRL)。

## 4. Agent-R1：环境如何给奖励，轨迹如何进入训练

Agent-R1提供多轮交互、上下文管理、轨迹记录和优化接入。当前本地v2设计采用步骤级表示：

```text
当前观察 → 模型动作 → 环境反馈
                         ↓
              奖励、下一观察、终止状态
```

接口形式是：

```python
next_obs, reward, done, info = await env.step(action)
```

这里的环境包含任务程序和评分规则。天气API返回“下雨”是观察，是否给奖励、给多少，需要另行定义。

### 4.1 两条奖励路径

```text
环境或工具直接提供reward
       → 保存为步骤reward_score

环境没有提供reward，reward_score为None
       → 调用配置的奖励函数补算
```

`None`表示尚未提供奖励，`0`已经是一个确定的数值奖励。本地 `_compute_score()` 仅在步骤奖励为 `None` 时调用奖励worker。

工具返回文字里出现“reward=1”，也不代表已经提交了训练奖励。GSM8K的一个工具会把检查结果写进观察，但结构化返回的奖励项是 `None`；后续评分函数与给模型看的反馈是两条不同通路。

### 4.2 任务不同，评分规则不同

| 本地recipe | 评分方式 |
|---|---|
| GSM8K | 提取答案，与标准值比较；当前函数正确为1，否则0 |
| HotpotQA | 规范化答案，与标准答案及别名做精确匹配 |
| WebShop | 普通有效步骤通常为0；结束且成功默认给10；无法形成合法命令等情况默认罚0.1 |

Agent-R1并非只有轨迹表示，也不是自带一套适合所有业务的统一奖励。它提供奖励接口与具体任务示例，业务目标仍由任务实现决定。

本地步骤级GAE会利用逐步奖励和critic估值计算优势，再分配到该步动作token。直接奖励为0的查询，也可能因后续回报获得学习信号。

### 4.3 为什么要保留每一步当时的输入

训练计算动作概率时，应当使用生成那一步时真正看到的上下文。不能在后面取得完整答案后，把未来信息放回过去动作的输入。

步骤记录保存 `prompt_ids`、`response_ids`、log-prob等信息，也减少了“先解码成文字再重新编码”带来的漂移。下一步上下文可以总结、筛选或重组，但训练仍要忠实使用当时的决策输入。

步骤级接口不自动消除部分可观测性；上下文压缩也可能丢失必要条件。它让这些设计显式、可研究，不保证任意摘要都保持充分状态。

源码入口：`agent_r1/env/envs/tool.py`、`agent_r1/agent_flow/agent_env_loop.py`、`recipes/*/reward_fn.py`。来源：[Agent-R1 v2](https://arxiv.org/abs/2511.14460v2)、[官方仓库](https://github.com/AgentR1/Agent-R1)。本地部分StepPO示例使用critic、GAE和单候选，不能按GRPO配置解释。

## 5. Agent-STAR：把完整旅行方案变成可检查的对象

Agent-STAR使用TravelPlanner作为主要场景，主线是：

```text
采样旅行元素与约束
 → 检查数据库中是否有可行解
 → 生成自然语言任务
 → 强教师生成轨迹，只保留成功示范
 → SFT
 → 学生模型自己多轮交互
 → 最终行程验收与RL更新
```

它不是简单地多写了一种GRPO公式，而是系统研究数据、奖励、模型规模、算法和环境稳定性的配合。

### 5.1 自然语言先变成JSON

例如Agent写：

> 第二天参观景点A和景点B，午餐去餐厅C，晚上继续住酒店A。

格式化模型将其提取为固定字段。以下只展示一天的教学结构：

```json
{
  "day": 2,
  "current_city": "杭州",
  "transportation": "-",
  "breakfast": "早餐店A, 杭州",
  "attraction": "景点A, 杭州;景点B, 杭州;",
  "lunch": "餐厅C, 杭州",
  "dinner": "餐厅D, 杭州",
  "accommodation": "酒店A, 杭州"
}
```

完整结果是按天组织的JSON数组。提取模型的职责是忠实整理，后续规则负责验收。提取错误会传递到评分，格式化模型不是一个无误差的组件。

当前本地实现调用DeepSeek做格式化。因此，信息查询工具可以主要基于本地CSV，整个评分链却不等于完全离线、没有外部模型依赖。

### 5.2 规则读取三份数据

```text
任务中保存的结构化要求
＋ 模型最终行程JSON
＋ 旅行数据库
      ↓
检查函数返回 True / False / None 和原因
```

常识检查集合涉及完整性、数据库存在性、餐厅与景点重复、住宿最低晚数、城市路线、交通一致性、当日城市安排等。本地集合包含八项。这里描述的是规则集合与检查目标，不表示已对评测器实现完成全面正确性审计。

用户硬约束包含五类：

| 字段 | 类型及含义 | 本地实现支持的例子 |
|---|---|---|
| `budget` | 总预算数值 | 1000 |
| `local_constraint.cuisine` | 菜系数组或null | `["Italian", "Chinese"]` |
| `local_constraint["room type"]` | 房型或null | `private room`、`shared room`、`entire room`、`not shared room` |
| `local_constraint["house rule"]` | 住宿使用需求或null | `pets`、`visitors`、`smoking`、`parties`、`children under 10` |
| `local_constraint.transportation` | 交通限制或null | `no flight`、`no self-driving` |

检查还使用 `days`、`people_number`、`org` 等辅助字段。`room type`和`house rule`的键名含空格，需要按实际Schema使用。

菜系检查关注整趟旅行是否覆盖指定菜系，不要求每顿都同时满足全部菜系；房型和住宿禁令检查遍历相应住宿；没有指定的偏好返回 `None`，不进入适用硬约束的分母。

### 5.3 预算是怎样算出来的

当前实现根据识别到的对象，读取数据库价格，并考虑人数、住宿最大入住人数等。主要包括交通、餐饮和住宿；不应扩写成对真实旅行全部费用的完整核算。

教学例子：

| 项目 | 计算结果 |
|---|---:|
| 两人交通 | 1300元 |
| 两晚住宿 | 1200元 |
| 两人餐饮 | 900元 |
| 合计 | 3400元 |

任务预算为3000元，预算检查就失败。模型自己在回答末尾写“合计2800元”，不能单靠这句话覆盖数据库核算结果。

“每天步行不超过3公里”“雨天不安排长时间户外活动”是我的业务迁移示例，并未自动包含在原有五类硬约束里。要加入，需要路线、天气等可靠证据及明确检查器。

## 6. SUM、MACRO、SUCCESS：分数究竟怎么产生

以一份超预算行程为例，假设八项常识全部通过，四项适用的硬约束通过三项：

```text
常识：8/8通过
硬约束：菜系、房型、交通通过，预算失败
住宿使用规则：用户未指定，不参与
```

程序计算五个指标：

| 指标 | 含义 | 本例 |
|---|---|---:|
| `commonsense_micro_score` | 常识通过项数除以8 | 1 |
| `commonsense_macro_score` | 常识是否全部通过 | 1 |
| `hard_micro_score` | 适用硬约束的通过比例 | 0.75 |
| `hard_macro_score` | 适用硬约束是否全部通过 | 0 |
| `success_pass` | 整体是否成功 | 0 |

完整性和数据库存在性等前置条件影响是否继续运行硬约束检查，不能把缺失和虚构信息仅当作少扣一点比例分。

### 6.1 三种奖励使用同一批检查结果

$$
R_{\mathrm{SUM}}=C_{\mathrm{micro}}+C_{\mathrm{macro}}+H_{\mathrm{micro}}+H_{\mathrm{macro}}+S
$$

$$
R_{\mathrm{MACRO}}=C_{\mathrm{macro}}+H_{\mathrm{macro}}+S
$$

$$
R_{\mathrm{SUCCESS}}=S
$$

| 方案情况 | SUM | MACRO | SUCCESS |
|---|---:|---:|---:|
| 常识全过，硬约束过2/4 | 2.5 | 1 | 0 |
| 常识全过，硬约束过3/4 | 2.75 | 1 | 0 |
| 两组全部通过 | 5 | 3 | 1 |

SUM能区分“错两项”和“错一项”；MACRO不再给用户要求这一组的部分完成比例分。它仍保留常识组全通过的分数，因此MACRO不是“整份方案没成功就一律0”。

如果常识只通过7/8、硬约束通过3/4，并且仍满足硬约束检查的前置条件，则：

```text
常识micro = 0.875，macro = 0
硬约束micro = 0.75，macro = 0
Success = 0

SUM = 1.625
MACRO = 0
SUCCESS = 0
```

这些都是对布尔检查结果的统计，不是评审模型凭感觉生成的0.875或0.75。今天用模拟的检查结果调用本地评分函数，核对了相应的聚合计算；没有因此验证一份真实杭州行程。

### 6.2 为什么早期可能需要部分得分

假设同组候选都失败，但满足约束的比例不同。SUM可能产生：

```text
[2.50, 2.75, 2.25]
```

训练器还有比较依据。MACRO若得到 `[1,1,1]`，仅凭这组任务奖励就没有相对区分度。SUCCESS得到 `[0,0,0]` 时同样如此。

反过来，始终允许部分完成得分，也可能让训练重点长期停留在较容易满足的指标上。课程设计希望早期提供可区分信号，后期强调完整成功；这是一种需要实验验证的训练选择，不是普遍必胜配方。

### 6.3 “密集”不等于每次工具调用都打分

当前 `TravelToolEnvironment.step()` 在普通工具交互时通常返回0，终止并提交行程时调用最终评分函数：

```text
查询交通：0
查询住宿：0
查询餐厅：0
提交最终行程：2.75
```

SUM所谓更密集，主要指未完全成功的最终方案也有区分度，不意味着已经得到“第3次搜索贡献0.2”的逐步归因。

## 7. 课程奖励怎样在代码里自动切换

本地1.5B课程脚本设置：

```bash
export REWARD_TYPE="PLANNER_R1"
export TOTAL_STEPS=154
```

Python入口将 `PLANNER_R1` 映射到 `planner_r1_reward_fn`。整个运行期间可以一直使用这个函数，不需要人工重启三次训练。

```text
Trainer维护global_steps
 → 创建环境时传入current_training_step
 → 环境保存这个计数
 → 最终行程提交后，将计数传给奖励函数
 → 奖励函数按进度选择求和方式
 → 奖励进入GRPO更新
 → 正常训练迭代结束，global_steps加一
```

核心判断等价于：

```python
progress = current_step / total_steps

if progress <= 0.33:
    reward = cs_micro + cs_macro + hard_micro + hard_macro + success
elif progress <= 0.67:
    reward = cs_macro + hard_macro + success
else:
    reward = success
```

以154作为课程分母，从第1步开始：

| 当前训练迭代 | 奖励分支 |
|---|---|
| 1–50 | SUM |
| 51–103 | MACRO |
| 104起 | SUCCESS |

这不是一条轨迹内部的工具轮数，也不是成功率达到阈值后自动晋级，而是按训练计数固定切换。一个global step中可以包含多个小批优化操作，不能简单等同于一次底层优化器调用。

`TOTAL_STEPS`在这里是课程分母，训练终止还受Trainer的epoch、数据批次数或总步数配置控制。修改训练长度时，两者需要同步核对。

成功方案的分数也会从5变成3，再变成1。这是尺子变化，不是能力退步。跨阶段应该观察固定定义的成功率，不能只比较原始奖励曲线。

源码入口：`examples/travel/train_travel_agent_format.py`、`rllm/trainer/verl/agent_ppo_trainer.py`、`rllm/environments/tools/travel_tool_env.py`、`rllm/rewards/travel_reward.py`。来源：[Agent-STAR论文](https://arxiv.org/abs/2603.21972)、[官方仓库](https://github.com/WxxShirley/Agent-STAR)。

## 8. 我的旅行项目与Agent-STAR：主线相近，验收依据不同

两者都采用教师轨迹、SFT、多轮工具交互、奖励与RL更新。值得对照的不是“是否又使用一次GRPO”，而是环境与评分定义。

| 方面 | 我的旅行项目当前读取到的入口 | Agent-STAR |
|---|---|---|
| 工具 | 搜索、网页访问、地图、天气、路线、票务查询等接口 | 主要查询TravelPlanner本地数据库 |
| 最终方案评价 | 参考答案与LLM judge，评价匹配度、可行性、细节、清晰度 | 格式化JSON后运行约束检查 |
| 辅助分数 | 过程、工具格式、答案标签、阶段、工具效率 | 常识与硬约束的micro、macro及Success |
| 课程 | 调整六项分数的权重 | SUM → MACRO → SUCCESS |
| 结果解释 | 开放旅行答案质量的代理评价 | 特定沙盒和规则集合下的约束满足情况 |

我的 `travel_verl` 默认六项权重为：

| 分项 | 阶段1 | 阶段2 | 阶段3 |
|---|---:|---:|---:|
| 过程 | 0.10 | 0.05 | 0.05 |
| 工具格式 | 0.10 | 0.05 | 0.05 |
| 答案标签 | 0.05 | 0.05 | 0.05 |
| 阶段 | 0.05 | 0.05 | 0.05 |
| 工具效率 | 0.10 | 0.10 | 0.05 |
| 最终答案judge | 0.60 | 0.70 | 0.75 |

默认阶段占比约为15%、20%、65%，可被环境变量覆盖。数学上，两边都可以写成分项加权；实质区别是分项测量什么，以及最后是否只接受完整成功。

开放接口还带来实时性、空结果、限流和失败等因素，不能直接拿沙盒实验数字比较。要借鉴Agent-STAR，首先应定义自己的结构化验收条件和证据来源，而不是先复制权重。

## 9. 多轮工具调用的五篇论文，分别改了哪里

本地《入门6》选取五个代表工作。它们属于不同环节，可以用同一旅行业务说明，但不能都叫信用分配算法。

| 工作 | 核心问题 | 迁移到旅行任务的理解 |
|---|---|---|
| [MUA-RL](https://arxiv.org/abs/2508.18669) | 动态用户如何进入训练循环 | 游客分轮表达日期、预算和偏好，Agent学习追问 |
| [CodeGym](https://arxiv.org/abs/2509.17325) | 如何规模化构建可交互、可验证的环境 | 构造可重复查询与验收的旅行练习世界 |
| [TARL](https://arxiv.org/abs/2509.14480) | 如何利用逐轮评审 | 评审各轮行为，再按设计聚合奖励 |
| [MT-GRPO + IRC](https://arxiv.org/abs/2604.02869) | 密集奖励怎样校准并进入优势 | 检查奖励的区分力和更新方向 |
| [Fission-GRPO](https://arxiv.org/abs/2601.15625) | 工具执行错误怎样变成纠错练习 | 保留失败前缀，加入诊断，重新采样恢复轨迹 |

### 9.1 把它们接成一条教学设计

```text
准备旅行任务、工具世界和验收器
 → 模拟游客与Agent来回沟通
 → Agent查询并规划
 → 过程评审与最终验收
 → 校准奖励、计算优势
 → 从错误现场增加恢复采样
 → 更新模型
```

这是借鉴不同论文的组合设计，不是五篇原样叠加后已经验证的系统。

TARL的主要方案将逐轮评审聚合为轨迹奖励；若改成MT-GRPO逐轮更新，应明确这是新的组合，避免同一证据重复奖励。

IRC原实验中，read-only奖励从0.3降到0，非标准状态修改从0.1改为负值。不能将教程表格中的初始奖励当作校准后的最终结论，更不能推广成“所有业务都应惩罚状态修改”。

Fission-GRPO的恢复轨迹是在新的纠正上下文下采样，应保留自己的比较组。普通错误提示或一次重试，不等于已经实现它的训练机制。二元奖励下全失败组会退化，但有部分奖励时，失败轨迹之间仍可能存在差异；真正关键的是组内奖励是否相同。

### 9.2 最终失败怎样定位

| 类型 | 例子 | 需要的证据 |
|---|---|---|
| 信息没问清 | 用户没给日期，Agent直接猜 | 生成前上下文、用户约束 |
| 工具选错 | 应查询订单却执行取消 | 工具定义、业务目标与政策 |
| 参数错误 | 订单ID写错，或日期语义不符 | 原始调用、解析参数、已知信息 |
| 后续决策错误 | 已查到超预算，仍选择该方案 | 工具返回及后续动作 |
| 环境或任务因素 | API故障、根本没有可行选项 | 错误码、环境快照、可行性信息 |

这些类别可以形成因果链：没问日期，导致猜错日期，最后参数合法但业务错误。错误类型诊断、奖励定义和优势估计是不同工作；一次终局0分不会自动产生准确的局部责任标签。

## 10. 信用分配的阅读路线：看比较条件，而不只记算法名

本地《入门2》以GiGPO、HGPO、SPA-RL、AgentPRM、ARPO、IGPO组织三类信号来源。它适合入门，但覆盖范围不等于截至2026年10月的完整进展。

| 路线 | 代表阅读 | 需要追问 |
|---|---|---|
| 比较对象是否公平 | [GiGPO](https://arxiv.org/abs/2505.10978) → [HGPO](https://arxiv.org/abs/2602.22817) → [CCPO](https://arxiv.org/abs/2610.19103) | 同观察下的历史、任务进度是否一致 |
| 当前动作是否被后续连累 | [GraphGPO](https://arxiv.org/abs/2605.26684)、[ConCal](https://arxiv.org/abs/2610.37195) | 能否复用图结构或后续证据校准价值 |
| 过程信号从哪里来 | [SPA-RL](https://arxiv.org/abs/2505.20732)、[IGPO](https://arxiv.org/abs/2510.14967)、[TRACE](https://arxiv.org/abs/2607.13988)、[ProCredit](https://arxiv.org/abs/2609.27532) | 是模型预测、答案概率，还是环境验收 |
| 信用粒度怎样选择 | [GACA](https://arxiv.org/abs/2609.12424)、[SHARPO](https://arxiv.org/abs/2610.00838)、[CAPO](https://arxiv.org/abs/2604.18401) | 改奖励、改优势、改权重或改更新比率 |
| 决策角色是否要分开 | [HiPER](https://arxiv.org/abs/2602.16165)、[Memory-R2](https://arxiv.org/abs/2605.21768)、[RIPPLE](https://arxiv.org/abs/2610.31276) | 计划、执行、记忆、恢复是否存在不同归因条件 |

箭头表示问题联系和阅读顺序，不表示后一篇全面取代前一篇。论文提交更晚，也不自动说明效果更强。

“把最终奖励拆回每一步”只能作为入门比喻。一般没有“所有步骤优势之和必须等于最终奖励”的恒等式。优势是相对基线的比较量，很多方法仍受后续采样、隐藏状态和匹配误差影响。

还需要消除同名歧义：本地信用分配教程介绍的是2025年2月的[AgentPRM框架](https://arxiv.org/abs/2502.10325)；另有2025年11月的[同名AgentPRM工作](https://arxiv.org/abs/2511.08325)，机制与训练目标需要分别核对。

## 11. verl与VerlTool：训练底座和工具交互扩展

| 项目 | 主要学习问题 |
|---|---|
| verl | 如何组织生成、奖励、优势、反向传播、分布式训练与权重同步 |
| VerlTool | 如何组织工具服务、轨迹状态、调用协议和多轮工具rollout |
| Agent-R1 | 如何以步骤为单位保存交互，并显式管理上下文和优化接入 |

当前verl已经有Agent Loop和ToolAgentLoop，不能按“verl不支持工具调用，VerlTool才支持”的旧印象理解。来源：[verl Agent Loop文档](https://verl.readthedocs.io/en/latest/advance/agent_loop.html)。

VerlTool基于verl，重点提供统一Tool Server、工具扩展接口、按 `trajectory_id` 管理的环境状态和工具训练配方。来源：[VerlTool仓库](https://github.com/TIGER-AI-Lab/verl-tool)。

```text
模型生成工具动作
 → 分派到工具服务
 → 加载当前轨迹的环境状态
 → 执行并保存状态
 → 返回观察和终止信息
 → 接回模型
```

天气查询的状态通常较简单；代码执行、浏览器、购物车和可写数据库，需要更谨慎的轨迹隔离。

我的旅行项目已经有 `loop.py`、`tools.py`、`reward.py` 等模块，承担部分相似职责。学习扩展框架的价值是比较接口、调度和状态设计，不是为“能调工具”重复迁移。

轨迹异步推进与生成、反向传播并行的全异步训练也应区分。支持前者，不自动证明已经采用后者。

## 12. τ-bench：业务题怎样出，成功怎样判，稳定性怎样测

τ-bench主要是评测环境。它在2024年将动态用户交互、领域政策、有状态API和可验证终态组织成业务考题；没有因此提出新的训练优化器。

### 12.1 一道本地实际存在的取消订单题

本地开发集的一位模拟用户买了订单 `#W5442520`，后来发现送达时自己正在旅行，无法收货。她希望取消并全额退款，回来以后再买，现在不要重新下单。

初始数据库中，该订单是 `pending`，已支付663.85，使用信用卡。参考操作是：

```json
{
  "name": "cancel_pending_order",
  "kwargs": {
    "order_id": "#W5442520",
    "reason": "no longer needed"
  }
}
```

模拟用户获得私有身份与诉求，被测Agent只获得工具、政策和逐轮说出的信息；参考操作留给评测器。用户说明需确定目标结果，避免同一考题因未指定关键偏好而出现多个不一致的标准终态。

原始构建流程包含人工设计Schema、API与政策，辅助生成数据，以及人工编写、试跑和校正任务。不是让LLM随意写一堆问题就完成基准构造。

### 12.2 从参考操作得到目标状态

```text
初始数据库
  ├─ Agent操作 → 实际最终状态
  └─ 参考操作  → 标准最终状态
                     ↓
                比较是否一致
```

取消函数修改状态、取消原因并追加退款记录。Agent可以采用不同合法查询路径，但应得到正确结果；额外修改其他数据也可能造成全局状态不一致。

部分任务还要求回复包含必要信息。原始奖励可以理解为：

$$
r=r_{\mathrm{action}}r_{\mathrm{output}}\in\{0,1\}
$$

这道本地取消题的 `outputs=[]`，没有额外指定输出字符串。其他题的输出检查也不等于对整段对话语义和政策遵守的全面证明。

例如没获得确认就执行取消，最终状态仍可能正确。原论文承认终局规则奖励可能漏掉这类过程违规。需要对话审计才能补足这些证据。

### 12.3 pass^k看持续成功，pass@k看至少成功一次

固定模型、任务、政策和初始数据库，重置后重复测试。变化可以来自用户和Agent的采样表达，不应每次改变业务目标。

若某题四次结果为 `[1,1,1,0]`，本地组合估计为：

| 指标 | 估计值 |
|---|---:|
| pass^1 | 0.75 |
| pass^2 | 0.50 |
| pass^3 | 0.25 |
| pass^4 | 0 |

例如选两次共有六种组合，其中三种全成功，因此pass^2为3/6。一般估计式为：

$$
\widehat{\mathrm{pass}^{k}}=\frac{\binom{c}{k}}{\binom{n}{k}}
$$

其中 `n` 是重复次数，`c` 是成功次数，最后对任务取平均。它不是仅数顺序上连续成功的最长长度，也不能随意把聚合成功率的k次方当成所有任务平均的pass^k。

来源：[τ-bench论文](https://arxiv.org/abs/2406.12045)、[原始仓库](https://github.com/sierra-research/tau-bench)。官方已将后续任务修订与新领域放入[后续基准仓库](https://github.com/sierra-research/tau2-bench)。本文讨论的是本地原始τ-bench实现。

## 13. Skill是什么：可复用方法、外部记忆与内部能力

我的旅行工具可以查询路线，但“低步行量旅行规划”这个skill还需要组织方法：

```text
适用：用户限制步行或要求轻松游览。
步骤：明确上限 → 分区域 → 查询路段 → 累计全天距离 → 超限调整。
检查：每段都短，不等于全天总距离不超限。
```

| 对象 | 例子 |
|---|---|
| 工具 | 查询A到B的路线 |
| 事实记忆 | 这次工具返回A到B步行4公里 |
| 程序性skill | 怎样组织查询、累计距离、发现并修复超限 |
| 模型内部能力 | 无需逐次展示完整攻略，也更容易执行有效方法 |

外部skill可以被检索、编辑和删除；写入文件不会自动更新模型权重。内部能力需要相应训练才能改变。没有外部库也不意味着模型每次从零开始，它仍能使用权重中已有的能力和当前上下文。

本地《入门5》的“同一个任务做两次”是帮助理解的标题，不是这几篇论文统一采用的协议。

| 工作 | skill主要放在哪里 |
|---|---|
| Skill-RM | 评审与奖励计算流程 |
| StraTA | 开始执行前生成的整体策略 |
| Maestro | 专家与技能注册表 |
| Evolving-RL | 从经历提炼、通过下游使用验证的经验 |
| SDAR | 训练时带技能指导的教师分支 |

## 14. Skill-RM：让裁判按技能组织证据

Skill-RM把评审说明、资源索引、rubric、参考材料、检查清单和验证脚本组织成可加载的Reward-Evaluation Skill。现有LLM裁判读取流程，按需取得证据，输出结构化判断，再按约定读出分数或候选选择结果。

```text
用户要求＋候选答案
 → 裁判加载评审skill
 → 选择有关规则、参考和验证资源
 → 记录逐项证据
 → 输出判断
 → 读出reward或最佳候选
```

旅行迁移可以使用费用核算、路线验证、证据覆盖检查等资源，但这是业务扩展示例，不是原论文已经验证了旅行能力。

它不必先训练一个新模型，再把模型“变成skill”。当前论文的技能主要由人工结合LLM辅助整理，在评测前固定。接入下游RL时，被更新的是作答模型；裁判加载技能执行评审，本身不等于进行参数训练。

不能将它统一概括为固定三个子裁判加权。来源：[Skill-RM论文](https://arxiv.org/abs/2606.03980)。

## 15. StraTA：策略和执行分别采样、分别比较

StraTA先生成紧凑的自然语言策略，随后每一步动作都以该策略和当前状态为条件。策略在一条episode中保持固定。

```text
旅行题
 ├─ 策略A：先选景点，再补交通 → 执行多次
 ├─ 策略B：先按区域和约束组织 → 执行多次
 └─ 策略C：先定住宿，再安排活动 → 执行多次
```

它通过分层GRPO式分组，同时学习怎样生成策略和怎样执行。v2的策略奖励使用该策略下较好一部分执行结果的平均值，减少早期执行噪声影响，并非教程中简单的全部平均。

它还通过语义最远点采样增加策略差异；执行后由Agent自评，对既不符合策略又不推进任务的步骤施加辅助惩罚。自评并非总是可靠，也不能保证策略和执行的因果贡献被完全分离。

创新重点不是“先写计划”本身，而是让策略文字成为独立采样和RL优化的对象，并设计多次执行与分层比较。只加一句“请先计划”，并没有实现这套训练机制。

来源：[StraTA v2](https://arxiv.org/abs/2605.06642v2)。

## 16. Maestro：训练调度者选择专家与技能

Maestro的4B编排模型学习是否委托、选哪个专家、使用什么技能、提出什么子问题及何时回答。专家保持冻结，默认技能注册表也不是训练时自由生成的工具集合。

调用可表示为：

```text
动作 = 专家模型 ＋ skill ＋ 子问题

<search>模型ID@@技能ID: 子问题</search>
```

技能采用两层：编排器选较粗的Level-1技能与专家，Level-2子程序通过规则或专家分类激活。不能把原论文全部简化成“任意原子技能和组合技能都由4B模型直接枚举”。

例如图表任务中，编排器可以调用图表专家提取数字，读回结果后自行计算，必要时继续委托。训练更新编排器的动作与推理，专家返回作为观察。

原论文还包含答案正确性奖励和协议格式惩罚，不能说只有一个纯0/1奖励。4B是编排器规模，不是整个多模型系统的总计算规模。

来源：[Maestro论文](https://arxiv.org/abs/2605.22177)。

## 17. Evolving-RL：同一个模型练习总结，也练习执行

这是今天反复追问最多的一部分。

Extractor读取已完成的源任务经历，生成可复用skill；Solver读取任务与skill，产生执行轨迹。两者共享参数，用不同提示词扮演不同角色。

完整流程：

```text
当前模型不带注入skill，完成一次源任务
 → 从该轨迹和环境结果生成多份候选skill
 → 检索相同的一组相关任务，包含源任务
 → 对每个“skill×任务”组合实际执行
 → 用结果训练skill提炼能力
 → 复用执行轨迹训练skill利用能力
 → 合并损失，更新同一个模型
```

相关任务基于源任务描述检索，不能让每个候选skill自己检索一组不同难度的任务再比较。这里主要是检索任务来评价skill，不是简单检索若干skill再重做一次。

### 17.1 一张矩阵，形成两种相对优势

教学环境成功得1、失败得0。原论文ALFWorld配置的任务奖励是成功10、失败0；此处为方便演算改用0/1。

| skill | 杭州任务 | 苏州任务 | 南京任务 | 平均回报 |
|---|---:|---:|---:|---:|
| A | 0 | 1 | 0 | 0.33 |
| B | 1 | 0 | 1 | 0.67 |

**Extractor先看每一行的平均值，再在候选skill之间比较。**

```text
两份skill平均成绩约0.50
A：0.33－0.50 ≈ －0.17
B：0.67－0.50 ≈ ＋0.17
```

论文再除组内标准差，得到生成skill文本的相对优势。

**Solver在每一列内部比较执行轨迹。**

```text
杭州：A执行失败，B执行成功 → B这次执行更好
苏州：A执行成功，B执行失败 → A这次执行更好
南京：A执行失败，B执行成功 → B这次执行更好
```

因此，B的总结优势可以为正，但“带B执行苏州题”的优势仍为负。不是Extractor和Solver互相比较，也不是把两种角色全部混成同一个GRPO组。

$$
R_i^{e}=\frac{1}{K}\sum_{j=1}^{K}r_{ij}
$$

$$
A_i^{e}=\frac{R_i^{e}-\operatorname{mean}_{i'}R_{i'}^{e}}{\operatorname{std}_{i'}R_{i'}^{e}+\epsilon}
$$

$$
A_{ij}^{s}=\frac{r_{ij}-\operatorname{mean}_{i'}r_{i'j}}{\operatorname{std}_{i'}r_{i'j}+\epsilon}
$$

技能主要评分依据是下游平均回报，不是教程所写的简单“带skill奖励减去裸跑奖励”。高平均回报也不单独证明严格的因果提升；它是候选经验的比较信号。

### 17.2 总结损失到底在训练什么

模型自己采样了一段skill，不需要一份人工标准skill逐字对照。环境使用效果决定这段生成行为应被强化还是抑制。

方向示意是：

$$
L_{\mathrm{ext}}\approx-A^{e}\log\pi_\theta(e\mid\text{原经历})
$$

正优势鼓励提高生成该经验的概率，负优势鼓励降低概率。实际算法使用包含新旧概率比、裁剪、KL等项的目标，不只是这条简式。

举一个只有两个简写技能动作的概率例子。按总体标准差演示，设优势为 `[-1,+1]`，旧概率都为0.5，新概率变为 `[0.45,0.55]`，新旧比率为 `[0.9,1.1]`。省略辅助项且位于裁剪区间内：

$$
L=-\frac{1}{2}\left(0.9\times(-1)+1.1\times1\right)=-0.1
$$

它体现了更新方向：降低较差skill概率，提高较好skill概率。真实长文本按生成token计算相应概率与训练目标，不能把这个两动作数值当作模型实际输出概率。

### 17.3 两份损失怎样更新同一模型

$$
L=\lambda_eL_{\mathrm{ext}}+\lambda_sL_{\mathrm{sol}}
$$

```python
# 教学伪代码：省略并行调度、裁剪和正则等实现
source_trace = solver(source_task)
skills = extractor(source_task, source_trace)
tasks = retrieve_related_tasks(source_task)

for i, skill in enumerate(skills):
    for j, task in enumerate(tasks):
        trajectories[i][j] = solver(task, skill)
        rewards[i][j] = evaluate(trajectories[i][j])

extractor_rewards = mean_over_tasks(rewards)
loss_ext = extractor_grpo_loss(skills, extractor_rewards)
loss_sol = solver_grpo_loss(trajectories, rewards, group_by="same_task")

loss = lambda_ext * loss_ext + lambda_sol * loss_sol
optimizer.zero_grad()
loss.backward()
optimizer.step()
```

损失函数内部需要重新前向计算带梯度的log-prob。skill文字是离散生成结果，不是一条可以让Solver梯度直接穿回Extractor的可微通道。下游回报作为生成skill的RL监督，才把两个阶段连接起来。

论文还处理经验评价噪声导致的训练不稳定，并非共享权重后就天然相互促进。实验主要在ALFWorld、Mind2Web上进行；旅行案例只是机制迁移说明。

来源：[Evolving-RL论文](https://arxiv.org/abs/2605.10663)、[官方仓库](https://github.com/Fanzy27/Evolving-RL)。

## 18. SFT也能做，为什么还要RL

我的一个疑问是：较大的模型已经会总结和按经验执行，SFT也可以训练，为什么必须用Evolving-RL？

这个问题应该保留。总结与执行不是RL独占能力。可以构造一条SFT路线：

```text
强教师生成经验和执行轨迹
 → 在相关任务中验证
 → 保留有效经验和成功轨迹
 → SFT
 → 再采样、验证、筛选、继续SFT
```

有实际反馈和迭代闭环，也不自动意味着必须使用RL。不同方法怎样消费这些数据、优化什么目标，需要实验比较。

Evolving-RL的主实验与消融比较了提示式经验方法、GRPO、SkillRL及只训Extractor、只训Solver等方案，没有直接给出同基座、同预算的优质教师SFT或迭代SFT对照。可以据此说明方法相对已测基线的效果，不能据此声称SFT做不到。

对我的项目，更值得保留以下实验：

| 方案 | 目的 |
|---|---|
| 提示词基线 | 测模型已有的总结与利用能力 |
| 教师SFT | 测优质示范是否已经足够 |
| 迭代筛选SFT | 测实际验证与数据改进的收益 |
| Evolving-RL | 测回报驱动联合优化的额外收益 |

固定基座、测试集、测试期经验获取权限与推理预算，还要计算教师调用、环境交互和训练成本。

目录中的[SFT or RL受控研究](https://arxiv.org/abs/2609.17848)在其工具调用设置中发现SFT经常很强，但它也不能替代对长程旅行任务的专门验证。

## 19. SDAR：训练时使用技能指导，推理时尝试内化能力

SDAR结合RL与带技能条件的教师分支，用门控辅助自蒸馏处理token级指导，强化正向信号、减轻不可靠负向指导。这里的技能指导服务于训练，不等于持续在外部库中新建经验。

需要区分三件事：

```text
把skill存到库里 → 改变外部可用上下文
训练模型选择skill → 改变调用或路由能力
利用skill指导蒸馏 → 试图将有效行为内化到权重
```

它们可以组合，但不是同一个更新动作。也不能从双前向示意图直接推断“每道任务完整执行两遍”，或认为所有带攻略的token都应盲目学习。

来源：[SDAR论文](https://arxiv.org/abs/2605.15155)、[官方代码](https://github.com/ZJU-REAL/SDAR)。

## 20. 把这些方法接到同一个旅行业务问题

以下是教学架构，不是已经完成的联合实验：

```text
构造有解、可重复的旅行环境与验收规则
       ↓
用户模拟器逐轮表达需求
       ↓
Agent形成策略，调用工具或委托专家
       ↓
保存动作、观察、环境状态和原始token
       ↓
最终计划验收＋需要时的过程评审
       ↓
校准奖励，选择轨迹级或步骤级优势
       ↓
必要时增加失败恢复采样
       ↓
提炼候选经验，在相关任务上验证
       ↓
更新执行、总结或编排模型中明确选定的参数
       ↓
用独立任务和重复试验评测能力与成本
```

实际实现需要先选定主要问题。若只想验证预算与路线，先完成可检查的任务成功条件；若要研究经验复用，再加入技能提炼。不能把模块堆叠后的改善自动归因于某一个算法。

## 21. 今天值得保留的问答

**环境已经返回reward，是不是就是环境奖励？**

是。它来自环境执行的任务评分逻辑，业务API的返回文本不会自动变成奖励。

**工具返回不算损失，是不是模型不看工具结果？**

仍然读取。它作为条件影响后续动作，只是不作为该Agent自己采样的动作目标。

**SUM和MACRO怎样区分？**

SUM保留完成比例；MACRO撤掉比例项，保留整组通过与整体成功。MACRO并不一律将未完全成功的方案判成0。

**课程奖励会自动判断模型已经学会了吗？**

本文核对的Agent-STAR代码按训练进度固定切换，没有自动掌握度判断。

**Skill-RM是不是先训练一个模型，再写成skill？**

核心是把评审流程与资源组织成skill，让已有LLM裁判执行；下游RL再使用奖励更新作答模型。

**StraTA是不是方法论？**

它是具体的模型训练方案。自然语言策略和执行动作都参与相应RL目标，而不只是提示模型先写计划。

**Maestro会训练专家和自动创造所有技能吗？**

主要训练编排器，专家冻结，依赖已准备好的技能注册表。真实模型池和技能层级要看原论文，不应只看“导演”比喻。

**Evolving-RL的总结奖励是谁给的？**

候选skill在相同下游任务上的环境回报，经跨任务汇总产生，不是只评价总结文风。

**Extractor和Solver的相对优势怎么比？**

Extractor比较各skill的平均下游成绩；Solver在同一任务内部比较不同skill对应的执行。共享参数不等于混用比较组。

**没有标准skill，总结损失怎么计算？**

以模型自己采样的skill为生成行为，用实际使用效果得到的优势构造策略损失，强化有用经验、抑制较差经验。

**RL是唯一能让模型总结、执行的方法吗？**

不是。需要与强提示、教师SFT、迭代SFT等方案，在相近资源与评测条件下比较。

**τ-bench奖励为1，业务就一定完全正确吗？**

它说明通过了相应状态与输出检查；未覆盖的过程政策仍可能被违反，需要额外证据审计。
