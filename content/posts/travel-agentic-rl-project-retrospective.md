## 1 项目的核心价值是生成能够执行的行程 {#chapter-01}

### 讲解经验

旅行规划的目标是同时满足用户提出的多种约束，输出切实可行的行程。

一份攻略即使读起来完整，如果景点之间距离太远、游览时间不够、遇到闭馆或恶劣天气，或者费用明显超出预算，也没有很好地完成任务。

以上海到黄山的旅行需求为例，系统需要综合处理以下问题。

| 约束 | 需要考虑的信息 | 忽略后的问题 |
| --- | --- | --- |
| 沿途餐饮 | 是否靠近路线、当季特色、评分、人均消费 | 为吃饭绕远，挤占游览时间并增加费用 |
| 景点选择 | 至少 6 处景点，其中 3 处适合拍照打卡 | 景点数量或偏好没有得到满足 |
| 路线顺序 | 先去哪、后去哪、每一段交通耗时 | 路线反复折返，整体时间不可行 |
| 游览安排 | 每处游览时长、开门和关门时间 | 到达时无法入园，或当天安排过满 |
| 天气因素 | 出行日期对应的天气、室内外活动适配 | 雨天仍安排不适合进行的户外活动 |
| 总预算 | 餐饮、住宿、门票和交通等开销 | 单项看似合理，合计后明显超支 |

讲解中的预算例子是：用户预算约 6000 元，方案却花到 10000 元，相差 4000 元。这样的方案即使景点安排吸引人，也不满足任务要求。

经验是：评估方案时要检查全部重要约束。某个方面做得好，不能抵消核心要求未满足的问题。

### 整理补充

落地时应区分硬约束和软偏好。例如，总预算、出行天数和必去地点可以作为必须满足的要求；餐厅评分、拍照体验和行程轻松程度可以用于比较多个可行方案。

约束冲突时，应指出冲突并说明可调整项。如果确实找不到可行方案，应如实返回原因，避免把未满足的要求隐藏在攻略文本中。

## 2 业务需求决定需要调用哪些工具 {#chapter-02}

### 讲解经验

这个场景需要获取外部环境信息。景点、路线、天气、餐饮和交通等信息共同决定行程是否成立。

系统需要根据问题进行搜索、筛选和路线规划。例如，从 A 点到 B 点途中，要搜索候选景点，再结合时间、距离和用户偏好进行选择，最后计算每段交通耗时和整体行程。

流程图中列出了 Google Search、Route Planning、POI Search、Flights 等环境工具。它们提供任务执行所需的信息和反馈。

### 整理补充

工具选择可以直接从约束倒推。

| 用户要求 | 对应的工具能力 | 应保留的结果 |
| --- | --- | --- |
| 餐厅靠近行程路线 | 地点搜索、周边搜索、路线查询 | 地点位置、绕行距离、预计耗时 |
| 景点适合游览和拍照 | 景点搜索、网页信息查询 | 候选景点、适用偏好、营业信息 |
| 三天内完成行程 | 分段路线查询、时间计算 | 各段交通时间、游览时间、每日时间表 |
| 按天气调整活动 | 日期对应的天气查询 | 查询日期、天气结果、替代安排 |
| 不超过总预算 | 费用信息查询、汇总计算 | 分项费用、估算依据、总计与余量 |

工具调用之后，还要把结果用于后续决策。调用过地图或天气接口，并不能单独证明最终方案符合要求。

工具的实际数据来源也需要核对。当前代码中的航班、火车票工具由模型生成模拟信息，不能仅凭工具名称将其当成真实票务查询；具体映射见第 19 节，工具边界设计见第 20 节。

## 3 整体流程包括数据构建 训练和评估 {#chapter-03}

### 先用六步理解主线

下面按理解和实施需要压缩成六步，并非对课件环节编号的逐字复述。

| 步骤 | 做什么 | 得到什么 | 先关注的问题 |
| --- | --- | --- | --- |
| 1 准备题目 | 获取种子、隔离数据集合、扩展 Query | 有来源且覆盖不同需求的任务集合 | 题目是否有差异，训练与测试是否隔离 |
| 2 采集示范 | 强教师模型在工具环境中完成任务 | 调用、反馈、后续操作与最终方案 | 示范是否真实可靠，过程是否完整 |
| 3 清洗数据 | 规则过滤、格式清洗、质量打分，再分配训练用途 | 合格示范和可用于 RL 的任务 | 语法合格与方案可执行是否分别检查 |
| 4 SFT 冷启动 | 用示范训练小模型 | 初步掌握工具协议和任务流程的模型 | 是否能按协议完成基本交互 |
| 5 GRPO 训练 | 当前模型执行任务，根据奖励更新参数 | 经过在线强化训练的模型及实验记录 | 奖励是否反映真实任务质量 |
| 6 独立评估 | 在隔离任务上与基线比较 | 质量、成功率和成本结论 | 提升是否真实，是否值得部署 |

工具环境贯穿教师采样、在线强化学习和最终评测；SFT 通常读取已经整理好的示范。数据污染、工具反馈错误或评分偏差都可能传递到下游，因此复杂性主要来自这些环节之间的配合。

这张图描述的是研发与训练流程。产品实际接收一次用户请求时，主要运行“需求输入 → 模型调用工具 → 根据反馈继续处理 → 输出方案”，不会每次都重新泛化数据、蒸馏和训练。

### 根据流程图与讲解整理

流程图展示了种子 Queries、训练与测试种子、样本泛化、工具交互蒸馏、规则过滤、格式清洗、大模型打分、数据切分、SFT、GRPO 和评估等环节。

结合后续“扩展前先划分数据”的讲解，可以将执行原则整理为：

```text
收集或编写原始种子问题
    ↓
去重并按原始需求分组
    ↓
先划分训练与测试种子
    ↓
各集合分别进行需要的数据扩展
    ↓
教师模型调用外部工具 采集执行过程
    ↓
规则过滤 格式清洗 质量评估
    ↓
构建 SFT 数据与 RL 任务
    ↓
SFT 训练 → GRPO 训练
    ↓
在独立测试集上评估
```

图中 DeepSeek 承担样本泛化角色，MiniMax 承担 Rollout 蒸馏角色；后续训练使用 Ms-Swift 框架，并包含课程式 Reward 设计和 LLM-as-Judge 评估。这些名称反映的是图中的方案配置，经验重点在各环节的职责及衔接关系。

### 整理补充

应区分三个对象：

| 对象 | 包含什么 | 解决什么问题 |
| --- | --- | --- |
| 种子问题 | 用户需求、场景和约束 | 决定模型需要学习处理哪些任务 |
| 执行轨迹 | 工具调用、参数、工具反馈、后续操作与最终回答 | 为模型提供任务执行示范 |
| 评估结果 | 约束检查、错误类别、质量评分 | 判断系统是否真的完成任务 |

流程图中的“清洗后数据切分”不能替代扩展前的训练与测试隔离。训练集合内部还可以继续划分 SFT、RL 等用途，但独立测试需求不能在此过程中重新混入训练。

## 4 种子数据不一定来自线上用户 {#chapter-04}

### 讲解经验

种子数据的来源取决于业务所处的阶段。

| 业务状态 | 数据来源 | 适用条件 |
| --- | --- | --- |
| 公司已有相关产品 | 从线上日志收集相关用户提问 | 已积累实际使用记录，有数据平台或相关人员支持 |
| 公司刚启动新产品或新业务 | 购买数据，或组织人工编写 | 尚未积累真实用户数据 |
| 学校 实验室 个人学习项目 | 购买数据，或多人合作编写 | 缺少公司产品与线上日志来源 |

从线上日志获取问题，确实需要先有相关产品及使用记录。这个条件限定的是“线上日志”这条路径，并不意味着没有产品就无法启动项目。

对新业务和学生项目，人工编写是一条可以直接开展的路径。

### 整理补充

购买数据时，应先检查样本是否对应本项目的任务形态。普通旅游知识问答未必包含路线、时间、天气和预算之间的组合约束，不能仅凭“属于旅游领域”就认定适合作为种子数据。

从日志中提取数据，也应先筛选与行程规划相关的问题，避免把无关查询直接混入。

## 5 冷启动不必一开始追求大量数据 {#chapter-05}

### 讲解经验

初始种子数据量可以较小。讲解中给出的量级是几百条，例如 300 至 400 条，之后再进行扩展和泛化。

可以组织实验室或团队中的几个人到十几个人，每人编写几十条，汇总形成启动数据。

这里的重点是先获得一份覆盖不同需求的种子集合，再开展后续扩展。

### 整理补充

300 至 400 条是讲解中的启动示例，不是适用于所有项目的最低门槛，也不表示几百条种子可以直接替代完整训练数据。

启动时更值得关注的是：这些问题是否具体、是否具有变化、是否包含关键约束、是否适合通过工具交互完成。

## 6 多人编写的价值在于需求多样性 {#chapter-06}

### 讲解经验

讲解特别强调：人工编写时应多找几个人参与，每人写几十条，避免全部由一个人完成。

一个人容易反复使用相似的问法、偏好和约束组合。即使写出了很多条，也可能都遵循同一种逻辑。

多人参与有助于引入不同视角，使种子问题更丰富。

### 整理补充

多人分工时，可以按场景分配任务，再统一检查任务表达是否完整。

| 场景方向 | 可以覆盖的变化 |
| --- | --- |
| 预算 | 预算紧张、适中、相对宽裕，以及明显冲突的预算要求 |
| 时间 | 短途、周末、多日游，以及到达或返程时间固定 |
| 同行人 | 独自旅行、朋友、亲子、老人同行 |
| 交通 | 自驾、公共交通、步行较多或不希望频繁换乘 |
| 偏好 | 拍照、美食、自然景观、博物馆、轻松游览 |
| 外部条件 | 雨天、闭馆、预约限制、部分信息无法查询 |

分工不宜只让不同人替换城市名称。汇总后还需要检查是否存在大量同义改写，以及某些重要场景是否完全缺失。

## 7 种子问题应写清需求与约束 {#chapter-07}

### 整理补充

为了便于人工编写和后续筛选，可以使用以下记录项。它们是工作模板，不是讲解中已经规定的数据格式。

| 记录项 | 内容 |
| --- | --- |
| 原始问题标识 | 唯一 ID，便于追踪扩展样本的来源 |
| 来源与编写人 | 线上日志、购买、人工编写及对应记录 |
| 出发地与目的地 | 旅行空间范围 |
| 日期与时长 | 出发日期、旅行天数、固定到达或返程要求 |
| 人数与同行情况 | 人均或总预算对应的人数、特殊出行需求 |
| 交通方式 | 自驾、公共交通或允许的组合 |
| 预算 | 金额、币种、按人还是按团，以及包含哪些费用 |
| 必须满足的要求 | 必去地点、景点数量、时间限制等 |
| 偏好 | 拍照、美食、轻松程度等 |
| 场景标签 | 用于检查需求覆盖和分组 |

示例种子问题：

> 从上海出发去黄山，安排三天旅行，总预算 6000 元。希望游览至少 6 处景点，其中 3 处适合拍照。餐厅尽量靠近路线，需要考虑景点营业时间、交通耗时和出行天气，并给出分项费用。

这是一条需求样例，是否能够同时满足所有要求，需要由工具查询和后续规划验证。

对于“明天出发”“下周末”等表达，应同时记录问题发生的日期。否则，同一条问题在不同时间运行，会对应不同的旅行日期。

## 8 必须在扩展前划分训练与测试数据 {#chapter-08}

### 讲解经验

后续要对种子数据做扩展。如果没有提前分开训练和测试，扩展后就可能产生相互重叠的样本。

这种重叠不要求问题文字完全一样。样本如果非常相似，模型在训练时实际上已经接触过相近内容，测试指标就可能虚高。

表现是：在原测试集上分数很好，换一批新数据却明显变差。此时难以判断模型或系统的真实能力。

因此，讲解中的明确经验是：先划分训练与测试种子，再分别扩展。

### 数据泄漏示例

假设原始问题是“上海到黄山三日游，预算 6000 元”。之后产生两个扩展版本：

- “用 6000 元安排从上海去黄山的三天行程。”
- “帮我规划上海出发的黄山三日游，总花费控制在 6000 元。”

如果一个进入训练集，另一个进入测试集，虽然文本不同，测试仍可能主要衡量模型对同一需求的熟悉程度。

### 整理补充

应至少以同一原始需求及其全部派生样本为分组单位，统一进入一个集合。推荐流程为：

1. 原始种子先去重、识别近重复需求。
2. 为同一需求及其改写分配同一个来源组标识。
3. 按来源组划分训练集和测试集。
4. 各集合内部独立生成变体，保留父样本与分组标识。
5. 扩展完成后再次检查跨集合的近重复问题和高度相似轨迹。

如需要调提示、选择模型或调整奖励，可另外设置验证集。验证集用于开发选择，测试集用于最终独立评估。

相同目的地不自动构成泄漏。应检查是否来自同一个原始需求，或存在高度相似的问题和答案轨迹。若要评估新路线泛化能力，再额外设计未见路线测试。

## 9 样本泛化负责扩展任务覆盖 {#chapter-09}

### 讲解经验

少量种子数据用于启动项目，后续还要通过样本泛化增加任务数量。可以向能力较强的大模型输入一条种子问题，通过提示词生成多条新的 Query。

讲解中举例：300 条训练问题，如果每条最终形成 5 条问题，便可得到 1500 条。这里统计的是 Query 数量；如果另外保留原始问题，应明确其是否已包含在扩展倍数中，避免重复计算。

泛化需要保留任务的上层结构，例如时间、地点、出行方式、预算、带小孩和游览偏好，同时改变具体需求，形成新的任务组合。

例如，原始任务围绕“五一期间重庆到宜昌、途经恩施、三日高铁亲子游、自然风光与土家文化、预算约四五千元”；扩展任务可以改成“春节前后广州到桂林、途经阳朔、四日亲子游、欣赏喀斯特地貌，并设置另一预算范围”。

这类变化扩大了需求覆盖。只把同一句话改写几遍，增加的主要是表达方式，而不是任务种类。

### 整理补充

扩展前应规定允许变化的维度、必须保留的约束字段、输出格式和目标数量。生成后检查需求是否完整、场景是否重复，以及是否意外丢失原始任务中的重要约束。

测试任务是否扩展取决于现有覆盖和数量。如果测试集已经足够，可以只扩展训练集；若测试覆盖不足，也可以在测试集合内独立扩展。两种方式都必须保持原有数据边界，不能把训练种子的派生样本补进测试集。

扩展后的问题需要标记是否可能存在约束冲突。有意构造的冲突任务可用于评价系统的识别与解释能力，不能直接当成已经确认有可行解的正常任务。

### 数据合成第一步的具体课件

本页“综合项目 数据合成”展示的是 Query 泛化步骤，尚未生成完整答案或工具执行轨迹。

| 项目 | 课件展示 |
| --- | --- |
| 初始数据 | 人工编写 306 条训练种子和 100 条测试题，合计 406 条，均为 Query |
| 调用组织 | 并发调用模型，配合重试机制 |
| 泛化模型 | 图中标注为 DeepSeek-V4 |
| 每条输入的目标 | 参考原问题，生成 5 个新的旅游问题 |
| 扩展后规模 | 1835 条训练问题和 100 条测试题 |

这页展示了只扩展训练集的做法，测试题数量保持 100 条。模型名称是课件中的配置记录，不作为当前可用型号或推荐选型的核实结论。

### 为什么本项目不扩展测试题

本段讲解进一步明确，406 条种子在这一阶段都只有问题，尚未配套完整答案和工具执行轨迹。泛化输入仅来自其中 306 条训练问题，100 条测试问题保持原样。

保留 100 条的理由来自本项目的任务特点与评测成本：每条题目包含较复杂的行程需求，需要多步处理；讲解者描述，完整跑完这批测试任务大约需要一个小时。因此，在当时的任务覆盖与资源条件下，选择将生成资源用于扩展训练问题，没有把测试题增加到数千条。

整理补充：这里的“100 条足够”是当前项目的设计判断，“约一个小时”是讲解中的运行经验，不是本次在工作区测得的结果。实际是否足够，应同时看任务类型、难度分布、错误覆盖和结果波动；更换模型、工具、并发或任务集合后，应重新记录评测耗时。

固定测试集有利于连续比较训练前后表现，但需要控制其用途。不能因为长期使用同一批题，就按测试结果反复修改训练策略；用于开发选择的任务应单独承担验证用途。

### 本页提示词的关键要求

| 要素 | 具体要求 | 作用 |
| --- | --- | --- |
| 角色 | 熟悉中国旅游城市、交通和景点路线的文字改写专家 | 指定生成任务所需的领域背景 |
| 数量 | 每次生成 5 个新问题 | 控制每条种子的扩展规模 |
| 变化 | 原问题仅作参考，新问题不能与其意思相同或相近 | 鼓励需求变化，减少只换说法的样本 |
| 内容 | 地名和景点应真实，问题符合逻辑，可替换地点和城市 | 减少虚构实体和明显不合理需求 |
| 约束 | 必要时增加价格、距离、评分、交通方式、预算、途经点等 | 扩展多约束任务组合 |
| 输出 | 每行一个问题，不输出理由或其他无关内容 | 便于程序解析和计数 |

提示词要求真实地点和合理需求，但仍需后续检查；模型遵循了输出格式，并不能单独证明地名、交通和约束组合正确。

### 对当前 notebook 与数据的核对

本次补充同时核对了工作区的 data_expansion.ipynb、data/train_seed.jsonl 和 data/train_expansion.jsonl，确认以下事实。

1. 输入文件有 306 条种子问题。
2. 当前 notebook 使用 ThreadPoolExecutor，MAX_WORKERS 设为 50；课件的“多进程并发调用”与当前代码的线程池实现应分别表述。
3. chat 函数带有默认值为 3 的 max_retry 参数；具体重试条件与等待方式应按实现检查，不能从图中直接推断。
4. 对成功返回的结果，程序将原问题和生成的新问题一并加入集合，然后进行去重。
5. 现有扩展文件包含 1835 条不重复问题，其中保留全部 306 条原题，新增不重复问题为 1529 条。

若每条原题恰好生成 5 条，并保留全部原题，去重前的理论数量是 306 × 5 + 306 = 1836 条。现有文件最终为 1835 条，说明不能把“每条要求生成 5 条”等同于最终固定倍数；仅凭最终文件和课件，不能断定差额恰好来自哪一次生成或去重。

当前输出文件只保存 question 字段；程序内部使用的种子索引没有随结果输出。后续若需要自动核查来源和训练测试隔离，应同时保存 seed_id、生成序号、数据集合、模型配置和处理状态，而不是依靠文件位置推断。

### 从这一实现提炼的经验

并发和重试解决吞吐与调用稳定性问题；数据多样性、真实性和约束合理性仍需单独评估。并发度应按接口限额和实测失败率调整，50 是当前代码配置，不是所有接口的通用值。

### 并发数与接口限额需要分别控制

讲解建议批量并发调用，避免逐条等待导致扩展时间过长。当前配置为 50 个 worker，可根据账户接口额度和实际运行表现增减。讲解者描述，300 多条种子在其当时配置下可在几分钟内完成扩展；复现时应以自己的计时和失败记录为准。

整理补充：worker 数表示允许同时进行多少个请求任务，QPS 表示每秒请求数，两者不能直接画等号。接口还可能按分钟请求数或 token 数限流，应以账户实际限制为准。

例如，请求耗时较长时，50 个并发任务不等于每秒发出 50 次请求；请求集中开始或同时重试，又可能形成瞬时突发。应在限制并发之外，单独控制请求发送速率，并对可重试错误设置有限次数的退避等待。

批量运行至少记录成功率、限流次数、重试次数、请求耗时和总完成时间。先使用小批量测量，再调整并发配置，比仅增加 worker 更容易判断实际瓶颈。

除去重外，还应检查模型是否恰好返回 5 条有效问题，并分别记录请求数、成功数、生成数量、原题保留数、重复剔除数和最终有效数量。重试和断点恢复应避免把同一结果重复写入；需要复现实验顺序时，应使用稳定去重及固定洗牌方式。

## 10 样本泛化与 Rollout 蒸馏是上下游关系 {#chapter-10}

### 讲解经验

样本泛化结束后，当前阶段仍主要持有 Query，没有对应的完整执行答案。下一步是使用能力较强的商业模型完成这些任务，采集可用于训练的示范数据。

两个阶段可以使用不同模型。流程图中，样本泛化与 Rollout 蒸馏本来就分别安排了模型角色。模型选择需要综合考虑任务效果、成本和生成速度，可以根据实际业务调整。

### 两个过程如何衔接

| 环节 | 输入 | 输出 | 主要作用 |
| --- | --- | --- | --- |
| 样本泛化 | 少量种子 Query、泛化提示词 | 更多不同需求的 Query | 扩大任务和约束组合的覆盖 |
| Rollout 蒸馏 | Query、工具定义、可交互环境 | 工具调用、工具反馈、后续操作、最终回答 | 获取强模型完成任务的示范 |

可以把它理解为：泛化阶段扩展题目，蒸馏阶段执行题目并记录过程。

```text
原始种子 Query
    ↓ 模型 A 进行样本泛化
新的 Query 集合
    ↓ 模型 B 调用真实工具执行任务
工具调用 → 工具反馈 → 后续调整 → 最终回答
    ↓ 清洗与质量审核
可用于小模型 SFT 的示范轨迹
```

例如，模型 A 生成“广州到桂林四日亲子游、预算 8000 元、尽量减少换乘”的需求。模型 B 再围绕这条需求查询景点、天气、交通和路线，检查时间与预算，形成完整行程及工具交互记录。

一条 Query 可以采集一条或多条候选执行轨迹。多条轨迹有助于比较执行质量，但它们仍来自同一个任务，不能作为多个独立种子跨训练与测试集合分配。

### 为什么允许使用不同模型

两步对模型的要求不同，可以分别评测后选型。

| 阶段 | 重点观察的能力 | 成本观察项 |
| --- | --- | --- |
| 样本泛化 | 需求多样性、约束完整性、重复率、场景覆盖 | 每条合格新 Query 的成本和生成耗时 |
| Rollout 蒸馏 | 工具调用、读取反馈、持续执行、多约束规划、结果可靠性 | 每条合格轨迹的成本、轮数、工具耗时和失败重试 |

前一步决定后续训练面对什么任务，后一步决定模型能从什么执行示范中学习。泛化问题过于单一，会限制轨迹的任务覆盖；蒸馏执行不可靠，会把错误操作和不成立的行程带入训练。

讲解中提到的模型名称和价格比较属于当时的选型背景。落地时应以同批任务的实测质量、速度和当期价格核对，不把某个模型固定为所有任务中的最佳选择。

### 区分教师蒸馏与在线强化学习中的 Rollout

| 使用位置 | 谁执行任务 | 轨迹如何使用 |
| --- | --- | --- |
| 教师 Rollout 蒸馏 | 已选定的强教师模型 | 清洗后作为学生模型的示范数据 |
| GRPO 在线训练 | 当前正在训练的策略模型 | 对当前轨迹计算奖励，再更新策略参数 |

两处都需要与环境交互，但参与执行的模型和数据用途不同。教师轨迹用于传递任务执行示范；在线强化学习需要当前模型自己尝试，依据实际反馈获得奖励。

只让模型直接写出一份最终攻略，得到的是答案层面的示范。若希望学生学习工具使用和多轮执行，就需要保留工具调用、参数和真实反馈等过程记录。

### 数据蒸馏课件强调完整交互轨迹

本页“综合项目 数据蒸馏”展示：扩展后的 Query 进入教师模型的 Agent Loop，教师通过工具环境反复获取信息，在处理异常和边界条件后，导出 rollouts。图中教师标注为 MiniMax-M2.7，属于本页方案配置记录。

这里采集的是可观察的完整交互轨迹，例如：

```text
用户提出行程需求
    ↓
教师选择天气查询和景点搜索等工具
    ↓
执行器调用接口并返回实际结果
    ↓
教师根据结果继续查询路线和交通
    ↓
必要时处理查询失败或调整安排
    ↓
教师输出最终方案
    ↓
保存完整消息 调用参数 工具反馈与结束状态
```

轨迹包含模型对外输出的计划或操作说明、工具调用及反馈和最终回答。采集完整轨迹不等于要求获取模型未公开的内部思维；工具过程和实际证据应完整保留，也不能补造推理或工具返回来填补缺失。

### 需要搭建的环境包含什么

本项目中的“环境”主要是一组可调用的业务工具，以及负责执行、返回、维护上下文和记录状态的程序。工具可以封装已有搜索、地图和交通服务，不要求自行开发地图或搜索引擎。

| 环境部分 | 需要准备的内容 | 作用 |
| --- | --- | --- |
| 工具定义 | 工具名称、用途、参数、类型和必需字段 | 让教师知道有哪些动作以及如何调用 |
| 接口适配 | 将规范参数转换为接口请求，统一成功与错误返回 | 连接外部数据来源 |
| 工具执行器 | 解析调用、检查参数、派发任务、关联返回 | 把模型输出转成实际操作 |
| Agent Loop | 把工具反馈加入上下文，再次请求模型，判断结束条件 | 支持多轮任务执行 |
| 运行管理 | 超时、重试、调用额度、上下文和轮次上限 | 使批量采集能够稳定结束 |
| 轨迹存储 | 问题来源、消息、调用、结果、状态和配置版本 | 支持清洗、复现及后续训练 |

课件中的工具环境包括 Google Search、Route Planning、POI Search、Flights Search、Web Visit、Around Search、Weather Predict 和 Train Search，分别对应网页搜索、路线规划、地点搜索、航班查询、网页访问、周边查询、天气和列车查询。

代码核对补充：当前两个 Agent 入口选择 Firecrawl 搜索与网页访问实现；天气、地点、周边和路线使用高德接口；航班、火车票为模型模拟。课件工具标签与代码实际调用的服务应分别记录，详见第 19 节。

“搭环境”指建设可交互执行链。对实际旅行方案，地点、天气、路线和交通等事实应有对应来源；低成本开发阶段可以使用模拟或回放，但应明确标记并限制其用途，不能将模拟票价或天气当成已核实事实。

### 批量工具调用需要尊重依赖关系

课件标注 Batch Tools 调用。同一轮中互不依赖的工具可以并发执行，例如对已知目的地查询天气和搜索景点；必须先拿到地点坐标才能计算的路线，则需要等待前置结果。

每个调用应有可关联的标识。即使结果返回顺序不同，也应能对应正确工具、参数和任务。某个工具失败时，其他有效结果可以继续保留，失败信息需要如实反馈给教师。

### 批处理可以发生在两个层级

补充讲解给出了两种相互关联的优化：教师在同一轮输出多个工具调用，以及单个工具一次接收多个查询项。

| 层级 | 示例 | 执行方式 |
| --- | --- | --- |
| 同一轮多个工具调用 | 同时查询已知目的地的天气、航班和景点 | 执行器派发独立任务，收集结果后回传教师 |
| 一个工具的多个查询项 | 搜索工具接收桂林攻略、贵阳攻略、沿途交通等关键词列表 | 工具内部逐项请求或调用服务商批量接口，再组织返回 |

这两层可以组合，但“接收一个列表”并不意味着服务商只计算一次请求，内部的查询量与费用仍需统计。

如果三个独立工具耗时分别为 2、5、3 秒，串行执行的工具等待约为 10 秒，并发后理想情况下约为 5 秒，即最慢工具的耗时。这里不包括模型生成、排队、重试和结果组织时间，实际收益需要测量。一次输出多个工具调用，还可能减少在各次调用之间重复请求模型的等待。

讲解采用协程实现网络工具并发。整理补充：协程适合组织这类 I/O 等待，但是否快于线程取决于接口、并发控制和实现，不能单凭使用协程就认定吞吐更高。

运行多工具并发需要两个条件同时成立：模型及其调用协议能够表达合法的多个调用，执行器能够实际调度并发任务。模型输出多个调用，不代表工具代码已经并行执行；存在前置依赖的调用也不能强行并发。

### 稳定性分别落实到工具服务和 Agent 循环

讲解强调，连接一组可调用接口只是起点。批量采集时，外部网络、服务商压力、工具参数、额度和长上下文都可能造成失败；需要在工具本身和调用方两层处理。

| 所在层 | 主要责任 | 反馈与记录 |
| --- | --- | --- |
| 工具服务 | 校验参数、请求接口、处理可恢复错误、控制返回长度 | 成功结果或可识别的失败类型 |
| Agent 循环 | 将结果与调用配对、反馈给教师、限制轮次和上下文、决定结束 | 每轮状态、后续操作和停止原因 |
| 批量采集调度 | 限流、任务隔离、凭据管理、保存进度和失败任务 | 完成数量、有效轨迹、成本及待恢复任务 |

这张表是依据讲解整理的责任划分，不表示当前代码已经实现或验证了全部机制。

### 按失败原因选择恢复方式

| 失败类型 | 应采用的处理方式 | 不宜采用的处理方式 |
| --- | --- | --- |
| 临时网络错误或服务超时 | 在总时限内有限重试，保留调用标识并避免重复落盘 | 无等待地无限重试 |
| 参数名、类型或必需字段错误 | 把字段、预期类型和合法范围返回教师，由其纠正参数 | 不改变参数反复请求同一接口 |
| 查询合法但无结果 | 返回明确空结果，教师决定换关键词、替代来源或说明缺失 | 把空结果伪装成成功查到内容 |
| 速率限制 | 按限流维度等待、降低发送速率，必要时暂停相关任务 | 仅增加并发，导致更多请求同时失败 |
| 凭据无效或余额不足 | 标记该凭据状态，在已配置可用资源中调度，或结束并报告 | 持续立即重试不可用凭据 |
| 响应格式异常 | 保留原始返回，标注解析错误，按固定策略恢复 | 编造工具结果来满足格式 |

讲解中的关键经验是：失败要变成模型能够理解的工具反馈，让教师有机会调整下一步。例如 POI 查询缺少城市参数，就返回缺失字段和预期要求，而不是让整条采样任务因未捕获异常直接退出。

整理补充：给模型的错误应精简、可操作；完整诊断单独保存。模型参数修正属于一次新的任务动作，网络重试属于同一请求的基础设施恢复，应分别统计，避免掩盖真实模型错误。

### 凭据池轮询不能替代限流

讲解提出使用多个可用 key 轮询，在某个凭据不可用时切换，并分散调用负载。

整理补充：调度应记录凭据健康状态、额度和冷却时间。限流可能按 key、账户或项目生效，多个 key 也可能共享同一额度，因此不能直接把 key 数量乘以单 key 限额作为可用吞吐。应按服务商实际限流维度配置发送速率。

工具重试与凭据切换需要统一请求标识和重试预算。收到超时后，先避免重复提交和重复记录；同一服务整体不可用时，应暂停或终止相关采样，而不是无上限轮换凭据。

### 长工具返回需要先提取相关信息

网页抓取等工具可能返回大量内容，但与用户目标相关的部分有限。讲解建议对返回进行截断或压缩，减少冗余内容占用上下文。

整理补充：优先保留与任务有关的证据、来源和日期，将完整返回另外存储。摘要或截断不得丢掉预算、营业限制、交通条件等影响结论的事实；纯粹截取前若干字符可能漏掉正文后半段的关键信息。

上下文预算应同时考虑系统提示、工具定义、历史消息、新工具返回和后续答案所需空间。模型 token 上限与文本字符数不是同一指标，应使用相应 tokenizer 或接口返回用量来测量，并给后续生成保留空间。

### 蒸馏循环的异常与边界

| 课件关注项 | 处理要求 | 轨迹记录 |
| --- | --- | --- |
| 上下文长度 | 限制进入模型的内容，保留任务约束与关键证据；完整原始返回另存 | token 用量、摘要或截断策略、是否触及上限 |
| 工具调用次数 | 设置每任务轮次和调用预算，达到上限后停止继续调用 | 实际轮数、调用数、终止原因 |
| 工具调用失败 | 返回可识别错误，对可恢复错误有限重试 | 错误类型、重试次数、恢复结果 |
| 答案标签未闭合 | 检查生成是否截断，按固定策略处理；无法可靠恢复时标为不完整 | 原始文本、修复或剔除依据 |
| 超时重试 | 分别管理模型请求与工具请求超时，避免无限等待和重复写入 | 请求标识、耗时与重试结果 |
| key 轮询 | 管理已配置的可用凭据，并遵守各自额度 | 记录凭据代号与调用状态，日志不保存密钥值 |

达到上限后即使输出了文本，也不代表完成了用户任务。导出数据应区分成功、失败、超时和轨迹不完整，再交给清洗流程筛选。

### 提前停止与答案修复需要保留质量状态

讲解提出，当上下文接近上限或工具调用次数达到阈值时，给模型明确反馈，要求依据已获取的信息收尾，并停止继续调用工具。

整理补充：收尾内容应指出仍缺少的信息或未完成的约束。需要区分“正常完成”和“因资源上限被迫总结”，不能把两者一律计为合格任务。一次模型输出可以包含多个工具调用，因此模型轮次、工具调用数、重试数应分别计数。

若出现答案标签未闭合，应先检查原始输出、结束原因及是否因 token 上限截断。只有确定内容已完整、缺少的仅是协议结束标记时，才按固定规则修复；内容缺失时应续写、重新采样或标为不完整，不能仅补闭合标签就当作正确答案。

本地 data_distill.py 中可看到 MultiTurnReactAgent、多工具异步执行、工具失败反馈、调用轮次与上下文边界处理等入口，便于后续对照课件继续学习；这不等于其全部边界处理已经通过质量验收。

### 用有效轨迹产出来衡量环境能力

讲解将稳定、可扩展的环境视为持续实验的重要基础：环境越稳定，同样时间内能够完成的有效采样越多，后续清洗、训练和迭代也越容易推进。

整理补充：观测至少包括每小时完整轨迹数、清洗后有效轨迹数、工具成功率、限流与超时次数、重试恢复率、提前停止比例，以及每条有效轨迹的时间和费用。仅统计发出了多少次请求，无法说明采集效率。

这些指标要区分模型错误、工具错误和基础设施故障，记录任务难度与配置。更高吞吐只有在任务覆盖和轨迹质量可比较时才有意义。

保存下来的 rollouts 是原始蒸馏数据，其中可以包含错误操作、失败恢复和不完整结果；采集结束之后仍要经过规则、格式和质量三层清洗，再决定哪些样本进入训练。

### 环境搭建与后续训练的联系

教师蒸馏先使用这套环境采集示范；GRPO 阶段再让当前训练模型通过同样的工具协议执行任务。应尽量保持工具定义、错误格式和结果结构一致，并记录变化版本，减少示范与训练之间的接口差异。

学习时可先打通“一条 Query → 一次工具调用 → 返回结果 → 继续执行 → 完整保存”的最小流程，再逐步加入批量工具、并发采样和异常恢复。

### 蒸馏的产品目标与环境选择

讲解强调，使用小模型蒸馏的产品动机，是在目标旅行任务上尽可能接近教师模型的表现，同时降低部署与调用成本。应一起衡量任务质量、硬件需求、推理时延和持续服务费用。

讲解还提出低成本复现与质量优先两类环境方案。两类方案都需要明确工具、接口、返回格式和反馈来源，再让教师模型进行多轮执行。可用 ReAct 式循环理解：根据当前任务选择动作，调用工具，读取结果，再决定下一步，直到能够给出最终方案。

整理补充：环境方案比较时，应记录哪些信息来自实际接口，哪些是回放或模拟结果，并将其作为实验条件。模型体量、总参数与激活参数属于不同信息，转写中的具体数字应查阅模型说明后再使用；小模型是否达到目标质量，应通过同批任务评测确认。

## 11 数据规模不能代替数据质量 {#chapter-11}

### 讲解经验

样本可以从几百条扩展到几千条，但不必因为生成容易就持续放大到几十万条。反复合成可能产生大量任务结构和表达都相似的样本，数量增长不一定带来同等的有效覆盖。

讲解特别强调垂直领域后训练中的数据质量，以及 Agentic RL 的执行成本。旅行任务往往包含较长的多轮工具交互，在线强化训练还需要当前模型执行这些过程；数据过多会显著增加训练时间与环境调用负担。

因此，数据规模应与任务覆盖、质量和可承担成本共同决定，后续清洗需要严格把关。

### 来自流程图的经验

扩展和蒸馏之后，还需要规则过滤、格式清洗和大模型打分，不能把生成的样本全部直接用于训练。

### 整理补充

清洗应分别检查以下内容：

| 维度 | 检查问题 |
| --- | --- |
| 任务完整性 | 需求是否清楚，是否丢失人数、日期或预算等关键约束 |
| 格式有效性 | 消息结构、工具名称和参数是否可解析 |
| 执行关联 | 工具反馈是否对应实际调用，轨迹是否前后连贯 |
| 结果一致性 | 最终方案是否使用了工具返回的信息 |
| 约束满足 | 时间、预算、景点数量和偏好是否得到检查 |
| 数据独立性 | 是否存在跨集合的同源样本和近重复内容 |

格式正确只能证明样本能被读取，不能证明行程能够执行。大模型打分可以帮助筛选，但距离、时间和费用等可计算要求，应尽量增加明确校验。

### 三级清洗策略

最新讲解将清洗明确拆成三层，各层处理不同的问题。

| 层级 | 主要处理什么 | 典型检查 | 处理结果 |
| --- | --- | --- | --- |
| 第一层 规则过滤 | 明显不可用的样本 | 空输出、任务未完成、显著无效内容、违反基本协议 | 快速剔除明显坏例，记录原因 |
| 第二层 格式清洗与修复 | 可解析性与交互结构 | 协议标签闭合、最终回答位置、工具调用与返回配对、无用内容 | 在不改变事实的前提下规范格式；无法可靠修复则剔除 |
| 第三层 大模型质量评审 | 执行过程与最终方案质量 | 工具选择和执行顺序、反馈使用、约束满足、合理性和可执行性 | 按冻结的评分标准过滤低质量轨迹 |

前两层优先处理显而易见的问题和结构规范，第三层进一步评估任务质量。三层不能互相替代，格式完整的样本仍可能包含不可执行的行程。

格式清洗应与训练、离线推理和线上调用使用的协议一致。例如，工具调用后需要有可对应的返回记录，最终回答应放在协议规定的位置。若接口实际调用失败，应保留真实错误，不能通过补写返回内容把失败伪装为成功。

可以修复确定的格式问题，但不能编造天气、票价、路线或工具反馈。修复后的样本应再次执行格式检查，保留原始记录和修复说明。

质量评审应分别看可观察的执行路径与最终回答。路径包括工具、参数、返回和后续动作，不要求依靠模型内部思维文本判断正确性。答案评审则关注需求响应、费用、时间和落地条件，两类结果都应有可定位的依据。

成本估算应分别统计 Query 泛化、教师轨迹采集、SFT 和在线 RL。对于在线 RL，可先用少量任务测量每条轨迹的轮数、token 数、工具次数和耗时，再估算任务数、候选轨迹数及重复训练带来的总开销。

不要用“成功生成多少条”代替“最终留下多少条有效且有差异的样本”。数据清洗还应记录剔除原因，以便判断需要补充的是新场景、更好的教师执行，还是更可靠的工具反馈。

## 12 清洗后的数据按用途组织 {#chapter-12}

### 讲解经验

清洗完成后，需要组织用于 SFT 冷启动、在线强化学习和最终验证的数据。最终验证任务应与最初隔离出的测试种子对应，避免其在数据生产或训练中重新进入训练用途。

这里有两次不同含义的数据划分：第一次是在扩展前确定训练与测试边界；第二次是将训练侧的数据和任务组织为 SFT、RL 等用途。后一次不能推翻前一次的隔离关系。

### 整理补充

| 数据用途 | 需要的内容 | 模型如何使用 |
| --- | --- | --- |
| SFT 冷启动 | Query、工具定义、合格示范交互与最终回答 | 学习示范中的输出和操作协议 |
| 在线 RL | Query、工具环境、任务限制、奖励规则 | 当前模型自己生成轨迹并接受评分 |
| 开发验证 | 独立任务与固定评测条件 | 调整提示、选模型、调整训练配置 |
| 最终测试 | 从最初保留的独立测试需求形成的任务 | 在方案冻结后报告最终表现 |

SFT 与 RL 可以围绕训练侧的相关任务开展，不必把它们强制视为互不相关的业务场景。两者的数据格式和用途不同，最终测试边界应始终保持。

讲解中使用“验证数据”指代最终保留任务。工程中需要区分：如果这批数据反复用于调奖励、挑模型或调提示，它就是开发验证集，还需要另一批最终测试任务。测试参考信息可以由固定流程构建，但不得用于更新待测模型或按测试分数反复调整方案。

## 13 SFT 冷启动与在线强化学习分两阶段完成 {#chapter-13}

### 讲解经验

先通过 SFT 让模型学习已有示范，再进行在线强化学习，是本项目采用的训练顺序。

SFT 阶段帮助小模型掌握基本输入输出规范和操作顺序，例如什么时候调用工具、如何接收工具返回、何时输出最终答案。冷启动完成后，再让当前模型在工具环境中执行任务，根据奖励信号优化参数。

| 比较项 | SFT 冷启动 | 在线 GRPO |
| --- | --- | --- |
| 主要学习来源 | 清洗后的教师示范 | 当前模型生成的任务轨迹及奖励 |
| 训练时做什么 | 根据已给定的示范输出计算训练损失 | 生成候选轨迹、计算奖励、更新策略 |
| 重点目的 | 建立基本执行能力与协议习惯 | 改善任务决策和最终完成质量 |
| 关键依赖 | 示范质量、格式一致性、任务覆盖 | 可交互环境、奖励、采样质量和运行成本 |

### 整理补充

SFT 后应先检查工具调用是否合法、是否会无依据提前回答、能否处理必要的反馈，再开始较大规模在线训练。若基本交互还不稳定，应先定位数据、提示或协议问题。

讲解提到 ms-swift、分布式部署，以及采样与训练之间的调度。它们属于训练工程层：负责组织模型生成、工具执行、奖励计算和参数更新，不改变两阶段各自的学习目标。

“异步工具调用”“异步推理服务”和“采样与参数训练真正重叠”是不同概念。具体是否启用、是否提高吞吐，应结合实际版本、配置和运行记录核验，不宜仅凭使用了某个框架就宣称实现了全部异步能力。

## 14 开放式规划任务需要复合奖励 {#chapter-14}

> **阅读衔接：** 本节保留奖励设计的讲解阶段；后续核对出的六项奖励、权重、评分范围与优势计算见[第 27.17–27.24 问](#question-27-17)。

### 讲解经验

旅行规划通常没有唯一标准答案。同一需求可以有多条合理路线、不同餐饮安排和不同表达方式，因此难以只靠与某个参考答案逐字比较来评价质量。

奖励设计需要结合中间过程和最终答案。讲解提出课程式、复合 Reward 方案，后续再展开具体规则。

### 整理补充

开放式不代表所有指标都只能主观评审。预算、时间衔接、景点数量、工具参数合法性等，可以进行规则检查；体验、偏好匹配和方案表达等，再结合质量评审。

| 维度 | 可检查的问题 | 评分来源示例 |
| --- | --- | --- |
| 格式与协议 | 调用是否可解析、回答位置是否正确 | 解析器与规则 |
| 执行过程 | 工具是否合适、是否利用反馈、是否无效重复 | 规则与轨迹评审 |
| 任务约束 | 时间、预算、景点数量等是否满足 | 实际工具数据与计算 |
| 最终方案 | 是否完整、合理、可执行并符合偏好 | 规则与质量评审 |

课程式奖励可以理解为随训练阶段调整学习重点，例如先建立合法交互，再逐步提高完整任务质量的权重。这里是理解方式；具体阶段、权重和公式应以实际方案为准，当前讲解尚未给出这些参数。

各阶段仍应保留核心约束。不能为了提高格式分或过程分，让明显超预算、时间冲突的方案获得很高的整体评价。

## 15 训练效果必须通过独立任务验证 {#chapter-15}

> **阅读衔接：** 多模型交叉评估在这里作为设计建议；当前脚本的双向 A/B 与历史结果见[第 27.27 问](#question-27-27)，两者不能混为已完成的同一套评测。

### 讲解经验

数据泄漏会影响对模型真实能力的判断，因此测试集必须能够反映模型对新任务的处理能力。

### 整理补充

评估旅行 Agent 时，除了回答是否清晰，还应核对：

- 是否识别并保留用户的重要要求。
- 是否选择了需要的工具，参数是否正确。
- 是否根据工具反馈调整了安排。
- 路线、营业时间与游览时间能否衔接。
- 餐饮、住宿、门票和交通的费用是否汇总完整。
- 信息不足或约束冲突时，是否如实说明。

可以分别比较未训练模型、SFT 模型和强化学习后的模型。应固定评测任务、日期基准、工具条件和预算，并记录不同版本的变化，避免把外部工具或数据变化误当成训练效果。

### 多模型裁判与角色隔离

最新讲解提出使用多个大模型对结果交叉评分，再汇总得分，并尽量选择未参与前面数据生产和训练辅助环节的模型，以降低同一模型偏好影响最终评估的风险。

需要区分裁判出现的三个位置：数据清洗中的裁判决定哪些示范进入训练；RL 奖励中的裁判影响模型优化方向；最终评测裁判用于评价训练结果。这些角色的模型、提示、评分标准和版本均应记录。

整理补充：不同模型交叉评分能够提供更多视角，但不能保证没有共同偏差。汇总前应统一量表和维度，保留各裁判原始分数、理由和分歧；若采用等权平均，应提前固定规则。对费用与时间等事实仍使用可复核的计算，不能用平均评分代替。

对比未训练、SFT 和 GRPO 模型时，可隐藏模型身份并随机排列候选结果，减少位置和身份偏好。最终报告同时给出客观约束完成情况与裁判评分，避免只报一个总分。

## 16 可直接采用的工作顺序 {#chapter-16}

以下是依据前面经验整理的执行清单。

1. 明确目标任务和要满足的业务约束，先定义怎样才算完成。
2. 根据业务阶段选择数据来源：线上日志、购买或多人编写。
3. 组织多人按不同场景编写少量高质量种子，记录来源。
4. 汇总去重，检查约束完整性和场景覆盖。
5. 按原始需求分组，先划分训练、验证和测试集合。
6. 按覆盖需要在各集合内部独立扩展，保留父样本与分组关系。
7. 分别评测泛化模型与教师执行模型，比较合格样本质量、耗时和成本。
8. 由教师模型通过工具交互采集真实执行过程，形成可追踪的轨迹。
9. 分别开展规则过滤、格式清洗和质量评估，保留合格示范及筛选记录。
10. 明确 SFT、RL、开发验证与最终测试的用途和来源边界。
11. 使用示范轨迹开展 SFT，检查基本工具交互能力，保留数据与模型版本。
12. 设计过程与最终任务质量相结合的奖励，检查明显失败方案能否被识别。
13. 测量小批量在线采样成本，再由当前策略执行任务，开展 GRPO 训练。
14. 固定评测任务、裁判与汇总规则，与未训练和 SFT 基线进行对照。
15. 分析错误类别和成本，决定下一轮需要补数据、改工具、改奖励还是调整训练。

### 密钥加载与模型服务切换

本项目通过 `load_dotenv()` 加载 `.env`，再通过 `os.environ[...]` 或 `os.getenv(...)` 读取配置。以搜索工具为例：

```python
load_dotenv()
self.firecrawl_client = Firecrawl(
    api_key=os.environ["FIRECRAWL_API_KEY"]
)
```

因此，代码中没有直接写密钥，也可以通过环境变量完成客户端初始化。`os.environ[...]` 对缺失变量会抛出 `KeyError`；默认的 `load_dotenv()` 不覆盖进程中已经存在的同名变量。

项目根目录 `.env` 的配置示意如下，仅使用占位符：

```dotenv
FIRECRAWL_API_KEY="你的Firecrawl密钥"
AMAP_MAPS_API_KEY="你的高德Web服务密钥"
OPENAI_API_KEY="你的模型服务密钥"
OPENAI_BASE_URL="https://your-model-service.example/compatible-mode/v1"
LLM_MODEL_ID="该接口实际支持的模型名称"
MAX_POI_RESULTS=3
```

服务提供的 `API_KEY`、`BASE_URL` 在本项目中需要分别写入 `OPENAI_API_KEY`、`OPENAI_BASE_URL`。服务地址可以指向 OpenAI 兼容服务；更换后还必须核对该服务实际支持的模型 ID，不能从密钥或 URL 推断模型名称。配置写入成功和实际模型调用成功需要分别验证。

这组模型配置同时影响 `visit` 的摘要、模拟航班和模拟列车工具。高德、Firecrawl 继续使用各自的密钥。真实凭据不写入经验总结、示例代码或运行记录。

```text
ModuleNotFoundError: No module named 'prompt'
```

直接执行子目录文件时，Python 将脚本所在的 `tools/` 目录作为入口搜索路径；根目录的 `prompt.py` 没有因此自动变为可导入模块。终端当前目录与脚本入口目录是两个概念。

本项目采用以下启动方式，让根目录参与模块查找：

```bash
cd /path/to/travel_agentic_rl
python -m tools.tool_web_search
python -m tools.tool_visit
python -m tools.tool_weather
python -m tools.tool_poi_search
python -m tools.tool_around_search
python -m tools.tool_route_planning
```

以上命令应按需要逐条运行，每个模块执行其末尾 `__main__` 中的测试参数。现有这些工具入口没有实现通用的命令行参数解析；修改查询内容时，应修改对应的 `params`，不能直接假定支持 `--city` 或 `--address` 等选项。

上传到 AutoDL 时，应保留完整项目依赖目录，至少包括：

```text
travel_agentic_rl/
├── .env
├── prompt.py
├── tools/
│   └── tool_*.py
└── utils/
    ├── logging.py
    ├── markdown.py
    └── text.py
```

此前截图未显示 `utils/`，而网页访问依赖其中的日志模块，高德相关工具还依赖 Markdown 转换与文本截断模块。应检查远端文件是否完整，不能仅解决 `prompt` 后就认定所有导入已通过。

安装依赖时使用运行脚本的同一个 Python，例如 `python -m pip install ...`，避免安装环境和执行环境不一致。单独测试网页访问时，项目版本的相关依赖为：

```bash
python -m pip install "qwen-agent==0.0.34" "python-dotenv==1.2.2" "json_repair==0.59.9" "openai==2.32.0" "httpx==0.28.1" "beautifulsoup4==4.13.4" "firecrawl-py==4.26.0" "tiktoken==0.12.0" requests
```

### 网页搜索、网页访问和独立运行入口

`search` 的输入示例为 `{"query": ["春熙路 美食", "成都 景区预约"]}`。工具为每个关键词发起搜索，支持并发，返回链接和摘要文本；默认结果限制为 5，接口超时参数为 35 秒。`SEARCH_MAX_RETRIES=2` 在当前循环中表示最多尝试 2 次，即首次加 1 次重试。搜索无结果不会触发异常重试，最终错误提示也是字符串。

`visit` 的输入为 `{"url": "网页地址", "goal": "希望提取的信息"}`，也支持 URL 列表。流程为抓取正文、清理或提取文本、按 token 截断、填入 `EXTRACTOR_PROMPT`、调用模型、解析并返回证据与摘要。它补充具体网页的详细信息；搜索工具主要负责发现网页。

`visit` 优先使用 Firecrawl 的 Markdown 正文，失败或提取文字不足时回退到 requests 与 BeautifulSoup。即使采用备用抓取方式，源码仍会导入 Firecrawl 包，并在默认初始化时创建模型客户端，依赖与配置需要分别准备。批量 URL 分支的 180 秒外层超时不能解释为所有单 URL 调用都受到同一总时限约束。

这两个工具的当前 `call()` 实现都按字典取参数；类型标注中的 `str` 不代表已经实现 JSON 字符串解析。直接调用时传 Python 字典。

当时在本地新增了 `run_visit.py`，显式加载项目根目录 `.env`，支持从命令行传一个或多个网址及提取目标。例如，在同步该文件到 AutoDL 后可执行：

```bash
python run_visit.py --url "https://example.com/article" --goal "提取开放时间与预约要求"
```

这里的 URL 是格式占位示例，实际运行需替换为目标网页。本地已检查脚本语法、`--help`、缺失模型密钥和缺失依赖的提示；没有据此确认真实网页抓取或模型摘要调用成功。

### 高德天气接口的要求与已跑通记录

高德密钥需要选择 Web 服务类型。天气接口为 `GET https://restapi.amap.com/v3/weather/weatherInfo`，官方规定 `city` 传地区的 `adcode`；`extensions=all` 获取预报，`base` 获取实况。当前工具固定读取 `forecasts`，所以应保持 `all`，改变气象类型时需要同步修改解析逻辑。

早期笔记最初按代码描述将 `city` 解释成城市名称，对照官方文档后已更正为城市编码。当前本地 `tool_weather.py` 的测试参数仍是 `{"city": "北京"}`，没有在本次文档整理中修改源码；后续应将描述和示例统一到官方约定，例如 `{"city": "110101"}`。当时的终端输出没有展示当时参数，不能推断远端已修改为该编码。

当时在 AutoDL 执行 `python -m tools.tool_weather`，终端返回了北京市 2026-10-18 至 2026-10-21 的四天预报，包含日期、昼夜天气、温度、风向和风力。本次独立调用的数据请求、解析和 Markdown 格式化已由该输出确认。`Casts` 是逐日预报列表的格式化标题。

高德接口的业务状态还需要在 JSON 中检查，HTTP 请求成功并不自动代表业务查询成功。常见返回包括：

| infocode | 含义 |
| --- | --- |
| `10000` | 接口请求正常 |
| `10001` | Key 不正确或过期 |
| `10009` | Key 与服务平台类型不匹配 |
| `10005` | 请求 IP 不符合已配置白名单 |
| `10012` | 对应服务权限不足 |
| `10003` | 当日调用量超限 |

### POI 输入输出与春熙路查询记录

`POISearch.call()` 输入 Python 字典：

```python
params = {"address": "春熙路", "region": "成都市"}
```

`address` 必填，表示地点名称或地址文本，发送给高德时映射为 `keywords`；`region` 可选，用于提高该城市区域结果的优先级，当前没有传入严格限制区域的 `city_limit`。`MAX_POI_RESULTS` 从环境读取，默认请求最多 3 条。

请求接口为 `GET https://restapi.amap.com/v5/place/text`，并通过 `show_fields=business` 请求商业信息。代码读取返回 JSON 的 `pois` 列表，再执行：

```python
return truncate_text(json2md(pois))
```

因此，工具输出类型为 Markdown 字符串，不能直接用 `res["location"]` 读取字段。文本超过 5000 字符时，当前截断函数保留首尾、插入省略提示；后续程序如需稳定提取坐标，可另行设计结构化返回，当前并未做此修改。

当时在 AutoDL 执行 `python -m tools.tool_poi_search`，实际返回以下三个候选。下表是该次查询的输出快照，不代表后续每次查询的排序和字段均保持不变。

| 候选名称 | location | 含义与使用场景 |
| --- | --- | --- |
| 春熙路步行街 | `104.077774,30.655544` | 具体步行街，可作为逛街、查询周边餐厅的候选中心 |
| 春熙路（地铁站） | `104.080019,30.653389` | 地铁站，适合接驳或公共交通相关任务 |
| 春熙路 | `104.078021,30.656609` | 商圈、区域地名，应结合需求判断是否适合作为目的地 |

重要输出字段包括 `name`、`id`、`location`、`type`、`address` 和接口提供的 `business` 信息。坐标格式为经度在前、纬度在后。`citycode` 与 `adcode` 是不同字段，不能将本次的 `028` 直接当成天气接口所要求的 `adcode`。

第一条结果还返回了营业时间和评分等信息，不能将其字段直接套用到其余候选。文本搜索结果中 `distance` 为空符合该接口字段约定；周边搜索才提供相对中心点的距离。缺少 `address` 时当前工具返回错误文本，高德状态失败或没有 POI 时则抛出异常。

### 周边和路线的下一步调用方法

周边搜索输入中心坐标、半径及关键词。以下使用前述查询得到的步行街坐标，表示查询附近 1 公里内的餐厅：

```python
params = {
    "location": "104.077774,30.655544",
```

把参数放入 `tool_around_search.py` 的测试入口后执行 `python -m tools.tool_around_search`。工具参数叫 `keyword`，发给 `GET https://restapi.amap.com/v5/place/around` 时转换为 `keywords`。半径单位为米，默认 5000；返回 POI 列表并格式化为文本。

`waypoints` 在当前工具中只传入驾车分支，多个点用英文分号分隔。公交分支先对起终点进行逆地理编码，读取 `citycode`，再查询公交路线。当前路线请求未传 `show_fields=cost`，耗时与费用等扩展字段可能缺失；若需要，必须在对应 HTTP 请求参数中增加，不能仅向现有 `call()` 多传一个未透传的字段。

## 20 工具划分与 Agent 决策理解 {#chapter-20}

本节记录该阶段讨论中形成的理解和可迁移的设计方法，属于结合项目代码整理的经验，不表示已经实现了额外业务工具。

### 第一轮就使用模型的理解和生成能力

早期对流程的理解是：模型先分析旅行需求，识别需要补充的信息，调用工具获取地址、网页详情等结果，再通过多步推理形成更详细的规划。这条主线成立，补充以下边界后更准确。

- 从第一轮开始就在使用模型的理解、推理和生成能力；生成工具名称与参数也是生成能力的一部分。
- 模型生成调用请求，Python 执行器真正请求接口并返回结果；之后模型继续决定下一步。
- 初步计划可以随着反馈逐步修改，无需先生成完整行程再补齐所有资料。
- 信息来源按需求选择。地点坐标可直接查询高德，需要网页中的详细规定时再使用搜索与访问工具。
- 工具既可以查询信息，也可以计算路线或执行其他业务操作；工具结果是否来自真实服务、模拟或另一个模型，要看内部实现。

例如，用户需要春熙路附近半天行程、安排餐厅且尽量步行，可以执行：

```text
理解需求，确定需要地点、餐厅与步行路线
    ↓
poi_search 查询春熙路，读取多个候选
    ↓
根据任务选择步行街或地铁站等合适对象
    ↓
around_search 查询选定地点附近的餐厅
    ↓
route_planning 查询候选地点之间的步行路线
    ↓
模型利用反馈调整顺序并生成行程
```

这是典型调用路径，不是每个任务固定执行的流程。在这条调用路径中，教师模型承担多轮决策，工具提供可选动作；上下文、轮次、失败恢复和标签检查属于执行框架。保存调用、参数、结果与最终回答可以构成可观察的 rollout，不需要把未公开的内部思维当成必备数据。

### 按模型可独立选择的业务动作划分

工具边界从用户任务倒推。一个工具应提供模型能够判断何时使用、能准备好输入、能理解输出的动作。工具数量由任务需要决定，旅行项目的八类工具可以迁移为其他业务的另一组动作。

| 本项目中的边界 | 划分依据 |
| --- | --- |
| 地点搜索与周边搜索分开 | 前者从名称获得候选与坐标，后者从坐标查附近地点；输入和目的不同，且可以独立使用 |
| 搜索与网页访问分开 | 前者发现网页，后者读取选定网页；模型可在中间选择来源和目标 |
| 五种路线方式合为一个工具 | 核心业务问题都是从 A 到 B 的路线，输入输出相近，通过 `mode` 选择分支 |
| 公交城市代码查询放在路线工具内部 | 属于准备公交请求的固定步骤，可由程序执行 |
| 文本截断和 Markdown 转换保持辅助函数 | 属于内部处理，不需要模型独立决定何时调用 |

工具与后端 API 不要求一一对应。`visit` 内部可以抓取网页并调用摘要模型，公交规划可以内部请求多次接口，仍分别对外表现为一个业务动作。

若两个步骤总是固定连续执行、无需新的选择，而且合并能够减少无用交互，可以组合为一个工具；若步骤之间需要筛选候选，或操作用途、输入、权限与业务影响不同，分开更便于控制。应通过真实任务观察工具误选、参数错误、冗余调用和任务完成情况，再调整边界。

### 在其他项目中如何定义工具

以电商客服为例，先列真实需求，再列完成需求所需的信息与操作，可以得到：

| 用户需求 | 工具 | 输入 | 输出 |
| --- | --- | --- | --- |
| 查询订单情况 | `get_order` | 订单号 | 商品、金额、订单状态 |
| 查询运输进度 | `get_logistics` | 订单号 | 物流状态和运输记录 |
| 了解退货条件 | `search_return_policy` | 商品类别或政策问题 | 相关退货规则 |
| 提交退货申请 | `create_return_request` | 订单、商品和原因 | 申请编号与处理状态 |

查询政策与提交申请分别定义，因为用途和业务影响不同。提交类工具由后端验证权限和业务条件。每个工具的设计至少写清：名称、用途及调用时机、输入字段与类型、输出约定、失败返回、实际执行逻辑。

例如，订单状态查询的接口定义可以表示为：

```json
{
  "name": "get_order_status",
  "description": "根据订单编号查询当前订单状态。",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "description": "待查询订单编号"}
    },
    "required": ["order_id"]
  }
}
```

这份定义告诉模型如何选择和填写参数，真实查询仍需实现对应的后端函数。成功与失败应保持可识别的返回结构，并保留后续需要的订单号、地点 ID 或坐标等字段；服务失败不能伪装成查询成功。

对应到本项目，`@register_tool(...)` 负责注册，`name`、`description`、`parameters` 说明工具接口，`call()` 执行真实逻辑，返回内容被加入模型上下文。`parameters` 的声明与运行时校验是两个环节，不能仅因为声明了字段类型或长度，就认定函数已经完成全部校验。

本项目 POI 工具当前返回 Markdown，便于作为工具消息阅读；如果后续要由程序稳定地传递坐标，可设计结构化结果或明确的解析层。设计建议与当前实现应分别记录。

工具设计的验证顺序可以采用：列真实需求、拆信息与动作、确定输入输出和依赖、实现少量工具、运行代表性任务、根据失败记录调整边界。参考本次阅读的 [Agent 工具设计工程指南](https://www.anthropic.com/engineering/writing-tools-for-agents)，评价重点是模型能否正确完成任务，以及调用、耗时和上下文成本是否合理。

## 21 票务超时排查与模型切换实测 {#chapter-21}

本节记录 2026-10-18 后续项目讨论中的实际测试。API 测试来自当时的 Windows 本地环境；AutoDL 的问题依据当时保存的终端异常栈。单次耗时用于定位问题，不作为不同模型的普遍性能排名，也不能据此保证服务器链路表现相同。

### 模拟票务也需要等待远程模型生成

火车票入口为 `python -m tools.tool_train_ticket`，机票入口为 `python -m tools.tool_transport`，都应在项目根目录执行。日期、出发城市和到达城市取各文件末尾的 `params`。

当前模拟票务通过 `client.chat.completions.create()` 请求远程模型，现场生成车次、时间、价格等文本。这里的模拟描述数据内容，不表示已经在本地准备好固定结果。

| 模拟方式 | 实现 | 等待来源 |
| --- | --- | --- |
| 本地固定或随机数据 | Python 返回预设列表或本地生成结果 | 本地处理 |
| 当前票务实现 | 模型根据提示词生成模拟票务文本 | 网络、服务排队、模型推理与输出生成 |

火车提示词要求生成 6 至 15 条信息，并约束日期、站名、票价、到达时间和运行时长等关系。较长推理与生成可能增加耗时；不能仅从提示词字数推断超时原因。若仅验证 Agent 的工具衔接，可以使用明确标记的本地模拟；保留模型生成时，可先缩小输出规模，分别测量首个响应与完整结果耗时。

### 原始异常分成模型超时和脚本错误两层

当时在 AutoDL 执行火车票工具时，先长时间没有输出，之后出现：

```text
httpcore.ReadTimeout
httpx.ReadTimeout
openai.APITimeoutError: Request timed out.

During handling of the above exception:
NameError: name 'logger' is not defined
```

第一层是在等待模型 HTTP 响应时读取超时。第二层是异常处理使用了未定义的 `logger`，又触发了 `NameError`。补齐日志对象能修复第二层，但不能单独证明模型响应超时已解决。

原工具没有流式输出，结果生成后才打印。客户端配置 `timeout=60`、`max_retries=2`，失败时可能首次请求加两次自动重试，因此等待可能持续数分钟；60 秒不能理解为整个脚本的总执行上限。

该轮排查在本地修复了 `tools/tool_train_ticket.py`：定义标准日志对象，在直接运行时启用 INFO 日志，记录请求开始与响应完成，并在失败文本中保留异常类型和信息。`tests/test_train_ticket.py` 先复现原来的超时后 `NameError`，修复后成功与超时两个测试均通过。测试使用真实 OpenAI SDK 与模拟 HTTP 传输，不访问真实接口，不加载真实密钥。

修复范围是本地火车票脚本，不能推断 AutoDL 已自动更新。机票文件的异常分支仍有使用未定义 `logger` 的同类问题，本次尚未修复。

## 23 data_distill.py 的执行流程与轨迹保存 {#chapter-23}

> 本节保留首次核对时的源码快照。2026-10-18 的脚本已加入新的批量入口、断点续跑、目录创建和原子保存；本节下文的“当前”指早期快照，不能用于判断这些功能的现状。更新后的行为和数据核对见第 24 节。

本节根据当时的 `data_distill.py` 实现整理。该文件让教师模型处理旅行任务、调用工具、读取反馈并保存执行轨迹，为后续数据清洗和训练准备示范；参数训练由其他脚本负责。

### 从入口到单条任务

```text
__main__ 读取 JSONL
    ↓
arun_episode 创建 Agent 与远程模型客户端
    ↓
make_trajectory 接收单条或多条任务
    ↓
run_agent 为一条问题执行多轮循环
    ↓
call_server 请求模型 ↔ custom_call_tool 执行工具
    ↓
正常结束后保存每个 qid 的 JSON
```

当前入口只配置读取 `data/rl_buchong_left_316.jsonl`，不是自动处理全部训练和测试文件。单条输入需要如下字段：

```json
{
  "qid": "travel_001",
  "question": "帮我规划成都三日游，包含春熙路，尽量使用公共交通。",
  "answer": ""
}
```

`qid` 与 `question` 必需；`answer` 是可选的原参考答案，主要保留在结果中，没有作为初始用户消息发送给教师。自动从问题生成 qid 的语句目前被注释。

`make_trajectory()` 对问题列表逐条 `await run_agent()`，所以任务之间当前是串行处理。单轮多个工具通过 `asyncio.gather()` 并发执行，不能将这两种并发范围混淆。

### 主 Agent 与工具内部模型分别配置

| 对象 | 使用的配置或文件 | 当前职责 |
| --- | --- | --- |
| 主 Agent | `AGENT_API_KEY`、`AGENT_BASE_URL`、`AGENT_MODEL_ID` | 分析任务，生成工具调用与最终答案 |
| 工具内部模型 | `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`LLM_MODEL_ID` | 网页摘要及模拟机票、火车票 |
| 本地 Qwen 分词器 | `pretrained/Qwen/Qwen3-4B-Instruct-2507` | 估算对话 token 数量 |

初始化调用的是 `AutoTokenizer.from_pretrained()`，没有在本文件中加载 Qwen 生成模型权重。下载了 Qwen 并不表示教师回答已经由本地 Qwen 生成。

这两组远程模型参数都是项目约定的环境变量名，不需要另行申请一种名为 Agent 的专用密钥。同一服务可以供两组调用使用，也可以按角色配置不同服务。

截至本节早期源码核对，本地 `.env` 中工具内模型已为 DeepSeek；`AGENT_MODEL_ID` 仍为 `MiniMax-M2.7`，`AGENT_BASE_URL`、`AGENT_API_KEY` 尚未配置。如果也选择 DeepSeek 作为主模型，可采用下面的示例：

```dotenv
AGENT_API_KEY="${OPENAI_API_KEY}"
AGENT_BASE_URL="https://api.deepseek.com"
AGENT_MODEL_ID="deepseek-flash"
```

示例应放在已有 `OPENAI_API_KEY` 配置之后，并替换原来的 Agent 配置，避免重复项。`${OPENAI_API_KEY}` 由 python-dotenv 展开，复用现有密钥。本次仅记录了该配置方法，尚未据此改写 `AGENT_*`。

`call_server()` 还发送 `tools`、`max_completion_tokens` 以及 `reasoning_split`、`enable_thinking` 两个定制字段。更换教师服务时需要核对接口支持；第 21 节的普通聊天和票务提示词成功，不能替代这些主 Agent 参数与原生工具调用的验证。

### 主模型选择工具，执行器真正执行

`__init__()` 创建八个工具实例，建立 `self.tool_map`，并把工具定义整理为 `self.tools` 交给主模型。模型返回 `tool_calls` 后，程序解析名称与参数，再执行：

```python
raw_result = await self.tool_map[tool_name].call(
    tool_args,
    **kwargs
)
```

因此，模型选择 `poi_search` 后，执行器会进入 `POISearch.call()` 并实际请求高德。主模型负责决策，Python 负责执行；真实执行机制已写在代码中，但本次还没有完成一条端到端蒸馏任务的验证。

工具是否真实执行，与返回数据是否为真实业务事实需要分别检查。地图和搜索工具会请求对应服务；票务工具也真实请求了模型服务，但内容仍是模拟票务。

### messages 同时是上下文和执行记录

轨迹在执行过程中逐步积累，不依赖模型结束后复述。初始消息先记录系统要求和用户问题：

```python
messages = [
    {"role": "system", "content": system_prompt},
    {"role": "user", "content": question},
]
```

每轮模型返回后，先保存完整消息对象：

```python
completion, message = await self.call_server(client, messages)
completions.append(completion)
messages.append(message)
```

工具调用本身在 assistant 消息的 `tool_calls` 字段中，包含调用 ID、名称及参数。因此，即使回复正文为空，只要返回了工具调用，追加消息时仍记录了这次动作请求。

工具执行后再追加对应结果：

```python
messages.append({
    "role": "tool",
    "tool_call_id": tool_call["id"],
    "content": result,
})
```

`tool_call_id` 把结果对应到原始调用。同轮多个工具可以分别配对；当前保存顺序按调用组织，不等同于每个底层 HTTP 请求的真实完成时间顺序。

下一轮模型请求仍传入累计的 `messages`，所以模型既能看到之前的信息，程序也能在结束时导出交互记录。例如：

| 顺序 | role | 记录内容 |
| --- | --- | --- |
| 1 | system | 系统要求、日期及轮数说明 |
| 2 | user | 旅行需求 |
| 3 | assistant | 请求调用 POI，含参数与调用 ID |
| 4 | tool | 对应的候选地点与坐标 |
| 5 | assistant | 根据地点坐标请求周边搜索 |
| 6 | tool | 对应的周边地点结果 |
| 7 | assistant | 继续查询路线或输出最终答案 |

### 正常结束、保存字段与文件位置

主循环检测到同时包含 `<answer>` 和 `</answer>` 的正文时，进入正常结束流程；最终答案也是 assistant 消息，已经保留在 `messages` 中。

保存前将 SDK 消息对象转换成普通字典：

```python
"messages": [
    m.model_dump() if isinstance(m, BaseModel) else m
    for m in messages
]
```

正常落盘内容包括：

| 字段 | 含义 |
| --- | --- |
| `question` | 用户原问题 |
| `answer` | 输入中已有的参考答案 |
| `messages` | 累计的系统、用户、模型和工具消息 |
| `prediction` | 提取的最终答案 |
| `termination` | 结束原因 |
| `stats` | 主循环轮数与按工具名称统计的调用次数 |

`completions` 保存完整 API 响应对象供内存中使用，写文件前通过 `pop("completions")` 移除。文件名取输入 qid，例如 `saved/rl_buchong_left_316/travel_001.json`，通过 `json.dump(..., ensure_ascii=False, indent=4)` 写入。

当前工具计数按执行记录累计，包含失败调用；工具内部多次查询和 SDK 重试没有因此自动计为多个 Agent 动作。统计请求成本时还需要区分模型轮数、工具次数与实际网络请求次数。

### 完整轨迹的记录边界

这里记录的是 Agent 层可观察的交互过程，不能直接理解为所有内部计算和原始网络数据均已完整保留。

- 模型接口实际返回的消息字段可以保存；未返回的内部计算过程不能凭空补写。
- 工具摘要或截断后返回什么，messages 就记录什么，原始网页和全部 HTML 不会自动一并保留。
- 工具内部的多次 HTTP 请求、辅助模型调用和 SDK 重试没有全部拆成独立轨迹步骤。
- 完整 API 响应在落盘前被移除，接口用量等元数据没有全部另存。
- 当前结果没有单独保存 `self.tools` 的完整工具 Schema 和版本，后续整理 SFT 数据时需明确补充方式。
- 工具异常在此处转成简短失败文本，完整诊断信息不一定在最终消息文件中。

### 早期源码快照的边界与保存缺陷

下表记录首次核对时的源码问题；其中部分已在后续版本修复，现状以第 24 节和实际源码为准。

| 问题 | 影响 |
| --- | --- |
| `call_server()` 的 `attempts` 没有自增 | RuntimeError 分支可能反复重试，声明的尝试次数限制未生效 |
| 模型请求只捕获 RuntimeError | 其他 API 异常会继续向外传播，批量包装又只打印简短失败信息 |
| `make_trajectory()` 没有返回 result | `arun_episode()` 得到 None；正常路径的文件保存仍可能完成 |
| 轮数用尽后只追加收尾提示，未再次请求模型 | 新追加的提示没有机会用于生成最终答案 |
| 部分分支直接对 content 做标签包含判断 | 工具调用消息 content 为 None 时可能发生类型错误 |
| 10 分钟超时和上下文超限分支提前 return | 绕过末尾统一保存，失败或被迫收尾轨迹可能没有文件 |
| 保存前没有创建输出目录 | 目录不存在时写入失败，先前模型调用成本已经发生 |
| 解析失败日志使用未定义的 matches | 参数修复再次失败时可能触发二次异常 |
| `tool_args["params"] = tool_args` | 给参数字典增加自引用，不必要且可能影响后续序列化或扩展 |

默认生成预算为每轮 10000，主循环模型轮数预算为 50；上下文预算为 204800，80% 即 163840 时尝试收尾。本地 Qwen 分词器采用手工消息拼接进行估算，没有完整计入工具定义与工具调用字段，不等同于教师服务的精确 token 用量。

10 分钟只在主循环开始时检查，不是对每个正在等待的请求施加硬性总时限。上下文触发收尾的额外模型调用也没有完整反映在原循环轮数计数中，因此预算和统计仍需按实际行为修正。

## 24 从教师轨迹到 Qwen 训练数据：后续核对记录 {#chapter-24}

本节记录 2026-10-18 后续讲解、当前本地源码与数据检查，以及通过已登录的 AutoDL JupyterLab 做的只读核对。下列数量是当时的文件快照；再次上传、补跑或清洗后应重新统计。本节没有启动批量蒸馏或质量评审 API。

### 当前批量入口、保存格式与断点续跑

`data_distill.py` 现在默认运行 `single` 模式，示例问题写入 `saved/tmp/123.json`。显式使用 `--mode batch` 时，默认读取 `data/test.jsonl` 和 `data/train_expansion.jsonl`，分别保存为 `saved/test/<qid>.json` 与 `saved/train_expansion/<qid>.json`；未提供 qid 时以问题文本的 MD5 生成。任务间仍逐条执行，一轮内多个工具可并发执行。

当前 `save_episode_result()` 会创建输出目录，先写同目录临时文件，再通过 `os.replace()` 原子替换结果。默认启用 `resume`；已有文件只有在 JSON 可读、问题相同、结束状态有效、`prediction` 非空、消息角色合法且 assistant 中存在完整 `<answer>` 时才会跳过。`--no-resume` 会重新生成全部样本并可能覆盖同名文件。

| 当时服务器输入 | 已上传轨迹 | 默认跳过 | 已有但会重跑 | 缺失后新建 |
| --- | ---: | ---: | ---: | ---: |
| `test.jsonl`：100 条 | 100 | 98 | 2 | 0 |
| `train_expansion.jsonl`：1835 条 | 1831 | 1811 | 20 | 4 |

本地对应的 22 条待重跑文件均以 `exceed available llm calls` 结束，缺少完整答案标签；服务器按同一完成条件得出了相同跳过数量。默认批量运行预计处理 26 条样本，仍会消耗教师模型与工具调用成本。两个数据集使用不同保存目录，不因相同文件名互相覆盖。

服务器的 `saved/tmp/123.json` 已直接解析成功：有 35 条消息，`termination` 为 `answer`，`prediction` 有实际换行。原始 JSON 在 Vim 中出现 `\n`、转义引号和长工具返回，是序列化后的正常显示；输入没有参考答案时 `answer` 可为空，教师最终回答在 `prediction`。为人工阅读可以另导出 Markdown，但训练与清洗仍以 JSON 轨迹为准。

### 第一层：按任务用途做规则过滤

`data_clean/simple_filter.ipynb` 的第 1、3 个代码单元分别读取 `saved/train_expansion/` 和 `saved/test/`，用 `stats["turns"]`、其他工具计数、末条消息的文本与语言检测剔除：超过 13 轮、零工具调用、超限或“没有找到”、英文回答、文本不足 100 字等样本。第 6 个单元再把保留消息转换成 `data/clean/train.jsonl` 与 `data/clean/test.jsonl`。

这里的 50 是 `max_llm_calls_per_run` 设置的**主循环模型轮数预算**，不是实际工具调用次数；同轮可调用多个工具。本地训练轨迹共有 1831 条，其中 1811 条以 `answer` 结束。仅对这 1811 条成功轨迹计算：

| 指标 | P50 | P80 | P90 | P95 |
| --- | ---: | ---: | ---: | ---: |
| 模型轮数 | 5 | 7 | 10 | 13 |
| 实际工具调用次数 | 6 | 11 | 14 | 19 |

成功训练轨迹中有 1725/1811 条不超过 13 轮，因而“13 轮”大约覆盖 95% 的成功样本；若把 13 当作“工具调用次数”阈值，则口径不同。采样上限 50 可保留容错，SFT 清洗阈值应单独选择。notebook 目前在执行 `turn > 13` 过滤**之后**才计算分位数，不能用它打印的分位数反证阈值 13。`tool_calls_stat[name] += 1` 统计的是保留样本中出现过该工具的次数，不是该工具真实调用总次数。

零工具调用的示范不适合本项目的工具使用 SFT 目标；在线 RL 的失败轨迹则可作为低奖励或错误分析的材料，不应照搬 SFT 的删除规则。语言和长度判断宜针对提取出的最终 `<answer>`，而不是把末条消息中的 `<think>` 或收尾提示一起计入。

### 第二层：统一训练文本中的工具协议

教师通过 OpenAI 兼容接口返回结构化消息：assistant 的 `tool_calls` 含 `id`、`type`、`function.name`、`function.arguments`，工具回复以 `role="tool"` 和 `tool_call_id` 配对。原始轨迹需要保留这些 ID 以追踪执行；“训练文本不要 ID”指**模型可见的工具调用内容**，并非删除原始执行记录。

`simple_filter.ipynb` 已开始把结构化调用写成 `<tool_call>` 内容，把工具回复写为带 `<tool_response>` 标签的 user 消息。`data_clean/format_filter.py` 继续删掉工具调用轮夹带的普通闲聊，只保留可用的 `<think>` 与调用；将每个调用拆成独立标签，去掉 ID、type、index，仅保留 `name` 与 `arguments`；最终回答轮只保留规范的 `<answer>`。它还统计调用与回复数量，并按模式过滤无效最终答案或工具失败。

项目的 Qwen3 分词器模板（`pretrained/Qwen/Qwen3-4B-Instruct-2507/tokenizer_config.json`） 在收到结构化 `tool_calls` 时，会把每个工具渲染为一段 `<tool_call>` JSON，并把相邻的 `role="tool"` 回复渲染成 user 轮中的 `<tool_response>`。当前项目选用的是**先在 `content` 手工写这些内层标签**的路线，之后模板再补 `<|im_start|>`、`<|im_end|>` 等外层对话边界。不要同时手工写标签又保留同一次调用的结构化 `tool_calls` 字段，否则可能重复呈现。`<answer>` 是本项目的最终答案协议，不是 Qwen 工具模板的必需标签。

一轮工具调用和后续回答的目标形态如下；多个工具各有一对独立标签，最终答案另起 assistant 轮：

```text
<|im_start|>assistant
<tool_call>
{"name":"weather_search","arguments":{"city":"重庆"}}
</tool_call><|im_end|>
<|im_start|>user
<tool_response>
重庆多云，22℃。
</tool_response><|im_end|>
<|im_start|>assistant
<answer>重庆今天多云，出门可带薄外套。</answer><|im_end|>
```

当前格式脚本尚未严格达到这个目标：`normalize_tool_call()` 未把 JSON 字符串参数转换为对象，随后 `f"{tool_call}"` 把 Python 字典表示写入标签。检查 `data/final/sft_train.jsonl` 的 850 条样本发现 4979 个 `<tool_call>` 块，均可按 Python 字面量解释，但全部不能被 `json.loads()` 直接解析。例如当前内容为 `{'name': 'search', 'arguments': '{"query": [...]}'}`，目标应为 `{"name":"search","arguments":{"query":[...]}}`。推理解析器（`run_tool_loop_infer.py`） 有 `json_repair` 兜底，不能以此替代训练数据的严格 JSON 协议。修正后可从已有原始轨迹重导出派生数据，不必重新调用教师模型；若重新执行第三层 LLM 评审则会产生新的评审调用费用。

文件名 `*_clean_openai_toolcalls.jsonl` 容易误导：当前输出并非仍含原生 `assistant.tool_calls` 字段的 OpenAI 消息，而是含 Qwen 风格文本标签的对话。`format_filter.py` 的默认输入与输出只针对 `test.jsonl`，训练集需显式给路径。转换后工具回复是 user 消息，但默认“空工具消息”规则检查 `role="tool"`，因此该项在当前转换结果上无法命中；其校验函数也按原生 `tool_calls`/`tool` 角色检查，不能直接证明文本标签格式合法。

### 第三层：模型评审与留样

`data_clean/quality_filter.py` 默认读取格式清洗后的测试 JSONL，从中提取问题、最终 `<answer>` 和工具轨迹摘要，调用评审模型。评分提示词在 `prompt.py`：任务相关性、完整性、事实安全性、工具合理性和格式质量分别评分，并要求模型返回总分、`pass`、`borderline` 或 `fail` 以及简短问题说明。默认保留 `pass,borderline`，写出逐条评审结果、汇总报告和保留的原始对话行。

该脚本默认最多 20 个并发请求、每条最多尝试 2 次；`--max-samples` 可限制试跑量。这里会实际消耗评审模型 token。Python 代码没有重新按权重计算并验证模型返回的 `overall_score` 与 `verdict`；而提示词拿到的是工具调用摘要与失败次数，并非完整工具返回，因此具体票价、时间等事实仍需额外核验。

### “黄金数据集”的两种用途与现有划分

模型评审后的 `pass` 只是高质量候选，不等于已经核实的金标准。当前 `data/final/train_clean_judged_filtered.jsonl` 有 1081 条，拆为 SFT 881 条（训练 850、验证 31）和 RL 200 条；`test_final.jsonl` 有 80 条，与训练侧的 ID 和原始问题文本均无完全相同项，但还不能据此排除语义近重复。

`train_rl.sh` 目前将 `RL_DATASET` 与 `ANSWER_JUDGE_GOLD_DATASET_PATH` 默认指向同一个 `data/final/rl.jsonl`。奖励插件（`ms-swift/examples/train/grpo/plugin/tooluse_reward_parser_aligned.py`） 按完整问题文本查找第一条非工具反馈的 user 消息和最后的 `<answer>`；当时的 200 条均能提取答案。这里的“gold”实际是教师示范参考答案，可作为 RL 奖励的伪金标准；若问题文本不一致或参考答案缺失，该条评审奖励返回 0，而评审奖励在当前课程权重中占 0.60、0.70 或 0.75，影响较大。

如需建立更可靠的 RL 参考集，应核验每条教师答案的约束、工具证据、时间敏感信息和可接受的不同路线，再保存为单独文件；问题文本须与 RL 输入完全匹配。最终评测金标准则应在独立测试任务上人工或用可靠规则核验、记录信息来源与核验日期、冻结版本，不能回流训练。现有 80 条测试题可以作为核验起点，但 LLM Judge 的自动通过并不使其自动成为最终金标准。

本节只记录核对结论；尚未修改格式清洗脚本、派生训练数据或已有模型权重。

### 两条旧测试失败轨迹：澄清后持续空转

本地旧 JSON 中的两条失败轨迹与 10 月重跑日志中失败的两条 QID **不同**。这两份旧轨迹都达到 50 轮模型调用预算，没有完整 `<answer>`，`prediction` 为 `No answer found.`；没有证据表明是工具额度耗尽。

| 旧样本 | 任务缺失的信息 | 实际轨迹 |
| --- | --- | --- |
| `7c73d0d0...`（`saved/test/7c73d0d06667eece151c8a7fadb35e14.json`）：广发这附近有啥好玩的游乐场 | “广发”指哪个地点、位于哪座城市 | 搜索一次后仍无法定位；之后大量轮次重复要求用户澄清，最终 50 轮、仅 1 次工具调用 |

缺失必要信息时向用户澄清本身是合理动作，失败在于批量 Agent 没有真人回复却继续把同一上下文送给模型。`data_distill.py` 在第 50 轮后追加“停止调用工具并给最终答案”的 user 消息，但主循环随即结束，没有再次请求模型；因此该提示无法挽救这两条结果。对无法安全推断出发地或具体位置的问题，应补全任务后再蒸馏，或在第一次澄清后结束并标记 `needs_clarification`，不要让模型空转到预算上限。

### 可推广的无进展检测经验

“空转”不等于轮数多。长轨迹如果持续获得新证据并推进规划，仍可能有价值；空转的特征是多轮之后**没有新增事实、有效动作或明确终止**。需要至少区分以下类型：

1. **澄清循环**：任务缺出发地、日期或“附近”的参照位置，模型反复向无真人回复的批处理环境提问。
2. **工具失败循环**：超时、短期限流、参数错误或空结果后，以相同参数反复调用同一工具。一次工具失败不构成空转。
3. **搜索无增益循环**：工具有返回，但多次结果仍不包含所需事实，模型只改写近似 query 而不换策略或说明证据不足。
4. **协议修复循环**：工具参数或 `<tool_call>` 标签解析失败，模型反复输出相似的错误格式。

建议在每轮记录工具名与参数的规范化签名、结果状态和新增证据；对连续无增益或重复签名设可配置的小上限，按失败类型有限重试、换工具、澄清或明确结束。最大模型轮数只是成本保险丝，不能代替任务进展判断。日志也应在工具执行**之前**记录开始事件，在返回或失败后记录耗时与原始异常类别；再配合批次心跳、进程退出码和实例事件，才能把模型空转、工具长等待和外部中断区分开。

本节记录分析与改进建议；尚未修改 Agent 的停止逻辑或重跑这两条旧测试样本。

## 26 SFT 冷启动的算力预算：事前估算与实测校准 {#chapter-26}

本节针对 `train_sft.sh` 的 Qwen3-4B-Instruct-2507、BF16、LoRA rank 128、`all-linear`、`max_length=32768`、每卡 batch 1、梯度检查点和 2 epoch。脚本将 `CUDA_VISIBLE_DEVICES` 与 `NPROC_PER_NODE` 设为 4，表示使用四卡数据并行，不代表该模型训练的最低卡数。[PyTorch DDP](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html) 在各卡保留模型副本；单条长样本的显存需求不能除以 4。

### 先离线统计样本长度，再估训练规模

训练前可用本地 Qwen 分词器将 `data/final/sft_train.jsonl` 按当前对话格式编码，统计长度分布。2026-10-20 的离线检查：850 条样本的近似平均长度为 10,435 token、P95 为 20,808、最长为 49,476；其中 7 条超过 32,768。排除这 7 条后，843 条的近似平均长度为 10,198，两轮合计约 **17,193,274 个输入 token**。该统计用手工拼接的对话边界，接近但不保证与 Swift 模板逐 token 一致；最终保留条数应以训练时的预处理日志为准。训练时被 loss mask 的 system、user 和工具返回仍作为上下文参与计算。

全局 batch 为 `GPU 数 × 每卡 batch × 梯度累积步数`；当前四卡配置是 `4 × 1 × 1 = 4`。总更新步数可先估为 `有效样本数 × epoch ÷ 全局 batch`，但分布式采样、尾批及数据过滤会影响精确值。`num_train_epochs=2` 是起始训练预算，不是由“4B 参数”推导出的固定值；应按验证 loss、工具调用格式和端到端任务质量选择检查点，测试集保持独立。

### 单卡显存：静态下限不能代替峰值

估算式为 `峰值显存 ≈ 冻结基座权重 + LoRA 权重/梯度/优化器状态 + 激活 + 临时张量 + CUDA 开销`。[Transformers 显存说明](https://huggingface.co/docs/transformers/model_memory_anatomy) 将这些部分分开讨论，尤其指出激活随 batch 与长度变化。

| 当前配置的可预估部分 | 粗略计算 | 解释 |
| --- | ---: | --- |
| 冻结基座 BF16 权重 | 约 `4.02×10⁹ × 2 B ≈ 8.0 GB` | LoRA 不为冻结基座保存 Adam 状态 |
| LoRA 可训练参数 | `A ≈ 264,241,152` | 36 层、rank 128，作用于 q/k/v/o/gate/up/down 投影；每个矩阵新增 `r×(输入维度+输出维度)` 参数 |
| LoRA 训练状态 | 若按 FP32 权重、梯度及两份 Adam 状态，`16A ≈ 4.2 GB` | 实际值取决于适配器和优化器 dtype |
| 静态部分小计 | 约 **12 GB** | 只是下限，不能据此选择 12 GB 显卡 |

例如 batch 1、32,768 token、隐藏维度 2,560、36 层时，`batch × 长度 × 隐藏维度 × 层数 × 2 B` 约为 **5.6 GiB**，仅表示每层保留一份隐藏状态的量级；若完整物化 `batch × 长度 × 词表大小 × 2 B` 的 logits，词表 151,936 又是约 **9.3 GiB**。梯度检查点、注意力与交叉熵实现会改变实际峰值，不能把这两个数机械相加当作最终需求。应以最长有效样本的短试跑读取 `torch.cuda.max_memory_reserved()`，再留显存余量。

### 事前计算训练量与单卡时长

令 `P≈4.02×10⁹` 为冻结基座参数量，`A≈2.64×10⁸` 为 LoRA 参数量，`D≈1.719×10⁷` 为两轮总输入 token 数。一次密集矩阵前向约为每 token `2P` FLOPs；反向传回输入梯度再约 `2P`。全参数训练还要计算基座权重梯度约 `2P`；LoRA 冻结基座但需要计算适配器梯度。因此 `4PD≈2.77×10¹⁷` 至 `6PD≈4.15×10¹⁷` FLOPs 可作为主要矩阵计算的粗范围，更贴近此配置的估计为：

`F ≈ (4P + 6A)D ≈ 3.04×10¹⁷ FLOPs`。

该式未完整包含长序列注意力、归一化、临时操作、数据处理与验证保存。训练时间需再除以**持续有效算力**：`T≈F/(GPU 标称 BF16 FLOPs/秒 × 利用率 u)`。NVIDIA 为 [RTX PRO 6000 Blackwell Server Edition](https://www.nvidia.com/en-us/data-center/rtx-pro-6000-blackwell-server-edition/) 列出的 BF16 Tensor Core 峰值是 1 PFLOP/s；若仅**假设**本任务的端到端利用率为 3%～5%，上式中的主要矩阵计算约需 1.7～2.8 小时。`u` 不是厂商规格，也不是事前已知常数；增加未计入的操作与运行开销后，**2～5 小时只是单卡租用预算区间，不是完成时间承诺**。若实际租到 Workstation、Max-Q 或限功率版本，不应直接代入 Server Edition 的峰值。

### 用一次短试跑收紧预算，再与历史实测分开报告

完整开跑前，选覆盖 P95 与最长有效长度的少量样本，做约 10～20 个更新步，记录稳定后的秒/步与单卡峰值显存，然后用 `预计总步数 × 秒/步` 外推训练循环时长，并另留初始化、评估和检查点保存时间。单卡若想维持原四卡的全局 batch 4，可将可见 GPU 与进程数设为 1、梯度累积设为 4；这会顺序执行四个 microbatch，并不把单条样本的显存乘以 4。

独立于上述事前公式，项目已有一次四卡训练的 `saved/output/qwen3_4b_sft_4gpu/v8-20260511-142452/logging.jsonl`：843 条有效样本、420 次更新、训练循环 3557 秒、记录的显存峰值约 **46.35 GiB／卡**。这是**该次软硬件与数据条件下的实测校准值**；日志未明确记载旧 GPU 型号，不能把四卡时长直接当作新 RTX PRO 6000 的单卡速度。按实测峰值再留约 20% 余量是 55.6 GiB，48 GB 卡很紧，64 GB 以上更稳妥；若换数据、GPU、Swift/PyTorch 版本或注意力实现，需要重测。

资源预算只回答“能否装下、约需多久”。训练数据中的 `<tool_call>` 严格 JSON 问题仍须按第 24 节检查；增加算力或 epoch 不会自动修正错误示范。

### 27.01 怎样用一分钟介绍项目 {#question-27-01}

**简洁口述：** 本项目以旅行规划为业务场景，基于 Qwen3-4B-Instruct-2507，通过 LoRA SFT 冷启动和在线 GRPO，提升 Agent 在多约束任务中的信息获取、工具编排和方案生成能力。工具侧接入高德 POI、周边搜索、路线规划及网页搜索、访问；数据侧覆盖种子扩展、教师轨迹采集、格式规整和质量筛选。训练采用 vLLM rollout 与分布式训练分离的部署方式，最后在同题任务上比较 Instruct 基线、SFT 和 RL 的调用轨迹与最终答案质量。

**口径：** 模型是“Qwen3 的 4B”，不是“Qwen 34B”。当前脚本配置 SFT 四卡、RL 六卡训练加两卡 rollout；GPU 的实际型号以实例与日志为准，不能仅凭脚本声称已在八卡 RTX 6000 上完成实验。航班、火车票等工具当前有模型模拟成分，不能把所有工具都表述成真实票务接口。多轮不等于每轮只调用一个工具，“数十次调用”需用轨迹计数证明。

依据：`train_sft.sh`、`train_rl.sh`、`rollout.sh`，工具来源见第 19 节。

### 27.02 训练整体链路是什么，训练的到底是谁 {#question-27-02}

**简洁口述：** 教师先在工具环境中生成示范，经清洗后用于学生 SFT；在线 RL 再让当前策略执行任务、获得工具反馈，采集多条轨迹，计算奖励与组内优势，更新策略参数，并同步到采样端。推理时只运行“问题—模型动作—工具反馈—后续动作—最终答案”的循环。

模型学习的是工具选择、参数生成、反馈利用和结束策略；工具函数本身不需要可微，也不通过 GRPO 更新。SFT 学习固定示范，在线 RL 使用当前策略产生的新交互。“在线”不等于必须连接互联网，也不等于采样与训练必然异步重叠。

### 27.03 两个多轮文件是否主要为了推训一致 {#question-27-03}

**简洁口述：** `run_tool_loop_infer.py` 是独立推理、评测入口；`ms-swift/examples/train/grpo/plugin/tooluse_multi_turn_scheduler.py` 把多轮工具交互接入 Swift rollout。两者共用工具解析、参数提取、工具加载和部分提示词处理函数，减少训练采样与实际推理的协议偏差。

scheduler 还负责请求状态、环境反馈、异常恢复和终止条件。当前两边的纠错消息角色、重复调用判断、重试与收尾规则仍有差异，因此应说“对齐关键规则”，不能说完整状态机已经完全一致。

### 27.04 scheduler 怎样注册到 Swift，怎样改造 {#question-27-04}

**简洁口述：** 自定义类继承 `MultiTurnScheduler`，在 `multi_turns['travel_tool_loop']` 中注册；启动时用 `--external_plugins` 导入文件，用 `--multi_turn_scheduler travel_tool_loop` 选择类。框架创建实例，并传入推理引擎和最大轮数。

原独立循环拆成三个扩展点：`run()` 初始化后复用父类循环；`check_finished()` 判断长度、轮数和答案；`step()` 解析动作、执行工具、追加反馈。每条请求的计数与状态放在 `infer_request.data_dict`，返回更新后的请求和 `rollout_infos`。这是 Agent 交互调度，不是 vLLM 的 GPU 请求调度器。

依据：插件注册与实现（`ms-swift/examples/train/grpo/plugin/tooluse_multi_turn_scheduler.py`）、框架实例化（`ms-swift/swift/pipelines/infer/rollout.py`）、多轮基类（`ms-swift/swift/rollout/multi_turn.py`）。

### 27.05 rollout.sh 有什么用，是否已经是异步训练 {#question-27-05}

**简洁口述：** `rollout.sh` 启动专门的策略采样服务，加载模型与旅行 scheduler，执行多轮生成和工具交互；`train_rl.sh` 请求轨迹、计算奖励与 loss、更新参数；`infer.sh` 用于模型推理和测试。

当前 `vllm_use_async_engine=true` 指推理引擎的异步请求接口。训练脚本未开启 `async_generate`，本地 Swift 还明确禁止其与多轮 scheduler 同时使用。当前可以确认训练与采样服务分离，不能直接宣称已实现完全异步的采样—更新流水线。

依据：`rollout.sh`、训练参数限制（`ms-swift/swift/arguments/rlhf_args.py`）。

### 27.06 怎样保证蒸馏和在线训练的环境稳定 {#question-27-06}

**简洁口述：** 从服务方和调用方两边保证。服务方关注可用性、限流、超时、输出格式和错误分类；调用方负责参数校验、有限重试、轮数与上下文预算、解析容错和明确终止。整条链路还要记录请求、回包、耗时与结束状态，区分模型错误和环境故障。

长上下文应保留原始需求、关键约束、已验证事实和必要调用关系。按字符截断、按 token 截断与语义压缩是不同措施；当前代码有预算和工具回包截断，不能据此声称已有自动语义压缩。恢复操作还需考虑是否重复修改环境。

面试可结合第 25 节的限流、长尾任务和澄清空转案例；没有执行完成记录时，不要把应用日志停止直接归因于 OOM 或 API 额度。

### 27.07 没有在线 API 的本地工具怎样训练 {#question-27-07}

**简洁口述：** scheduler 调用的是本地工具类的 `call()`，内部可以是 Python 函数、SDK、命令行、软件自动化或 GUI 操作。模型仍然输出工具名与参数，执行器运行后返回观察，训练框架根据轨迹和任务结果更新模型。

有状态任务需要每条轨迹独立的环境、工作目录或软件会话；同题多个候选从相同快照开始，轨迹内保持状态、轨迹之间隔离，并实现 `reset/step/close`。当前工具加载每次新建对象，尚不能代替这套环境生命周期。执行环境位于 rollout worker 所在机器；Linux 训练机调用 Windows 软件时，可由 Windows 执行 worker 提供内部桥接，不要求软件已有公网 API。

奖励应核验实际产物、测试或仿真指标，不能只相信模型声明。只有静态日志时可先做 SFT；交互式在线 RL 还需要真实环境或可信模拟器。依据：工具执行器（`ms-swift/examples/train/grpo/plugin/tooluse_multi_turn_scheduler.py`）、Swift Env 接口（`ms-swift/swift/rollout/gym_env.py`）。

### 27.08 为什么清洗数据，三阶段怎样讲 {#question-27-08}

**简洁口述：** 清洗同时保证协议可学和内容可信。第一阶段规则过滤明显异常轨迹；第二阶段统一调用、反馈与答案格式；第三阶段用 Judge 评价需求覆盖、工具使用合理性和答案质量，保留逐条评审与汇总记录。

三阶段是逻辑分类，不要求恰好三个独立脚本。当前流程见 `data_clean/simple_filter.ipynb`、`data_clean/format_filter.py` 与 `data_clean/quality_filter.py`。已有报告记录输入 1698 条，经规则与格式处理保留 1143 条，再经质量筛选保留 1081 条；这是存档报告，不能保证当前脚本未经修正就能严格复现所有校验口径。

冷启动可优先选择干净的成功示范；RL 的失败轨迹可以提供低奖励与恢复学习信号，不能照搬全部删除。训练与测试应在种子扩展前隔离。

### 27.09 格式清洗具体做了哪些工作 {#question-27-09}

**简洁口述：** 按本项目协议分开工具 action 和最终回答；删除不承担有效动作的闲聊轮，保留必要思考与上下文；规范 `<answer>` 内的最终内容；筛选空回包和失败后编造确定结论的示范；统一多工具调用、参数和反馈的表示方式。

目标工具调用是 `<tool_call>{"name":"search","arguments":{"query":["杭州天气"]}}</tool_call>`；同轮多个工具分别闭合标签。这个选择应与模型模板一致，不代表 JSON 列表或其他协议天然错误。“减少协议表示歧义”比“压缩模型输入空间”更准确。

一致性看的是最终渲染后的角色与协议语义，底层原始消息不必逐字段相同。当前训练数据仍有 Python 字典表示与字符串参数问题，不能声称严格 JSON 验收已完成，详见第 28 节。

### 27.10 loss 正常下降，为何工具调用仍没学会 {#question-27-10}

**简洁口述：** loss 下降只能证明被监督的目标在改善。应沿“原始消息—预处理—模板文本—input_ids—labels/loss_scale”逐层检查，确认工具名、参数和必要边界实际进入监督，再通过端到端工具调用验证。

必须区分：工具字段未被模板渲染，根本没进入 `input_ids`；已经进入输入，但对应 `labels=-100` 或 loss 权重为零。最终答案仍被监督时，整体 loss 可以下降，不能由此证明工具动作训练正确。

不能笼统说“Swift 不支持 OpenAI 工具格式”。应描述具体版本和适配链路未把字段转换成模板需要的目标文本。本地有 Agent 标准格式与模板转换机制；Qwen tokenizer 也有结构化工具调用渲染逻辑。历史漏监督案例需有编码与标签对照证据，本次没有重跑旧数据来证明该历史根因。

依据：Agent 数据与监督说明（`ms-swift/docs/source_en/Instruction/Agent-support.md`）、模板预处理（`ms-swift/swift/template/base.py`）。

### 27.11 为什么训练文本不保留随机 tool_call_id {#question-27-11}

**简洁口述：** 模型主要学习工具名和参数，随机关联 ID 通常不必成为预测目标。训练文本可只保留 `name/arguments`，原始轨迹和运行时仍保存 ID，用来关联调用与回包，特别是并行调用。

“ID 全无意义、全局删除”不准确；生成 ID 的主体也取决于服务端或执行器，不能一概说由 SDK 后处理添加。`type`、`index` 等字段是否进入目标文本由选定协议决定，不能推广成所有工具系统都应删掉它们。依据：原始执行与回包配对（`data_distill.py`）。

### 27.12 数据质量 LLM Judge 怎样设计 {#question-27-12}

**简洁口述：** 输入是 query、工具轨迹摘要和 answer，摘要补充调用数量、工具种类与失败情况。按任务相关性、完整性、事实安全性、工具使用合理性和格式质量五维评分，要求输出结构化分数、等级和问题说明；默认保留 `pass` 与 `borderline`，剔除 `fail` 等未保留等级。

当前 DATA_JUDGE_PROMPT（`prompt.py`） 每维 1—5 分，要求按 `0.30/0.25/0.20/0.15/0.10` 加权、乘 2 后取整；`pass>=8`、`borderline=6或7`、`fail<=5`。五维是业务 rubric，不是统一行业标准。程序按返回的 verdict 留样，并未重新核算总分与等级。

当前摘要没有完整工具返回，也未完整统计参数校验成功率，不能声称事实均已核验。裁判模型通过 `JUDGE_MODEL_ID` 等配置选择，讲解中的特定型号需要当次调用记录支撑。格式清洗 Judge、RL 奖励 Judge、最终 A/B 评测 Judge 是三个不同用途，不能混为一个评分器。

### 27.13 教师模型怎样选，为什么选它 {#question-27-13}

**简洁口述：** 结合垂直任务效果、整条轨迹效率和有效样本成本选型。在相同任务与工具预算下比较协议遵循、有效轨迹率、工具选择、答案质量、长尾耗时和限流情况，再看清洗后每条有效轨迹的总成本。教师输出长度和学生的可学习性也要考虑。

`有效轨迹单价 = 模型与工具总费用 / 清洗后可用轨迹数`。几十条小样本可以做初步验证，但不能代表所有任务。没有实际对比时，应说“拟采用的验证方案”，不能说已经验证某模型排名靠前或“肯定最强”。公司接口可用也不等于实际使用过。

当前教师调用读取 `AGENT_MODEL_ID`；`data_distill.py` 中加载 Qwen tokenizer 不能证明教师就是 Qwen。历史教师、评审与辅助工具模型分别核对日志和配置，不能照搬转写里的商业型号。依据：教师请求入口（`data_distill.py`）。

### 27.14 如果优化清洗过滤，还会怎么做 {#question-27-14}

**简洁口述：** 我会增加难度分层和质量加权。难度结合调用次数、依赖深度、约束数量和上下文长度划分，再通过分层采样、课程学习逐步增加复杂任务；质量则对保留样本分配不同的 SFT loss 权重或采样权重，降低边界样本影响，同时保持场景覆盖。

这是建议，当前不能声称已实现并取得增益。难度与质量分别标注；调用多也可能只是低效，不能当作唯一难度指标。若用次数辅助分层，可取 `1—3、4—10、>10`，避免边界重叠，并区分工具次数与模型轮数。明显错误仍过滤，不能只降权。

添加 `weight` 字段不会自动生效；需接入采样或损失，例如 `L=sum(w_i*L_i)/sum(w_i)`，其中样本损失的 token 归一化口径应一致。清洗决定是否可用，分层与加权决定如何使用。样本难度课程、SFT 质量权重、RL 子奖励课程是三件事。

### 27.15 为什么先做冷启动，不做行不行 {#question-27-15}

**简洁口述：** 可以不做。当前项目选择先 SFT，让学生适应工具协议、反馈利用与多轮收尾，再用在线 GRPO 优化策略和答案质量。主要考虑格式控制、探索效率和有效训练信号，减少把预算消耗在无效交互上。

`Qwen3-4B-Instruct-2507` 已有指令训练背景，不做项目 SFT 不等于完全从零探索。SFT+RL 是常见路线，不是所有 Agent 的强制标准。没有同预算的“直接 RL 与 SFT+RL”消融，就不能声称已经证明冷启动必需或一定避免崩溃。

[ZeroTIR 原始研究](https://arxiv.org/abs/2505.07773) 探索不使用监督工具示范、通过 RL 学习生成和执行 Python 代码，主要面向数学任务。不能据此泛化成所有工具环境，也不能反向断言直接 RL 的上限普遍远低于 SFT+RL。

### 27.16 冷启动中有哪些值得讲的提示词适配问题 {#question-27-16}

**简洁口述：** 同一个 system prompt 在教师与学生模型上可能表现不同。遇到混合输出、标签不闭合、重复调用或不收尾，先固定任务、解码参数与工具反馈，排除数据和模板问题，再精简重复约束、明确 action 边界、增加最小示例，并统一训练与推理协议。

效果用格式正确率、有效调用率、终止率和任务完成率验证。不能只因模型小就把错误归因于 prompt，也不能声称所有大模型一定更能理解冗长规则。当前 COLDSTART_SYSTEM_PROMPT（`prompt.py`） 与 推理提示词简化函数（`run_tool_loop_infer.py`） 有明确协议，但改提示词带来的因果收益仍需对照实验。

### 27.17 六项奖励怎样定义，前五项是不是规则 {#question-27-17}

**简洁口述：** 奖励类继承 `ORM`，实现 `__call__`，输入批量输出及轨迹信息，返回同序的 `List[float]`，并注册到 `orms`。当前先统一解析完整会话，将最后一个 assistant 轮作为最终轮，其余作为中间轮，再计算六项子奖励。

| 子奖励 | 当前关注点 | 原始输出范围或取值 |
| --- | --- | --- |
| Process | 规范调用、过程异常、提前回答等 | `[-1,0.3]` |
| Tool Schema | 工具名、参数为字典、调用结构比例 | 上下界 `[-1,0.25]` |
| Answer Tag | 最后回答的标签、长度与多余内容 | `{-1,-0.2,0,0.3}` |
| Stage | 工具阶段与回答阶段的关系 | `{-1,-0.8,-0.5,-0.4,-0.1,0,0.3}` |
| Efficiency | 唯一调用比例、重复和超过十次的数量 | `[-1,0.3]` |
| LLM Judge | 最终答案的匹配度、可行性、细节与清晰度 | `[0,1]` |

前五项是基于解析与统计的规则评分，不是五个训练出来的奖励模型；其中 Answer Tag 是最终输出格式，不能全称为“中间过程奖励”。每条轨迹最终汇总一个标量，没有逐工具步骤独立的奖励优势或 PRM。Schema 检查也不等于完整 JSON Schema 校验或 API 成功验证。

依据：奖励插件（`ms-swift/examples/train/grpo/plugin/tooluse_reward_parser_aligned.py`）。Schema 基础公式 `-0.2+0.45*q` 中 `q<=1`，因此虽然写了 `min(reward,0.3)`，实际正向上限仍为 0.25。

### 27.18 为什么负到 -1，正向只到 0.3，不对称合理吗 {#question-27-18}

**简洁口述：** 这是手工选择的评分尺度，没有必须对称的要求。它体现对规则达标的小额正分与违规扣分，但是否过重，应看加权分差和组内优势，不能只比较零点两侧的范围。

GRPO 使用 `A_i=(R_i-mean_group(R))/(std_group(R)+eps)`。同组都是负分时，较高的负分仍能得到正优势。将某项统一加 0.35 后范围变成 `[-0.65,0.65]`；若固定权重且没有新增截断，加权总分只平移常数，组内优势不变。

例如某规则权重 0.1，得分从 0.3 变成 -1，会令总分降低 0.13；Judge 权重 0.6、质量提高 0.2，只增加 0.12。处罚是否压过质量收益，应结合真实样本排序检查。原始 reward 的范围也不约束归一化后 Advantage 的范围。

### 27.19 六项怎样组合，课程权重怎样变化 {#question-27-19}

**简洁口述：** 当前 `ParserAlignedCurriculumReward` 先调用六个评分器，再按训练步数选择权重，加权成每条轨迹一个总分。答案质量从前期就占主要权重，后期进一步提高；规则项保留一定权重，维持交互与输出约束。

以下以 `train_rl.sh` 的默认 200 步为准，顺序固定为 Process、Schema、Answer、Stage、Efficiency、Judge：

| 步数 | 六项权重 |
| --- | --- |
| 0—29 | `[0.10,0.10,0.05,0.05,0.10,0.60]` |
| 30—69 | `[0.05,0.05,0.05,0.05,0.10,0.70]` |
| 70—199 | `[0.05,0.05,0.05,0.05,0.05,0.75]` |

环境变量会覆盖插件内置默认值，不能混用两套配置。`_normalize_weights()` 只是把权重变成比例，不是对奖励做组内归一化。多数规则正分封顶约 0.3，不意味着范围内任意值都可达到。

以六项上限计算，上述三阶段的总分上界分别为 `0.715、0.7875、0.8225`；末尾 `clip[-1,1]` 不代表总分一定能到 1。权重变化本身会改变总分曲线，因此不能仅凭曲线上升判断能力改善。动态权重是项目选择，不是所有 RL 必需条件。

### 27.20 一般怎样按任务设计奖励 {#question-27-20}

**简洁口述：** 先定义任务成功标准，再为可验证事实、开放式质量和执行成本选择信号。程序检查预算、时间、产物和执行状态，Judge 评价需求匹配、方案合理性和表达。过程奖励尽量奖励有效进展，避免直接奖励动作数量。

关键约束可以通过总分上限、条件奖励或单独验收体现，避免大量小项补偿关键失败；不可行任务和合理澄清也要有完成标准。范围、方差、相关性与权重共同决定贡献。训练前用删证据、改错误事实、增加无关调用等样本检查评分排序，训练后再以独立任务质量验收。

当前 Process 仍含按调用次数加分的项，不能把“不要奖励次数”说成已经全面落实。规则评分也可能被利用，LLM 评分同样可能有偏差。

### 27.21 多项 reward 会一起涨吗，一项不涨怎样单独优化 {#question-27-21}

**简洁口述：** 不保证。模型根据组合信号更新，共享参数使目标可能协同、冲突或饱和。先区分满分饱和、评分失败、组内同分、信号太弱、缺少成功探索和目标冲突，再决定加权、补数据还是修改指标。

有区分信号时，可从同一 checkpoint 做短程权重消融，并监控其他能力底线；同题某项全为零或同分时，提高权重仍不会创造该项的组内区分信号。若无法采到高质量策略，应补示范或调整任务分布；若效率与质量冲突，可在满足核心任务条件后才给效率正分。

比较原始子奖励、违规率、任务成功率、组内标准差与评分失败率，不只比较加权均值。KL 约束和数据混合可以降低退化风险，但不能保证所有维度都不下降。

### 27.22 子奖励分别归一化、再组合优势怎样做 {#question-27-22}

**简洁口述：** 每题采样 G 条轨迹，每条算 M 项分数，形成 `[B,G,M]`。分别沿同题候选维度计算各项均值、标准差，得到各项相对优势，再按业务权重求和，最后对整个 batch 的综合优势标准化，送入策略 loss。

`A_ij=(r_ij-mu_j)/(sigma_j+eps)`；`A_i=sum_j(w_j*A_ij)`。当前普通配置是“先合奖励、再归一化”，两者顺序不同。

例如同题三条轨迹的质量分 `[0.6,0.8,1.0]`、效率分 `[0.3,0.1,0.2]`，按样本标准差分别归一化为 `[-1,0,1]`、`[1,-1,0]`。权重 0.8/0.2 时，组合优势为 `[-0.6,-0.2,0.8]`；若 batch 只有这组，再标准化约为 `[-0.832,-0.277,1.109]`。

本地 GRPO Trainer（`ms-swift/swift/rlhf_trainers/grpo_trainer.py`） 已有 `scale_rewards='gdpo'` 分支。但当前课程插件只向 Trainer 返回一列混合分，单改开关无法让它看到六项；需要分别启用六个已注册子奖励，再配置 `reward_weights`。原课程变量不会自动调度新的 Trainer 权重，需另行实现。奖励无差异时仍没有该项优势，微小评分噪声也可能被放大。

算法来源：[GDPO 原始论文](https://arxiv.org/abs/2601.05242)。这是可选改进，不是当前训练已启用的设置。

### 27.23 本项目是不是 Rubric-based RL，与 RLVR、GRPO 什么关系 {#question-27-23}

**简洁口述：** 广义上包含 rubric-based RL 成分，更准确地说是规则奖励、参考答案辅助的多维 LLM Judge 与 GRPO 的组合。Rubric 是评分标准，Judge 是评分执行者，GRPO 是策略更新方法，三者不冲突。

当前内容 rubric 就在第六项 Judge：匹配度、可行性、细节与清晰度。它是通用四维评分，并未逐题生成原子检查清单，且依赖参考答案；不能直接等同于 [Rubrics as Rewards](https://arxiv.org/abs/2507.17746) 的全部具体设计。

“没有唯一正确答案”不代表不能有参考答案，也不代表没有客观约束。前五项能验证格式和行为，不等于已验证真实任务成功的 RLVR；预算、时间、测试和环境结果还需可靠验证。

### 27.24 全部换成 LLM rubric 打分，去掉规则合适吗 {#question-27-24}

**简洁口述：** 可以作为消融方案，但应区分删除数值奖励与删除执行校验。可以重写粗糙的次数或阶段奖惩，用完整轨迹 rubric 评价策略合理性；参数可解析、工具真实执行、最终产物是否正确，仍由程序和环境提供证据。

当前 Judge 只接收问题、最终答案和参考答案，不接收完整工具反馈。只删除前五项，就会显著减少过程监督；要替代需加入任务细则、调用回包、环境状态与证据定位，再由代码确定性聚合。scheduler 的 tool-first、轮数和结束逻辑不会因删除 reward 自动消失。

建议比较“当前混合奖励”“完整轨迹纯 rubric 奖励”“精简客观验证加 rubric”三组，在同一评测集上看任务成功、事实或产物正确性和调用成本，避免只由训练时同一个 Judge 验收。[相关奖励欺骗研究](https://arxiv.org/abs/2605.12474) 表明评分上升不必然对应更广泛的质量改善。

### 27.25 八条训练 Trick 哪些值得采用 {#question-27-25}

| 经验 | 口述与适用边界 |
| --- | --- |
| 先 rollout smoke，再正式训练 | 先检查闭环与奖励，再做少量参数更新，验证监督、反传与权重同步；smoke 通过不等于效果已验证 |
| reward 留上升空间 | 关注真实质量与组内区分度，不能靠压低分数制造“空间”；格式满分也可能是正常收敛 |
| 不奖励工具调用次数本身 | 奖励任务进展和证据，冗余与实际成本另计；复杂任务需要较多调用并不等于低效 |
| Judge 只评 final answer | 是可选分工；结构规则不能覆盖工具选择、反馈利用和恢复策略的语义质量 |
| system prompt 不与 reward 冲突 | 同时核对模板、解析器、scheduler 和预算；容错可解析不等于规范格式 |
| 工具失败单独建模 | 区分坏参数、缺工具、空结果、超时、限流与服务异常；不要全部当成模型错误 |
| max_turns 与长度限制配合 | 分清单轮输出、总上下文、工具回包和收尾空间；轮数也不等于工具次数 |
| 小模型需要清晰协议 | 简洁、一致、少量有效示例值得验证；不等于标签越多或行为限制越强越好 |

当前 Process 仍有 `min(0.1,0.03*调用数)` 的正项，整体封顶后未必每加一次都增分，但仍需核查是否鼓励无增益调用。对截断样本的不恰当奖励会产生噪声，相关机制可参考 [DAPO](https://arxiv.org/abs/2503.14476)。

### 27.26 常见训练问题与对应方案怎样讲 {#question-27-26}

| 问题 | 优先定位与处理 |
| --- | --- |
| OOM 与显存压力 | 区分训练反向、推理 KV cache、模型加载和同步峰值；ZeRO、激活检查点、micro-batch、长度和并发各作用于不同部分 |
| rollout 进程“残留” | 独立服务常驻可以正常；异常孤儿 worker 才需按任务进程树回收，换端口不会释放显存 |
| 单步很慢 | 拆分生成、工具、Judge、更新耗时，观察 P50/P95 和长尾；减少候选和 batch 会减少工作量，也有采样与吞吐代价 |
| 工具或 Judge 被限流 | 限流器、缓存、有限重试与错误分类；评分缺失不应不加区分地等同内容零分 |
| 过早结束 | 判断必要证据是否足够；tool-first 只保证流程的一部分，调用一次或收到错误回包不等于获得事实 |
| 奖励高而曲线平 | 检查饱和、同分组、评审失败与课程权重变化，不能仅以均值诊断 |

图示方案中的 ZeRO-3、checkpointing、batch 1、vLLM 显存预算 0.8，当前脚本大多已配置。0.8 是显存预算而非计算利用率，也非通用最优值；训练端 ZeRO 不直接解决独立采样端 KV cache。减少 `num_generations` 要保留有意义的同题比较，当前组内优势配置不能简单改为 1。

“POI 换 Web”只能有条件降级：结构化经纬度与网页摘要不是相同输出能力，需保证后续路线查询仍可执行。“format 降、content 升”适合格式已稳定的阶段，但要看独立质量，不能为曲线好看而调分。

还应排查组内同分、重复轨迹与探索下降、reward hacking、循环与截断、NaN/Inf 和 KL 异常、请求与评分错配、token/logprob/mask 对齐、分布式通信与权重同步、评测污染及本地环境串扰。真正异步后还需控制样本策略版本与陈旧程度；[AReaL](https://arxiv.org/abs/2505.24298) 讨论了长尾等待与异步数据陈旧的权衡。这些是排查项，不代表本项目已实际发生每一种故障。

### 27.27 Base、SFT、RL 都怎样评测 {#question-27-27}

**简洁口述：** 当前 `llm_judge.py` 一次读取两份输出，在同题上比较调用轨迹摘要与答案；交换 A/B 位置再评一次，将对应分数平均，以减轻位置偏差。评分提示词要求 30% 路径、70% 答案，当前脚本最终汇总双方均分，未汇总胜率。

**答案评价重点：** 匹配度检查是否覆盖用户子需求和约束；可行性检查时间、交通、预算是否自洽；细节丰富度关注有依据的时间表、费用与预约信息；清晰度关注结构和可读性。细节数量不能替代事实可靠性，方案写得漂亮也不等于能够执行。路径侧看工具调用覆盖、需求相关性与冗余情况，不要求模型逐字模仿某条教师路径。

通常比较 SFT 对基线、RL 对 SFT、RL 对基线。这里 Base 实际指 Instruct 基线；当前脚本默认读 RL 与该基线，其他配对需换输入。路径摘要只提取 assistant 调用信息并去掉 think，没有完整工具回包，不能称为基于全部执行证据的事实核验。双向评分减轻而非保证消除位置偏差。

| 已保存配对结果（各 80 条） | 对照均分 | 实验组均分 |
| --- | ---: | ---: |
| SFT 对 Instruct 基线（`test_output/sft_vs_baseline.txt`） | 6.22625 | 6.5075 |
| RL 对 SFT（`test_output/rl_vs_sft.txt`） | 6.313125 | 6.851875 |
| RL 对 Instruct 基线（`test_output/rl_vs_baseline.txt`） | 6.118125 | 6.941875 |

这些是存档结果，不是本次重新调用裁判所得；旧记录的裁判型号和参数以当次日志为准。同一模型在不同配对中的分数会变化，不宜拼成统一绝对排行榜。应固定题目、工具环境、生成预算与评分口径，报告失败与丢失样本，必要时补充胜/平/负和不确定性。

当前离线脚本的“双向 A/B”不同于“多个大模型交叉评分”；后者须有多裁判记录。训练时的 Judge 是单候选与教师参考答案评分，GRPO 再按同题候选总分算优势，不是让 Judge 把全部候选两两互评。

若扩展为多裁判，可选择未参与数据生成和训练奖励的不同模型家族，分别保存评分、尺度与分歧，再明确采用均分还是投票。这样的角色隔离有助于降低评测耦合，但不能保证无偏。相对评审也不是所有任务都一定比绝对评分稳定；仍需盲化模型身份、交换位置，并补充关键事实、约束或最终产物的独立检查。这些补充检查是完善方向，不能仅凭现有调用摘要声称已经全部实现。

### 27.28 什么是 Reward hacking，本项目怎样缓解 {#question-27-28}

**简洁口述：** Reward hacking 指策略利用奖励设计或评分器的漏洞得到高分，却没有真正完成任务。例如，旅行 Agent 为细节分编造未核实票价，或为过程分增加无关查询。项目通过组合奖励、控制规则正分、重复与异常行为扣分，以及参考策略 KL 约束降低部分投机收益，并结合独立任务评测检查奖励与真实质量是否背离。

| 当前可核对的机制 | 作用与边界 |
| --- | --- |
| 六项组合，Judge 权重 60%→70%→75% | 让内容质量承担主要贡献；不能保证多个错误评分器组合后就正确 |
| 多数规则正向得分封顶约 0.3 | 限制仅靠格式达标获得的收益，仍需结合各项权重与方差 |
| Efficiency、Stage、Schema 等规则 | 对重复、过多调用、混合输出和协议异常给出信号，但不全面核验每次调用是否有业务价值 |
| `ref_model` 默认使用 SFT 模型，`beta=0.04` | 限制策略偏离参考分布；KL 不修复错误奖励，也不保证没有 hacking 或遗忘 |

依据：训练配置（`train_rl.sh`）、奖励实现（`ms-swift/examples/train/grpo/plugin/tooluse_reward_parser_aligned.py`）、策略损失（`ms-swift/swift/rlhf_trainers/grpo_trainer.py`）。本项目仍有调用次数正项、工具成功判断不严和评分转换等风险，详见第 28 节，不能说已经“完全避免”作弊。奖励与质量背离是需要调查的信号，单凭曲线还不能排除噪声、数据变化等原因。

扩展方向应与已实施措施分开：混合不同来源和阶段的候选有助于覆盖分布，但不能自动修复奖励漏洞；低置信度可能来自困难任务或证据不足，不能直接认定作弊，宜校准后复审或补证据。当前没有训练输出置信度的专用 RM，也没有实现 WARM。

[WARM](https://arxiv.org/abs/2401.12187) 对共享预训练来源、结构与参数对应兼容的多个奖励模型微调后做权重平均，不是任意模型参数都能直接平均。当前外部 Judge API 不能直接进行权重空间平均。也不能把“不使用 KL”称为投机取巧；是否保留与具体目标和算法有关。定义与过度优化问题可参考 [Reward Model Overoptimization](https://arxiv.org/abs/2210.10760)。

### 27.29 为什么选 GRPO，不选 PPO、DPO 或其他变种 {#question-27-29}

**简洁口述：** 我们把 GRPO 作为任务适配、资源与生态之间的工程基线。旅行规划可对同题多条完整轨迹计算标量奖励，适合组内比较；相对常见 PPO actor-critic 实现，GRPO 不额外训练 critic，减少相应显存和训练开销；Swift 又已有多轮 scheduler、奖励插件和 vLLM 集成，便于先把执行与评分链路做好。

当前默认每题六个候选仍会增加生成、工具与评审成本，不能说 GRPO 总耗时必然更低。“不训练 critic”不等于不需要参考模型或 Judge：critic 估计价值基线，Judge 提供奖励，两者职责不同。

| 备选 | 适合怎样解释取舍 |
| --- | --- |
| PPO | 能处理在线交互；常见实现还需要价值学习，当前先采用无需额外 critic 的基线 |
| 常见离线 DPO | 利用 chosen/rejected 偏好对；当前重点是持续执行环境并按奖励优化，轨迹偏好训练仍可作为备选 |
| DAPO、GSPO 等 | 针对具体长度、稳定性或更新问题做同预算对照，不能未经实验就断言收益很小，也不只适用于发论文 |

GRPO 是算法选型，不是模型选型。成熟框架有支持能降低接入成本，但迁移仍要核对模板、mask、loss 聚合、KL、采样概率与权重同步。没有记录就不报“数据占 70% 时间”“算法只能提升两分”等数字，也不声称 GRPO 最优；比较时控制初始模型、任务、奖励与计算预算，报告成功率、质量和成本。

依据：[DeepSeekMath 原始论文](https://arxiv.org/abs/2402.03300)、[verl 官方实现说明](https://github.com/verl-project/verl/blob/main/docs/algo/grpo.md)、[DPO 原始论文](https://arxiv.org/abs/2305.18290)。

### 27.30 场景题：长程 Agent 历史无限增长，怎样管理上下文 {#question-27-30}

**简洁口述：** 先做预算与分层，再考虑学习式记忆。当前上下文保留固定协议、任务约束、已验证状态、近期完整交互和按需检索的历史证据；原始轨迹外置保存。接近预算前压缩冗余、生成可追溯摘要，并为下一轮模型输出和工具回包留空间。

旅行任务应保留预算、日期、用户偏好、已选路线与未解决约束；票价和天气附来源、时间与适用范围，避免过期事实进入后续规划。摘要和检索不能保证无损，应能定位回原文；调用与回包的必要关联也不能在截断时丢失。外置存储仍需去重、更新与淘汰，不能把无界历史重新全部塞回 prompt。

进一步可把记忆操作放进工具动作空间：

| 记忆职责 | 操作 |
| --- | --- |
| 持久记忆维护 | `ADD / UPDATE / DELETE` |
| 活跃上下文管理 | `RETRIEVE / SUMMARY / FILTER` |

对应研究为 [Agentic Memory / AgeMem](https://arxiv.org/html/2601.01885v1)：轨迹先构建 LTM，再重置 STM、保留 LTM 并注入干扰，最后联合记忆完成任务。这里的三阶段交互结构不等于“SFT→RL”三段训练。其核心是学习何时存、取、改和压缩，外部数据库仍然可以存在，并不要求存储可微；也不能把所有 RAG 都概括为静态或不能学习。

若在本项目扩展，奖励应同时看任务成功、关键事实与约束保留、检索相关性及实际成本，不能只奖励压缩率或记忆操作次数。无论是否使用 RL，硬预算保护仍要存在。固定 token 预算比较滑动窗口、规则摘要检索和学习式记忆的成功率、证据保真度与成本；当前项目主要是预算和回包截断，尚未实现这套记忆系统。

### 27.31 场景题：用 OPD 替代或补充 GRPO，怎样设计 {#question-27-31}

**简洁口述：** OPD 是 On-Policy Distillation，即在学生自身策略生成的数据上蒸馏。我会保留多轮工具环境，让学生自己采样动作和答案，再用固定教师在学生实际访问的历史前缀上提供 token 级概率监督，更新学生，最后以真实任务质量和成本比较是否值得采用。

流程是“学生执行—保存生成 token、可见历史和采样概率—教师对这些 token 打分—计算对齐后的蒸馏信号—更新学生”。与预先生成教师答案再模仿不同，它训练学生面对自身生成所导致的状态。相关研究早已有 [GKD](https://arxiv.org/abs/2306.13649)，不能把起源或效果直接归因于某个近期商业模型发布。

一种 sampled-token 信号是 `s_t=log pi_T(a_t|h_t)-log pi_S(a_t|h_t)`。当动作按学生策略采样时，其条件期望对应负 reverse KL；单个差值可以为正或负，不等于已经计算完整词表 KL，也不等于教师准确定位了语义或逻辑错误。可参考 [Thinking Machines 的 OPD 实践](https://thinkingmachines.ai/blog/on-policy-distillation/)；OPD 不必总采用 GRPO、GAE 或同一种散度。

当前 GRPO 的轨迹末端奖励反馈较粗，但优势会广播到参与 loss 的 token，不能说“前面 token 没有训练信号”。教师匹配项与 SFT 参考策略 KL 的用途不同；是否同时使用及其权重需要实验，而不是默认相加。

| 接入要点 | 需要处理什么 |
| --- | --- |
| 教师可评分性 | 支持对学生已经生成的序列计算概率；只返回教师生成文本的接口不够，需验证服务能力或自部署 |
| token 与模板对齐 | 核对词表、tokenizer、角色模板和概率口径；不同词表不能直接逐索引比较 logits |
| 监督区域 | 通常监督学生生成的 assistant 内容，用户与工具回包作为条件；明确 token mask、padding 与截断 |
| 因果一致性 | 教师评分动作时使用学生当时可见历史，避免引入未来工具反馈或标准答案 |
| 成本与可靠性 | 教师不反传仍有前向与显存成本；教师偏好不等于任务正确，需环境结果验收 |
| 阶段权重 | “早期更依赖教师、后期降低”可以消融，但不能假定总是最优；由验证质量、成本和偏移情况决定 |

不能仅在当前 `List[float]` 奖励插件里增加“第七项”就声称完成 token 级 OPD。若把它压成轨迹标量，会丢失逐 token 的区分；需让采样、教师评分和训练 loss 保留这些信号。保留原 GRPO 并采用 `L=L_GRPO+lambda*L_OPD` 属于混合方案；纯 OPD 可以不用原六项作为训练奖励，但仍需执行校验和独立评测。

本地虽然有 GKD Trainer，但此版本显式禁止 GKD 与 `multi_turn_scheduler` 同时启用，不能只改 `rlhf_type` 开关。本地参数限制（`ms-swift/swift/arguments/rlhf_args.py`）。以上是扩展设计，未在本项目实现或验证。

### 27.32 项目做完有哪些收获 {#question-27-32}

**简洁口述：** 第一，Agent 训练依赖完整交互链路，工具可用性、限流与超时、状态一致性及可追溯日志直接影响轨迹质量、奖励可信度和采样成本，需要与算法一起设计。第二，上下文长度是一项资源与效果预算，应根据真实轨迹分布、峰值显存、吞吐和任务成功率确定，再逐步增加长任务并验证收益。

“环境比算法重要”可以表达本项目的投入重点，不能成为对所有场景的定量规律。没有记录不报 80% 工作量、每卡 80G 等数字；单步工具成功率也不自动等于长任务成功率，依赖步骤可能放大失败。

参数量不直接决定可靠上下文长度；模型支持、位置编码、训练长度分布、激活或 KV cache、并发与算力都会影响结果。逐步加入更长样本属于长度课程，不自动等于突破模型原生窗口的长度外推。实际预算与已有 SFT 实测分别见第 26 节，不能用某次 SFT 峰值替代当前全参 RL 的显存结论。

## 28 项目表述与实际实现的差异清单 {#chapter-28}

以下依据 2026-10-21 本轮只读核对。它们是静态代码或数据可见的问题，不自动等同于某次训练故障的已证实根因。本轮仅整理文档，未修正训练代码、重导出数据、重新训练或调用付费 Judge。

### 可以直接核对的实现问题

| 项目 | 当前可见行为 | 表述与后续验收 |
| --- | --- | --- |
| 工具调用严格 JSON | 850 条 SFT 样本共 4979 个调用块均只能按 Python 字面量解析，arguments 均为字符串；格式脚本用字典字符串插值 | 不能声称严格协议验收通过；将参数规范成对象并用 JSON 序列化，重导出后逐块校验 |
| 空工具返回检测 | 转换后回包位于 user 的 tool_response 标签，但空回包规则检查 tool 角色 | 需统一检查的表示；零报错计数不能证明该规则有效 |
| 质量分级核验 | 程序按 Judge 的 verdict 留样，没有重新计算 overall_score 与阈值 | 增加字段、分值与等级一致性校验；保留 raw 评审与失败状态 |
| 工具“成功”状态 | valid_tool_calls 在拿到函数名后就增加，加载或执行失败仍可能标 tool_executed，saw_tool_response 也会置真 | 区分可解析、已执行、执行成功与有效证据；不能把收到反馈当成功取得事实 |
| 答案完整性 | check_finished 同时接受完整 answer 或仅有开始标签；提取文本却依赖闭合标签 | 可能状态完成但答案为空；完整答案、截断与格式失败应分开 |
| Judge 分数转换 | 只有 raw_score>1 才除 10，0—10 制中的 1 会变 1.0，2 却变 0.2 | 明确唯一评分尺度，校验边界值，避免排序倒置 |
| Judge 失败处理 | 缺参考、缺 API key、请求或 JSON 解析失败可能都返回 0 | 将评分缺失与低质量区分，统计覆盖率，再决定重试、重采或训练处理 |
| 工具与评分耗时 | scheduler 逐个执行工具，协程桥接 thread.join 阻塞调用线程；Judge 使用同步 HTTP 请求逐条评分 | 实测分段耗时再考虑异步执行、独立 worker 或缓存，不能仅凭 async 标志声称全链路非阻塞 |
| 推训控制规则 | 推理与 scheduler 的反馈角色、重复判断、重试和收尾不同 | 用同一批正常与异常轨迹对照；共享解析器只是对齐的一部分 |
| 多目标归一化 | 课程插件向 Trainer 返回一列混合 reward | 要做六维 GDPO，须分别暴露子奖励并处理新的权重调度 |

定位：格式脚本（`data_clean/format_filter.py`）、质量筛选（`data_clean/quality_filter.py`）、奖励插件（`ms-swift/examples/train/grpo/plugin/tooluse_reward_parser_aligned.py`）、scheduler（`ms-swift/examples/train/grpo/plugin/tooluse_multi_turn_scheduler.py`）、独立推理（`run_tool_loop_infer.py`）、GRPO Trainer（`ms-swift/swift/rlhf_trainers/grpo_trainer.py`）。数据与标签检查的口径见第 24 节。

### 面试中需要证据支撑的说法

1. **冷启动必需、直接 RL 更差：** 需同起点、同任务和预算的消融；当前只有选择这条路线的依据，不能引用不存在的对照实验。
2. **某个教师或 Judge 效果最好：** 需当次模型 ID、任务集合、质量、耗时和费用记录；不要按公司能用的 API 编造经历。
3. **prompt 是训练失败根因：** 先排除数据渲染、mask、截断与评分问题，再做固定条件对照。
4. **已做难度课程和样本加权：** 当前作为建议；须有标签、采样器或损失接入、实验配置与结果，不能仅新增字段。
5. **多裁判交叉验证、八卡某型号已跑通、数十次调用成功：** 分别查评测日志、硬件记录和真实轨迹；A/B 换位、GPU 数配置与最大轮数不能替代这些证据。
6. **清洗后质量或成功率：** 明确输入分母、筛选规则和失败样本；测试题若被筛选应说明口径，不能按被评测模型是否成功来删题。

### 建议补齐的实验记录

每条轨迹至少记录任务与轨迹 ID、策略版本、模型轮数、实际工具次数、解析与执行状态、各段耗时、输入输出 token、终止原因、原始子奖励、当前权重与评分有效性。汇总时关注任务成功率、格式正确率、真实工具成功率、最终答案完成率、截断率、重复调用率、组内奖励方差和长尾耗时。

回归任务覆盖正常多工具、空结果、坏参数、超时、限流、缺少必要信息、答案标签不完整、重复调用与上下文接近上限等情形。先用少量任务核对执行与评分，再跑少量训练更新验证数据、监督和同步；模型效果使用固定独立任务与可信检查验收。文档记录的风险与优化建议不代表这些回归和消融已经执行。

### 续补研究方案的实施边界

1. **Reward hacking 防护：** 当前能核对组合奖励、规则正分控制、效率与协议扣分及 KL；尚不能证明已消除作弊。专用置信度 RM、多来源去偏与 WARM 均需另行实现和评估，不能列为已完成措施。
2. **GRPO 选型：** 当前是有框架支持的工程基线，未提供与 PPO、DPO、DAPO、GSPO 的同预算消融，不能声称算法收益差异已被证明。
3. **多裁判评测：** 当前脚本的固定 Judge 双向 A/B 不等于自动多模型聚合；若有其他裁判的存档，应分别核对其覆盖、版本和聚合记录。
4. **Memory 与 OPD：** 当前未实现学习式记忆或 token 级教师蒸馏；Swift 的 GKD 多轮限制也需处理。新增工具定义或一个标量 reward 字段都不能单独证明这些系统已接通。
