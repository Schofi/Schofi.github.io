项目记录里有一个很具体的发现：850 条 SFT 训练样本中，共有 4979 个工具调用块。它们都能按 Python 字面量解释，却全部无法被严格的 JSON 解析器直接读取。

数据已经经过清洗，推理端也有格式修复兜底。但这两件事加在一起，仍然不能证明模型正在学习正确的工具协议。

整理这个旅行规划 Agent 时，我越来越关注这些衔接处：需求怎样变成任务，任务怎样变成工具轨迹，轨迹怎样进入训练，奖励又怎样对应一份能够执行的行程。任何一环的含义发生偏移，后面的训练曲线和评测分数都可能变得难以解释。

本文依据整理至 2026 年 10 月 21 日的项目笔记。涉及数据、运行时间和评测的数字，均保留原记录的范围；已有存档、当前实现问题与后续改进方向分别说明。

## 1. 先定义什么是一份能够执行的行程

这个项目以 Qwen3-4B-Instruct-2507 为学生模型，采用教师轨迹采集、LoRA SFT 冷启动和在线 GRPO 的路线，目标是改善多约束旅行任务中的信息获取、工具使用和方案生成。

用一个需求就能说明任务的难点：

> 从上海出发去黄山，安排三天旅行，总预算 6000 元。至少游览 6 处景点，其中 3 处适合拍照。餐厅尽量靠近路线，考虑营业时间、交通耗时和天气，并给出分项费用。

这是一条需求示例，不能预先假定所有要求都能同时满足。系统需要用证据判断可行性。

如果方案花费 10000 元，或者最后一个景点在到达前已经闭馆，即使文字完整、描述生动，核心任务也没有完成。

我会先把要求拆成两类：预算、天数、固定到达时间等硬约束，用来判断方案能否接受；拍照体验、餐饮风格、轻松程度等偏好，用来比较可行方案。遇到缺少出发地、预算范围不清或约束冲突的情况，应澄清或解释原因。

这一步会影响后面的所有设计：工具要查什么，种子题怎样写，奖励如何打分，最终测试又检查什么。

## 2. 工具提供证据，执行器负责把动作落到现实

旅行规划需要地点、路线、天气、营业信息和费用依据。模型生成工具名与参数，执行器解析和校验，再把真实结果或明确错误交回模型。模型根据这些反馈决定下一步。

当前项目的工具来源并不完全相同：

| 能力 | 项目记录中的实现 | 使用边界 |
| --- | --- | --- |
| 网页搜索与访问 | Firecrawl 搜索、抓取，必要时做网页解析和信息提取 | 摘要不等于完整原始网页，需要保留来源与时间 |
| 天气、地点和周边 | 高德相关接口 | 城市、日期、位置等参数必须对应当前任务 |
| 路线规划 | 高德路线接口 | 地点与交通方式确定后，才能解释距离和耗时 |
| 航班、火车票 | 辅助模型生成模拟信息 | 适合开发流程，不能作为真实票价、余票或可预订班次 |

尤其容易混淆的是最后一行：工具请求了真实的模型 API，并不意味着返回的就是来自票务系统的真实事实。工具名称也不能证明数据来源。

并发执行同样需要按依赖关系决定。已知目的地时，天气与景点搜索可以独立进行；计算两个地点之间的路线，则需要先获得对应地点。模型一次输出多个调用，还需要执行器真正调度它们，才可能减少等待。

记录工具状态时，至少要区分：调用是否可解析、是否开始执行、是否执行成功、是否取得足够证据。收到一条失败回包，只能说明得到了反馈，不能当作查到了事实。

## 3. 数据扩展之前，先固定训练与测试的边界

项目记录中的初始任务包含 306 条训练种子和 100 条测试题。扩展后的训练问题为 1835 条，其中包含全部 306 条原题和 1529 条新增的不重复问题。

如果每条种子恰好生成 5 条，再保留原题，理论数量是 1836 条。最终文件少一条，只能说明需要进一步核对生成与去重记录；不能仅凭这个差额，断言某一次请求失败。

比数量更重要的是来源关系。比如，同一个黄山需求改写成：

- “用 6000 元安排从上海去黄山的三天行程。”
- “规划上海出发的黄山三日游，总花费控制在 6000 元。”

如果一条进训练、一条进测试，即使字面不同，测试仍可能主要衡量对同一需求的熟悉程度。

因此，应先按原始需求分组，再划分训练、开发验证和最终测试。随后只在各自集合内部扩展，并保留父样本标识。更换目的地不自动产生新能力覆盖，使用相同目的地也不自动构成泄漏；要检查来源、约束组合和答案结构的相似程度。

原记录还指出，扩展文件只保存了 `question`，生成时使用的种子索引没有一起输出。这个缺口会让之后的来源追踪变得困难。下一版数据应至少携带种子标识、派生关系、集合归属和生成配置。

人工编写种子时，我更倾向于让多人分别覆盖预算、同行人、交通方式、偏好和信息缺失等情形。多样性应体现在需要作出的决策上，而不只是城市名和问法的变化。

## 4. 教师采集的单位是执行轨迹

Query 扩展得到的是更多问题；教师 rollout 得到的是完成问题的示范过程。只保存最终攻略，无法向学生展示该查什么、怎样使用回包，以及遇到错误后如何调整。

一条有用的轨迹应包括用户需求、工具定义、调用参数、工具返回、后续动作、最终回答和结束原因。这里的过程是可观察的交互记录，不需要补写模型没有公开的内部思维。

采集循环可以概括为：

```text
用户需求
  → 教师生成工具动作
  → 执行器校验并调用工具
  → 返回结果或明确错误
  → 教师继续查询、调整或结束
  → 保存轨迹、状态和必要的成本信息
```

### 98 条正常收尾，不等于 98 条正确行程

一次存档日志记录了 100 题测试采样：98 条正常收尾、2 条失败，整批耗时约 4 小时 3 分钟。这里的 98% 是该批次的答案生成完成率，不是经事实核验后的行程正确率。

另一段日志只记录了 13 条训练扩展任务完成，累计约 2013 秒；其中最慢一条约 545 秒，占这段已完成任务耗时的约 27%。后续批次没有完整结束记录，因此不能用这 13 条代表整批训练数据的完成情况。

这些记录提示了两个成本问题：平均耗时可能被少数长任务明显影响；模型轮数、工具调用次数和底层网络请求数必须分别统计。工具内部的重试和辅助模型调用，也可能产生额外成本。

### 没有真人回复时，澄清也需要一个结束状态

旧轨迹里有一条“三天两晚、400 公里以内”的需求，没有说明从哪里出发。模型要求澄清是合理的，但批处理环境没有真人回答，循环仍继续请求模型。同一段澄清回复重复了 44 次，直到耗尽 50 轮预算，期间没有工具调用。

问题出在交互状态：系统没有把“等待用户补充信息”当作一种可结束的结果。

改进方向是将 `needs_clarification`、`completed`、`tool_error`、`timeout` 和 `incomplete` 等状态分别记录。连续轮次没有新增事实、有效动作或任务进展时，也应有限重试、换策略或结束。最大轮数只能控制最终开销，不能代替进展判断。这些属于后续需要验证的改进，原记录没有显示该空转案例已修复重跑。

## 5. 三级清洗，要分别检查结构、协议与内容

项目把清洗分成三层：

| 层级 | 关注点 | 不能据此证明的事情 |
| --- | --- | --- |
| 规则过滤 | 空输出、未完成、明显无效轨迹等 | 通过规则不代表方案真实可行 |
| 格式规整 | 消息角色、调用参数、回包配对、答案边界 | 标签完整不代表工具查询成功 |
| 质量评审 | 需求覆盖、工具使用、答案合理性 | Judge 通过不等于事实已独立核验 |

存档报告记录过从 1698 条输入筛至 1143 条、再保留 1081 条的过程。但这些数字不能证明当前导出脚本的每条检查都有效，也不应与其他日期的轨迹数量直接拼成一条无损的数据流水线。

### 严格 JSON 与“解析器能修好”是两回事

开头提到的 4979 个调用块，问题集中在 Python 字典表示和字符串化参数。下面是简化示意：

```text
待修正的表示：
{'name': 'search', 'arguments': '{"query": ["杭州天气"]}'}

目标 JSON：
{"name":"search","arguments":{"query":["杭州天气"]}}
```

单引号字典不是 JSON；此外，本项目选定的工具协议要求 `arguments` 为对象，不能继续把其中的 JSON 存成字符串。推理时可以有修复兜底，但训练前仍应逐块验证。否则，模型可能被要求学习一种表示，执行器却期待另一种表示。

这项静态检查不能直接证明它导致了某次训练失败。它能说明的是：严格协议验收尚未通过，继续增加训练量无法替代数据修正。

还需要检查**最终渲染后的训练文本**。教师返回的结构化 `tool_calls`、Qwen 模板里的文本标签和执行器使用的工具角色，可能是不同层的表示。选择手写 `<tool_call>` 标签后，就不应再让同一次调用通过结构化字段重复渲染。

关联 ID 则要按用途处理：原始执行记录需要它来配对调用与回包，尤其是并发调用；模型是否需要预测这些 ID，应由选定协议决定，不能从所有日志中一删了之。

清洗规则本身也要接受检查。原记录中，工具回包已经转换成 user 消息，但“空工具回包”规则还只检查 tool 角色。这种规则即使报出零个问题，也可能只是没有命中真正需要检查的数据。

## 6. SFT 冷启动：先确认模型究竟在学什么

SFT 学习固定的教师示范；在线 GRPO 再让当前策略自行执行任务，按奖励更新。这个项目选择先 SFT，是希望学生先熟悉调用协议、反馈利用和结束方式，并不意味着所有 Agent 都必须经过同样的冷启动。

检查 SFT 时，我会沿着这条链路看：

> 原始消息 → 预处理 → 模板文本 → 输入 token → 监督标签和权重 → 实际工具调用。

需要区分工具内容根本没有进入输入，与进入输入后没有参与监督。最终答案仍被监督时，整体 loss 可以下降；这不能单独证明工具名、参数和动作边界已经学好。遇到调用失败，也应先排查这些环节，再把原因归结为提示词或模型能力。

### 训练预算应从长度分布开始

项目的长度检查记录显示：850 条样本的近似平均长度为 10435 tokens，P95 为 20808，最长为 49476，其中 7 条超过 32768。统计采用手工拼接边界，与框架实际模板可能存在差异，最终有效条数仍要看训练预处理记录。

项目另有一次四卡 SFT 的历史日志：

| 指标 | 存档记录 |
| --- | ---: |
| 有效样本 | 843 条 |
| 更新次数 | 420 次 |
| 训练循环耗时 | 3557 秒，约 59 分钟 |
| 峰值显存 | 约 46.35 GiB／卡 |

这是当次数据、软件和硬件条件下的记录，日志没有明确保留 GPU 型号。它不能证明换一张新卡也能在一小时内完成。

四卡数据并行通常让各卡持有模型副本；单条长样本需要的显存不会简单除以四。[PyTorch DDP 文档](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html)也明确说明了这种多副本机制。租卡前更有用的做法，是先用覆盖长尾长度的少量样本试跑，测量稳定后的秒／步和峰值显存，再估总预算。

工具回包即使不直接参与 loss，仍可能作为上下文消耗计算和显存。因此，上下文长度同时是一项质量预算和资源预算。

## 7. GRPO：让奖励对应真正的任务进展

在这个任务里，同一个旅行需求可以产生多条合理轨迹。当前配置为每题采样六个候选，再用组内相对奖励优化策略。[DeepSeekMath](https://arxiv.org/abs/2402.03300)提出的 GRPO，为这类组内比较提供了算法基础；它不额外训练传统 PPO actor-critic 实现中的 critic，但仍有采样、工具执行、参考策略和评审开销。

这里更新的是模型策略。地图查询、网页抓取等工具函数不需要可微，也不会因为 GRPO 更新而自己获得新参数。

项目采用六项组合奖励：Process、Tool Schema、Answer Tag、Stage、Efficiency 和 LLM Judge。前五项是规则，最后一项是模型评审；它们最终合成每条轨迹的一个标量，不是六个训练出来的奖励模型，也不是逐工具步骤的过程奖励模型。

按默认 200 步配置，Judge 权重从 0.60 调到 0.70，再到 0.75，规则项仍保留权重。这个设计体现的是阶段性侧重点。权重变化本身就会改变总分尺度，因此 reward 曲线上升还需要结合固定规则的评测来解释。

### 一个很小的分数转换错误，也会改变学习方向

项目记录发现，Judge 原始分数转换只在“分数大于 1”时除以 10。若原始量表是 0—10，这会让 1 分变成 1.0，2 分却变成 0.2，造成排序倒置。

在讨论复杂算法之前，这类边界值必须先验收。还要把评审调用失败、缺少参考答案和真实低质量区分开；统一返回零分，会让环境或评分故障混进策略表现。

Reward hacking 也应落到具体检查：无关查询是否也能增加过程分？编造更多细节是否能讨好 Judge？工具失败是否误记为执行成功？格式分是否掩盖了预算或时间冲突？

这些实现风险不等于已经观察到模型主动作弊。组合奖励、重复扣分和参考策略 KL 可以提供约束，却不能修复错误的评分器。预算、时间和事实一致性仍需要可复核的检查。

另一个边界是推训一致性。独立推理循环与训练 scheduler 共享部分解析逻辑，但错误反馈、重试和结束规则仍有差异。采样服务与训练服务分离，也不自动意味着采样和参数更新已经完全异步重叠。对当前工程，更重要的是先明确两边实际执行的状态机，再测吞吐与收益。

| 对照 | 对照组均分 | 实验组均分 |
| --- | ---: | ---: |
| Instruct 基线 → SFT | 6.226 | 6.508 |
| SFT → RL | 6.313 | 6.852 |
| Instruct 基线 → RL | 6.118 | 6.942 |

这些记录给出了值得进一步检查的改善信号，但不是本次新跑的实验，也没有提供完整的统计显著性结论。各配对独立评分，同一模型在不同配对中的分数会变，不能把几列数拼成统一的绝对排行榜。

现有评审会交换 A/B 位置后再评分，以减轻位置偏差。它不等于多个独立裁判交叉验证。评审输入包含调用摘要和答案，而非全部工具回包，因此也不能据此宣称所有票价、时间和行程事实都已核验。

我会把后续验收拆成三个层次：

1. **任务是否成立**：预算、时间衔接、必须满足的地点要求是否通过检查，信息缺失和冲突是否如实说明。
2. **交互是否可靠**：工具参数是否合法，回包是否有效，是否存在重复、空转、截断或不完整收尾。
3. **成本是否值得**：每条可用方案的模型与工具费用、人工修订量、平均及长尾耗时。

比较 Instruct、SFT 和 RL 时，应固定任务、日期基准、工具条件、生成预算和评分规则，保留失败与丢失样本。开发中反复用于调奖励或挑模型的集合，应承担验证用途；最终测试仍需保持独立。

数据清洗裁判、训练奖励裁判和最终评测裁判，也要分别记录配置和职责。教师参考答案可以辅助奖励，但教师生成、Judge 通过与经过事实核验的金标准，是不同的证据级别。

## 接下来优先补什么

这份复盘留下的下一步很具体：先修正并重导出工具协议数据，核查模型可见文本与监督标签；给澄清和无进展循环明确的结束状态；校准 Judge 量表、缺失评分和工具成功判定；再把检查点、训练配置、完整轨迹与评测输出关联起来。

后续训练方法可以继续探索，但应先让输入、动作、反馈和评分的含义可信，新实验的差异才更容易解释。

我希望下一版项目报告能让读者顺着一条需求，找到它的来源、调用证据、训练用途和最终验收结果。届时再讨论模型提升了多少、每条行程便宜了多少，数字才有明确的落点。
